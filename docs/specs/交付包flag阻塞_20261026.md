# 交付包重打阻塞：已解决（2026-10-26）

> 状态：**已解决**。根因不是"融合树带 flag"，而是**门禁对非 git 目录的判定方式**。
> 原以为要三选一，实际是门禁自身的缺陷。保留本文作为复盘。

## 结论先说

| 动作 | 结果 |
|---|---|
| 交付面排除 `CTF-Agent_融合/` 与 `cmd/runner/`（USER 拍板：评委不需要其源码） | 纳入文件 3616 → **2350**，flag 1791 → 1108 |
| 修 `secret_guard` 的「非 git 目录」分支 | `--dir staging` 由 **恒红** 转为 **PASS** |
| 重打交付包 | **2617 条目 / 171.5 MiB / 七项红线全过** |

## 真根因：`secret_guard` 对非 git 目录一律 fail-closed

`secret_guard.py` 里 `tracked_set = _git_tracked(root)`，非 git 目录返回 `None`，
随后走这条分支：

```python
if tracked_set is None:
    if not hits:
        return (False, "无任何明文 flag 命中 → 放行", ...)
    return (True, f"该目录不在 git 仓库中，无法区分新旧，且含 {len(hits)} 条明文 flag → fail-closed", ...)
```

而交付包的 staging（`D:/tmp_sam_delivery/staging-*`）**天生不是 git 仓库**。
于是只要包里含任何 flag 形态文本就恒红 —— 本仓 `data/ctf_benchmark`（机验基准集）与
`internal/` 下大量测试夹具本来就有 flag，**必然命中**。

⇒ **自 2026-10-25 引入 flag 卡口起，交付包就一直打不出来**，只是这期间没人重打过，
所以没暴露。10-26 这次重打才撞上，最初被误判成"合并带进了 flag"。

## 修法（`scripts/secret_guard.py`）

新增环境变量 `SECRET_GUARD_TRACKED_ROOT`：允许调用方指明「这份内容来自哪个仓库」，
按该仓库的 `git ls-files` 判定跟踪状态，从而走正常的三个上限卡口：

| 卡口 | 实测 | 上限 |
|---|---|---|
| `tracked_hits`（明文 flag 总数） | 1108 | 2535 |
| `real_brand_hits`（真赛事品牌） | 84 | 245 |
| `known_answer_hits`（sha256 命中题库真值） | 344 | 1144 |

**判据一条没放松**：只替换"跟踪状态"的来源；未设置该变量时行为完全不变（仍 fail-closed）。
`make_delivery_package.py` 在红线 3 调用时传入 `SECRET_GUARD_TRACKED_ROOT=ROOT`。

## 附带修掉的误报

融合树的 `sk-` 形态串全是**测试夹具**（`sk-env…890`、`sk-fal…345`、`sk-qia…est`、
`sk-sec…456`，其中一处正是在断言"掩码不得泄漏完整 key"）。已按「path + 行内容 sha256」
双钉死补 14 条白名单（`scripts/secret_guard_allowlist.json`），复验**真实凭证命中 0**。
