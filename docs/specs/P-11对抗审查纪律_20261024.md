## 一、需求类型识别（收到任务的第一件事）

先判类型，再选动作；类型判错，后面全错。

| 类型 | 判据 | 允许的第一动作 |
|---|---|---|
| 实施 | 有明确交付物与验收口径 | 查路由表 → 读锚点 → 动手 |
| 方案讨论 | "怎么做比较好"，尚无定稿 | 出方案（含"明确不做"），**不写码** |
| 决策 | 存在互斥选项，取舍属用户 | 列选项+代价，等拍板 |
| 可行性 | "能不能做到"未知 | 最小验证实验，**不建完整实现** |
| 诊断 | 有故障现象 | 先复现，再归因，后修复 |
| 纠错 | 指出已有产出有错 | 先核实指摘是否成立，再改 |

## 二、提问边界

- 只问**前置已全部敲定**的问题；下游问题等上游结论，不抢跑。
- **事实类自己查**（grep / 读文件 / 跑脚本真值源），**取舍类必须问人**（影响范围、优先级、对外口径）。
- 禁止把无歧义的维度列出来凑数提问——问出来的是"确认"，不是"信息"。

## 三、共识门禁（动手前）

1. 未确认前**不动手写码**；方案未定稿时产出的任何代码都是废料风险。
2. **终点锚**：验收标准必须逐字抄需求原文，禁止改写成"更清楚的版本"——
   方案忠实于改写版而非原文，是本项目 10-06 质检（4/10）复盘定位到的根因之一。
3. 计划必须含"明确不做"一节（与 P-08 对齐），范围蔓延挡在写第一行代码之前。

## 四、对抗审查（方案写完、准备动手之前）

1. **换一个独立认知源**审查：另起会话 / 另一个 agent / 换一份文档视角，**禁止自查自过**。
2. 输出分级：**高危 / 中危 / 低危 / 待澄清**，每条带文件位置与理由；没有证据的问题不写。
3. 修订记录**逐条回应**：采纳写采纳理由，驳回也必须写驳回理由——静默忽略等于没审。
