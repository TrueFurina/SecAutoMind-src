# flag 泄露专项分析：为什么修了 19 个脚本还在漏（2026-10-31）

> 触发：用户指出「flag 相关问题太多，需要单独深入研究，比如训练时答案泄露、明文入库」。
> 本文只做两件事：**用实测数据说清现状**，**指出结构性根因**。不含"加强意识"这类空话。

> 🔴 **2026-10-31 修订（本文第一版有硬错误）**：第一版把「历史重写」排在 P2 并写
> 「除非要公开仓库，否则不建议做」。**实测仓库已是 PUBLIC**（`gh repo view` → `visibility: PUBLIC`），
> 且 `data/ctf_benchmark/benchmark.json` 等含明文答案的文件**已在远端分支上**
> （`git cat-file -e ghssh/docs/race-day-card:data/ctf_benchmark/benchmark.json` 命中，
> 该文件内明文 flag 形态 74 条）。所以这不是"未来风险"，是**当下的公开暴露**。
> 修订后的排序见第 6 节；第一版的 P0-1（记忆脱敏）与 sha256 建议也一并降级/修正。

## 0. 一句话结论

**项目一直把 flag 泄露当成"检测问题"（文件里有没有敏感串），但它本质是"数据流动问题"** ——
同一份答案从题库出发，被复制到 benchmark、生成器源码、测试夹具、文档、会话记忆、交付包共 6 个面。
每新增一个面就复发一次；检测做得再准，也只是追着面的增长跑。

## 4. 根因：三个结构性错配

### 4.1 「题面」与「答案」同源同文件

题库（西湖论剑归档、`data/questions_*`）里答案和题面在同一个 json。任何"整体摄入"的流水线
（迁移、备份、融合、打包）都会连答案一起带走。**只要没有物理隔离，"记得排除答案"就是靠人。**

### 4.2 「需要答案」与「不能有答案」是同一个文件的两个消费者

自测/评测要答案，交付/入库不能有答案。于是同一个文件被迫同时满足两个矛盾需求 →
只能靠"跑完再改"（redact）→ 改之前的那一版已经进了 git 历史。

### 4.3 「形态判据」打不过「内容判据」

品牌正则（`DASCTF{...}`）可被改名洗白；只有 **sha256 命中真值**是硬判据。但它的覆盖率取决于
真值集大小（当前 473 个 sha256 / 270 个 benchmark json），且**新题一进来就没覆盖**。

## 5. 现有防线与盲区

| 面 | 现有防线 | 盲区 |
|---|---|---|
| 入库 | `secret_guard` 三卡口（tracked/real_brand/known_answer）+ CI | 基线"只许减不许增"，新增面不受约束 |
| 生成器 | `externalize_generator_flags.py` | 只覆盖被它列举的生成器，新写的生成器默认内联 |
| benchmark | `check_benchmark_plaintext_answer` / `migrate_*_to_sha256` | 迁移做了一半（7 个文件仍有明文） |
| 记忆 | **无** | agent 写入即落盘，事后才扫 |
| 历史 | **无** | redact 只改工作树，历史仍在 |
| 交付 | `make_delivery_package` 红线 | 靠 staging 扫描，不阻止源头产生 |

**最大盲区是"记忆面"和"历史面"** —— 前者每天都在长，后者不可逆。

## 6. 建议（2026-10-31 修订版：第一版有 4 处判断偏差）

### 先说第一版错在哪

| 第一版说法 | 实际 | 性质 |
|---|---|---|
| 「P2 历史重写，除非要公开仓库」 | **仓库已是 PUBLIC**，答案已在远端 | **硬错误**：没验证可见性就下结论 |
| 「P0 记忆层写入前脱敏」 | 记忆是**症状**，源头是 agent 手里有明文 | 排序错误：把兜底当治本 |
| 「迁移到 sha256」 | 现有 `flag_sha256` **无盐**，低熵 flag 可离线爆破 | 方案缺陷：把一个可穷举的格式当安全方案推 |
| （未提）真值物理隔离 | 主仓永远不含答案，真值放私有 vault | 遗漏了结构上更优的选项 |

### 修订后的排序

**P0（决策级，先定这个）**：公开仓已含 291 条真答案，二选一——
- **(a) 重写历史**：`git filter-repo` 移除 `data/ctf_benchmark/*`、生成器内联 flag、writeup 中的答案，强推。
  代价：所有并行会话分支失效、需重新 clone；GitHub 的 fork/缓存可能仍留副本。
- **(b) 正式接受并声明**：在 README 写明「本仓基准集含已结束赛事的公开赛题答案，仅用于自测」。
  代价：观感风险（评委看到交付物里有别家答案）；若赛题被回收复用，风险回升。

判据：**这些答案对应的赛事（羊城杯/西湖论剑/DASCTF/XCTF）是否已结束且不会复用**。
已结束且不复用 → (b) 可接受；否则 (a)。

**P0（结构级）**：真值物理隔离 —— 主仓（public）永久不含答案，真值放**私有 vault**
（独立私有仓或服务器目录，评测时挂载）。这比"把明文改成哈希"彻底：
不是把明文藏起来，而是**让它不在这条分发链上**。

**P1**：生成器源码禁止内联 flag（从事后搬改成事前禁）+ 测试夹具改合成答案（掐断训练污染入口）。

**P1**：若继续用哈希，升级为 **HMAC-SHA256 + 仓库外密钥**（现为无盐 sha256，低熵答案可爆破）。

**P2**：记忆层脱敏 —— 兜底手段。真正的解法是让 agent 看不到明文（工具返回掩码/sha256），
记忆自然干净；脱敏只是防止"已经看到了"的那部分流出去。

## 7. 需要拍板的事（修订后）

1. **公开仓的 291 条真答案怎么办**：(a) 重写历史 / (b) 接受并声明。
   判据是「这些赛题会不会被复用」——这条决定后续所有动作的紧迫度，**必须先定**。
2. **真值是否迁出主仓**（私有 vault + 评测时挂载）：这是唯一能让"明文入库"结构性不可能的做法。
3. **哈希是否升级为 HMAC/加盐**：现有无盐 sha256 对低熵答案可爆破。
4. **测试夹具是否改合成答案**：断言语义不变，但会失去"用真实格式回归"的覆盖。
