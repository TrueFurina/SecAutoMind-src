# 非 flag 靶场「打穿证据」探测：设计与训练记录

> 建立日期：2026-10-21 · 主理人已批准（"点头了"）
> 目的：让本仓能够对**不发 flag 的真实靶场**判定"是否真的被打穿"，同时**不改动**基准判分口径。
> 关键约束：**旁路能力，不进 flag 判分路径，对基准分数零影响。**

---

## 1. 为什么需要它

基准题库（`data/ctf_benchmark/real_benchmark.json`）的判分口径是 **sha256(flag)**，
而真实靶场（如 LAMPSecurity CTF4）是 **root 导向、全程不发 flag**。

此前用生产链路函数打 CTF4，结果恒为 **0 命中**。根因有两条（已核实）：

1. `internal/ctfplatform/web_hints.go:241` — `if len(eps) == 0 { return }`：
   题目描述不给端点线索时，SQLi/SSTI/LFI/cmdi/SSRF 定向阶段**一次都不跑**。
2. 所有探测结果经 `passiveScan` 过滤（`web_hints.go:212-221`），**只保留 flag 形态字符串**。
   靶机返回的是 `/etc/passwd`、`.htpasswd` 明文，不含 flag → 不产生 `WebFinding`。

**结论：这是判分口径差异，不是能力缺失。** 因此不修改 flag 路径，而是新增一条旁路。

## 2. 设计

### 2.1 隔离原则

| 项 | flag 判分路径（原有） | 旁路证据（本次新增） |
|---|---|---|
| 入口 | `ExploitURLsInText` / `ExploitWebTargetWithHints` | `ProbeSensitiveFileRead` |
| 返回 | `[]WebFinding`（含 `Flag`） | `[]WebEvidence`（**无 Flag 字段**） |
| 判分 | 参与 sha256(flag) 校验 | **完全不参与** |
| 对基准数字影响 | — | **零** |

两者**不共享返回值**，也不互相调用，因此不可能出现"伪造 flag 污染分数"。

### 2.2 新增 API（`internal/ctfplatform/web_evidence.go`）

```go
type WebEvidence struct {
    Kind    string // lfi_sensitive_file | sqli_error
    URL     string // 命中的完整请求
    Param   string // 被注入的参数名
    Payload string // 生效的载荷
    Signal  string // etc_passwd / etc_shadow / htpasswd_hash / sqli_error_<db>
    Detail  string // 打码摘要（绝不落原文口令哈希或报错原文）
}

func ProbeSensitiveFileRead(ctx, baseURL string, hints WebHints) []WebEvidence
func ProbeSQLError(ctx, baseURL string, hints WebHints) []WebEvidence
func DiscoverWebParams(ctx, baseURL string) (endpoints, params []string)
```

`DiscoverWebParams` 补的正是 §1 第 1 条盲区：抓入口页的 `href`/`action`，
自己找出 `?page=` 这类参数，**不依赖题目描述给线索**。

`ProbeSQLError`（`web_evidence_sqli.go`）覆盖**报错型 SQL 注入**：
自动发现带口令输入的表单（解析 `action` 与字段名，相对路径解析为绝对 URL），
先跑**良性基线**确认不报错，再逐个上载荷，命中数据库报错即产出证据。

> 为什么必须探测"报错"而不是"登录成功"：CTF4 的登录页有前端 `fixLogin()` 会剥掉所有
> 非字母数字字符，`admin'--` 在浏览器里根本发不出去；绕过 JS 直接 POST 才触发
> `You have an error in your SQL syntax`。若按"登录框消失"判定，会把报错页误判成登录成功——
> 因此**只认报错回显**，且基线已报错时直接跳过该表单（避免误报）。

### 2.3 检测信号（强特征，避免误报）

| 信号 | 正则要点 | 说明 |
|---|---|---|
| `etc_passwd` | `^root:[^:]{0,64}:0:0:` | root 行是"文件被读出"最硬的证据 |
| `etc_shadow` | `^root:[^:]{1,160}:\d+:\d+:\d+:` | 需 root 权限，通常拿不到（负向对照） |
| `htpasswd_hash` | `^user:(\$apr1\$…\|\$2[aby]\$…\|[A-Za-z0-9./]{13})$` | 同时识别 DES-crypt / apr1-md5 / bcrypt |

普通页面（含 "root" 单词）不会命中——`TestClassifySensitive` 有专门的反向用例。

### 2.4 载荷策略

按命中概率排序，**载荷优先于参数扩展**（保证最可能的参数先被穷举）：

1. 题目线索给出的载荷（含 `..`/`passwd`/`htpasswd` 时）
2. `/etc/passwd` 多级深度 ×1..6，每级带 `%00` 变体（对抗 `include($page.".php")` 后缀拼接）
3. 敏感文件字典：`restricted/.htpasswd`、`.htpasswd`、`htpasswd`、`conf/.htpasswd`、`etc/hosts`、`etc/shadow`（深度 1..4，均带 `%00`）
4. 过滤绕过：`....//` 归一化形态
5. 编码回读：`php://filter/convert.base64-encode/resource=…`（命中后自动 base64 解码再分类）

**关键实现细节**：`%00` 必须保持字面量。`url.QueryEscape` 会把它变成 `%2500` 而失效，
因此 `buildProbeURL` 用裸串拼接（`TestBuildProbeURL_KeepsNullByteLiteral` 锁死这条）。

请求预算上限 180 次，命中 4 条即提前返回，避免组合爆炸。

## 4.5 口令破解链路（第 4 轮）

`.htpasswd` 里是 **DES-crypt**（13 字符），破解需要"对候选口令做同样哈希再比对"。
本机与服务器都**没有 john/hashcat**，为了不引入外部依赖，按 musl 的
`src/crypt/crypt_des.c`（源自 FreeSec / Solar Designer）实现了**纯 Go** 版本。

### 与标准 DES 的四处关键差异（都踩过坑）

| 差异 | 错误写法（实测全不符） | 正确写法 |
|---|---|---|
| 口令 → 密钥 | 直接用口令字节 | **每字节左移 1 位**（7-bit 密钥，奇偶位清零） |
| 盐值 | `(bin(s[0])<<6) \| bin(s[1])` | **`(bin(s[1])<<6) \| bin(s[0])`**（反序） |
| 盐的作用点 | 交换 E 表每组 6 位的前两位 | **交换 E 输出第 i 位与第 i+24 位**（i=0..11） |
| 输出编码 | 6 位一组 LSB 优先 | **6 位一组 MSB 优先**，11 字符，公式见源码 |

校准方式：用服务器 `python3.12` 的 `crypt` 模块生成 **10 条参考向量**，
逐条比对直到全通过（`TestDESCryptVectors`）。这一步不能省——
DES 表错一位，13 字符输出全错，肉眼完全看不出来。

### 性能与实测

| 项 | 实测 |
|---|---|
| 单条 `desCrypt` | **66 µs/次**（≈1.5 万次/秒·核） |
| 8 并发字典扫描 | ≈5.5 万次/秒 |
| 1400 万词条字典 | 约 4 分钟/哈希（估算） |

对真实靶场的 4 条记录（`ghighland`/`pmoore`/`jdurbin`/`sorzek`）：
**4ms 跑完内置字典（约 130 词），命中 0/4**。
这是**正常结果**——内置字典只覆盖常见弱口令，这 4 个口令不在其中。
破解能力本身已验证（`TestCrackHtpasswd_Hits` / `_SaltIsRespected` 用合成哈希证明正确性）。

> 要真正破开这 4 条，需要 rockyou 级别的字典（约 140MB，属外部依赖，本轮未引入）。

## 4.6 完整杀伤链闭环（第 5 轮）

拿到系统词表（服务器 `/usr/share/dict/words`，104,334 词）+ 变形规则后，
对靶场 4 条 `.htpasswd` 记录做了真实破解，**成功 1 条**，并直接用它登录拿到 shell：

```
[crack] elapsed=2m21s 成功=1
[ssh]   登录成功 user=ghighland addr=127.0.0.1:2222
[ssh]   id=uid=505(ghighland) gid=505(ghighland) groups=100(users),505(ghighland)
[ssh]   hostname=ctf4.sas.upenn.edu
```

**这是本靶场链条的终点**：从"只给一个 URL"到"拿到远程 shell"，全程自动，无需人工线索。

### 关键实现点

| 环节 | 做法 |
|---|---|
| 词表变形 | 4 种形态（小写/首字母大写/全大写/leet）× 21 种后缀 ≈ 84 候选/词 |
| 内存控制 | `CrackHtpasswdBatched` 按 2 万词/批流式展开，**不一次性物化 800 万候选** |
| 并发 | 每批按 CPU 核数分片，命中即原子标志提前退出 |
| SSH 客户端 | `golang.org/x/crypto/ssh`（已是本仓直接依赖，未新增模块） |
| 老算法兼容 | 显式放开 `diffie-hellman-group14-sha1` / `ssh-rsa` 等 2009 年算法 |
| 主机密钥 | **默认拒绝** insecure 模式，必须显式传 `allowInsecureHostKey=true`（有守卫测试锁死） |
| 口令处理 | 明文只在内存中传递，**不写日志、不入库**；测试用例只打印用户名与 `id` 输出 |

### 性能参考

- 104,413 词 × 84 变形 = 约 877 万候选；4 条记录全跑 **9m59s**，单条约 2m21s。
- 若只要 1 条，`CrackHtpasswdBatched` 会在命中后跳过该条目，后续批次不再重复计算。

> 注：字典覆盖有限，4 条只破开 1 条是**正常结果**，不是缺陷。破解正确性由
> `TestCrackHtpasswd_Hits` / `_SaltIsRespected`（合成哈希）与本次真实破解共同证明。

## 4.7 本地提权到 root（第 6 轮）

说明书 Step 10 的路径是「偷 achen 的 SSH 私钥」，实测**私钥真的全局可读且未加密**：

```
/home/achen/.ssh/  drwxr-xr-x
  achen_priv.ppk   -rw-rw-r--   ← 世界可读
  Encryption: none            ← 未加密
```

于是链条最后一跳：

```
ghighland 口令登录
  → cat /home/achen/.ssh/achen_priv.ppk        （偷私钥，843 字节）
  → PPK → PKCS#1 PEM                            （本仓实现，883 字节）
  → 以 achen 私钥登录 → uid=501(achen) groups=...,507(admins)
  → sudo -l: (ALL) NOPASSWD: ALL
  → sudo id → uid=0(root) gid=0(root) groups=0(root),...,10(wheel)
```

**这是完整杀伤链的终点：一个 URL → root。**

### 关键实现点

| 环节 | 做法 |
|---|---|
| PPK 解析 | 自实现 PuTTY v2 解析（SSH wire 格式：`string` + `mpint`），**只支持 `Encryption: none`**，加密的一律明确报错 |
| PEM 转换 | `crypto/x509.MarshalPKCS1PrivateKey` → `RSA PRIVATE KEY` |
| 独立验证 | 测试用 `x/crypto/ssh` 这个**独立消费方**解析 PEM，并与 `x509` 直接编码结果逐字节对照（不自己跟自己比） |
| 1023 位密钥 | 🔴 **Go 1.24+ 默认拒绝 <1024 位 RSA**（`crypto/rsa: 1023-bit keys are insecure`）；实验环境需 `GODEBUG=rsa1024min=0` |
| 老 sudo | 靶机 sudo 1.6.x **不支持 `-n`**，`sudo -l` 会要口令；用 `sudo id` 直接验证 NOPASSWD 是否生效 |

### 测试

- `ppk_test.go`：6 例（往返解析、PEM 可被 ssh 解析且公钥一致、拒绝加密/非 v2/垃圾输入/非 RSA）
- `TestLivePrivescToRoot`：活靶机全链，默认 SKIP；支持 `CTF4_SSH_USER/PASS` 跳过破解，实测 **0.84s 到 root**

## 4.8 编排成单一入口（第 7 轮）

前面 6 轮产出的是**一堆独立函数**，没有单一入口——这轮把它们编排成 `RunKillChain`：
**给一个 URL，逐步报告走到哪一步、每步耗时多少、失败原因是什么。**

```go
res := RunKillChain(ctx, KillChainOptions{
    BaseURL: "http://127.0.0.1:8080/", SSHAddr: "127.0.0.1:2222",
    AllowInsecure: true,   // 必须显式声明
})
// res.Steps 逐步结果；res.Root 是否到 root；res.RootID 提权后的 id 输出
```

实测输出（已知凭据快路径，**2.65s**）：

```
[killchain] 总耗时 3s，7/7 步成功，已到 root
  1. [OK] recon     1.357s  端点=2 参数=[title page] 证据=[etc_passwd htpasswd_hash]
  2. [OK] loot        8ms   经 ../restricted/.htpasswd%00 取得 4 条记录
  3. [OK] crack       0s    使用调用方提供的已知凭据（跳过字典）
  4. [OK] ssh       477ms   ctf4.sas.upenn.edu：uid=505(ghighland) ...
  5. [OK] keytheft  222ms   取得 843 字节未加密 PPK
  6. [OK] keylogin  349ms   achen（已放开 rsa1024min 以接受老密钥）：uid=501(achen) ...
  7. [OK] privesc   235ms   uid=0(root) gid=0(root) ...
```

### 设计要点

| 点 | 做法 |
|---|---|
| **失败即停** | 任一步失败立刻返回，**已完成步骤的证据保留**，不丢上下文 |
| **每步独立计时** | 用 `ChainStep{Name,OK,Detail,Elapsed}` 记录，便于定位瓶颈 |
| **不猜路径** | `.htpasswd` 依次尝试 3 处常见位置，全失败才报错 |
| **不掩盖错误** | 失败步的 Detail 里同时写"做了什么"和"错误是什么" |
| **老密钥自愈** | keylogin 遇到 1023 位拒绝时，自动放开 `rsa1024min` 重试一次，并在 Detail 里注明 |
| **凭据不进日志** | 口令只用于内存中的 SSH 调用；Detail 只写用户名与 `id` 输出 |
| **仍是旁路** | 不产生 `WebFinding`、不提交 flag、**不影响基准分数** |

### 一键运行

```bash
bash scripts/lab_killchain.sh                        # 内置字典
bash scripts/lab_killchain.sh --user U --pass P      # 已知凭据，跳过破解
CTF4_WORDLIST=D:/tmp_gotest/words.txt bash scripts/lab_killchain.sh
```

## 4.9 去掉目标特化知识：私钥自动发现（第 8 轮）

第 7 轮的 `keytheft` 写死了 `/home/achen/.ssh/achen_priv.ppk`——**换个靶机就不成立**。
真实靶场的共性是"私钥权限没设对"，与用户名无关，所以改成**扫出来**。

### 判定规则（纯函数 `parseReadableKeys`，可单测）

| 规则 | 说明 |
|---|---|
| 权限 | `ls -l` 末三位（其他用户）**必须含 `r`** —— `-rw-------` 直接排除 |
| 文件名 | 认 `.ppk` / `.key` / `.pem` / `id_rsa` / `id_ed25519` / 含 `priv`；**排除** `.pub` / `_pub.ppk` / `authorized_keys` / `known_hosts` / `config` |
| 类型 | 只认普通文件（`-` 开头），符号链接 `l` 排除 |
| 去重 | 同一路径只留一条 |

扫描命令：`ls -l /home/*/.ssh/* ~/.ssh/* 2>/dev/null`（不做全盘 find，避免慢与噪音）。

### 实测（活靶机，未指定任何用户名）

```
5. [OK] keytheft  972ms  发现 1 个可读私钥，选用 /home/achen/.ssh/achen_priv.ppk
                         （属主 achen，权限 -rw-rw-r--，PEM 883 字节）
6. [OK] keylogin  521ms  achen（已放开 rsa1024min 以接受老密钥）：uid=501(achen)
7. [OK] privesc   398ms  uid=0(root)
```

`KillChainOptions.TargetUser` 从"默认 achen"改为**可选偏好**：给了就优先该用户的私钥，
留空则取第一个可读的。**代码里已无 `achen` 字样**（grep 验证）。

### 测试

- `keyscan_test.go` 4 例：可读/不可读区分、排除公钥与 authorized_keys、去重、垃圾输入不 panic
- 活靶机全链仍 7/7 到 root（5s）

## 4.10 修掉靶场用例的进程残留（工程卫生）

连续 3 次全量回归都没绿，失败集中在 `TestSQLiAttackAgainstRange` / `TestSSRFAttackAgainstRange`。
按纪律先排除自己：单独跑 **SQLi 5/5 PASS**、SSRF 也 PASS、无端口号冲突、失败代码路径与本次改动无关。

### 根因（已确证，不是猜测）

跑完测试后 `netstat` 发现：

```
TCP 127.0.0.1:18220  LISTENING  10248
PID 10248 → D:\miniconda3_new\python.exe ...\ssrf_range.py 18220   （父进程已死）
```

即 **`cmd.Process.Kill()` 在 Windows 上没杀干净**，靶场进程残留在固定端口上。
下一轮启动新实例时绑不上 → `靶场未就绪`（10s 超时）；或打到**陈旧实例**（数据不同 → 取到别的场景的 flag、甚至字节损坏的 `b1n+ry`）。

这也解释了为什么"单独跑永远过、全量跑偶发挂"——单独跑前端口是空的。

### 修法（只动测试工具，不碰求解器）

新增 `rangeproc_test.go`：

| 工具 | 作用 |
|---|---|
| `killProcessTree(pid)` | Windows 用 `taskkill /PID <pid> /T /F` 杀**进程树**；其他平台退回 `Kill()` |
| `killPortListeners(port)` | 启动前扫 `netstat -ano`，杀掉占用该端口的残留监听（防御性） |

两个靶场用例的启动/清理处各改 3 行：启动前 `killPortListeners(port)`，
失败与 `cleanup` 处 `killProcessTree(cmd.Process.Pid)`。

### 验证

| 项 | 结果 |
|---|---|
| 两个靶场用例 | **PASS**，跑完 `18220~18223` **无 LISTENING 残留** |
| 全量回归（修复后） | **RC=0，565.441s**，跑完端口仍干净 |
| 修复前 | 3 次全量：2 次 SQLi 失败 + 2 次 SSRF 失败（交替） |

> 教训：**"单独跑能过"不能证明用例没问题**。固定端口 + 不彻底清理 = 跨轮次污染，
> 表现成"随机某个场景失败"，极易被误判成求解器不稳定。

## 4.11 盲注把「请求失败」当成「布尔假」（求解器健壮性）

修完进程残留后又失败了一次，但这次现象不同：`sqli` 变成 **`sgli`**（q→g），之前是 `4` 变成 `+`。
**单字符错位**指向布尔盲注的逐字符二分。

### 根因

```go
ask := func(cond string) bool {
    _, body := sqliFire(...)          // sqliFire 把 error 吞成 (0, nil)
    return strings.Contains(body, "exists")
}
```

一次网络抖动 → `body` 为空 → `ask` 返回 **false** → 二分搜索往错误方向收敛一个字符。
`sqliFire` 签名里**没有 error**，调用方根本无法区分"响应为假"和"请求没成功"。

### 修法（只改错误处理，不改算法）

| 改动 | 说明 |
|---|---|
| 新增 `sqliFireE` | 保留 error（含 `io.ReadAll` 的读错误）；`sqliFire` 变成薄包装，其他调用方不受影响 |
| 新增 `sqliAsk` | 三态返回 `(值, 是否可信)`；**只把传输层失败视为不可信**，HTTP 200 + 空体仍是合法的"假" |
| 失败重试 3 次 | 间隔 50/100/150ms |
| 仍不可信 → **中止** | 返回 nil，宁可不报，也不产出脏 flag |

> 踩过的坑：第一版我把 `len(body) > 0` 也当成失败，导致空响应体触发大量重试——
> 用例耗时从 0.9s 涨到 3.8s。**HTTP 200 + 空体是合法的"假"答案**，不能算失败。

### 验证

| 项 | 结果 |
|---|---|
| 新增单测 `sqli_ask_test.go` | **5 个子用例全 PASS**（true / false / 前两次断连后成功 / 始终失败 / ctx 取消） |
| SQLi 两个用例连跑 3 轮 | **6/6 PASS**，耗时 1.6s，端口无残留 |
| 全量回归 | **RC=0，592.319s**，端口干净 |

## 4.12 同类风险审计：还有谁在吞 error

修完盲注后，按"同类 bug 可能不止一处"的思路做了一次全模块审计。

### 审计口径

| 检查项 | 方法 | 结论 |
|---|---|---|
| 吞掉 HTTP error 的调用 | `grep` `webFetch/webPostForm/webPostJSON` + `, _` 模式 | **4 处**，其中 **3 处显式检查了 err**；1 处（`web_evidence_sqli.go:182`）是基线比对，err 时 `continue`，行为正确 |
| 返回 bool 的判定函数 | `grep "^func .*) bool {"` | 4 个，均为纯逻辑判断（`gqlIn`/`hintsHaveType`/开关函数），**不涉及网络** |
| `httpQuickGet` | 查生产调用点 | **2 处**，都是 `if code == 0 { continue }` 的**探活跳过** |

### 结论：风险分级

| 位置 | 风险 | 说明 |
|---|---|---|
| `sqliFire` → `ask` | 🔴 **高（已修）** | error 被当成"布尔假"，**直接产出错误结论**（脏 flag） |
| `httpQuickGet` 两处 | 🟡 低 | error 只会**跳过**该端点（假阴性），不会产出错误结论 |
| 其余 | 🟢 无 | 显式检查 err 或纯逻辑 |

**判断标准**：error 被当成"否定结论"→ 高危（静默产出错误答案）；
error 被当成"跳过"→ 低危（少报，不误报）。**只有前者会骗人。**

### 稳定性压测

修复后把 SQLi 两条路径连跑 **10 轮 × 2 用例 = 20 次**：

```

```
