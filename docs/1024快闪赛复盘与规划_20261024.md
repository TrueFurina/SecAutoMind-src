## 三、经验教训（按危害排序）

### L1 · 多会话并行 = 引擎互踩（本次最大事故源）
- **现象**：多个并行会话各自启动 ctf-agent，新实例启动时执行 `cleanup_orphan_containers()`，**误杀前一个实例的 solver 容器** → 连环互踩、同一题反复从头解。
- **根因**：引擎缺少"单一写者"所有权约定；启动清理逻辑对"别人的在跑容器"无区分。
- **处置**：收敛为唯一实例（本会话持有）。
- **纪律（后续比赛必守）**：**一场比赛只允许一个会话拥有引擎**；任何人要启动引擎，先 `Get-CimInstance Win32_Process` 查已有 `*ctf-agent*` 进程，有则接管不新起。

### L2 · stdout/stderr 分流导致"假卡死"误判
- **现象**：`final_entry.py` 状态行走 stdout（"已解/开始"），INFO 日志走 stderr（Sandbox started / Solver started / Retrying）。只看 stdout 2 分钟无新行就误判"卡死"，实际 stderr 持续活动（API 重试中）。
- **纪律**：判断引擎健康必须同时看 **stderr 时间戳 + 进程 CPU/内存 + Docker 容器**，任一活跃即非卡死；杀进程前先看 stderr 尾部 5 行。

### L3 · 误删在跑 solver 的容器
- **现象**：调控中 `docker rm -f` 删掉 4 个 ctf-sandbox 容器，事后发现它们是正在攻"第 1024 行"的 solver 环境（该题恰好当时已解出，未造成实际损失）。
- **纪律**：删容器前必须确认归属（容器名/创建时间/对应 solver）；宁可让引擎自己 `cleanup_orphan_containers`，不手动批量 rm。

### L4 · 止损参数的价值
- `--per-task-timeout 900`（单题 15 分钟硬超时）保证 Pwn 等难题不无限啃；`_FAILED_GIVE_UP=3`（连续失败 3 次本场放弃）防单题吃整场。这两条是引擎默认的自保机制，赛时不要覆盖。

### L5 · 平台侧核验
- 平台描述"19 题 1024 分"是两赛道合计；**Agent 赛道实际 9 题**（stage 列表为准）。判断"做完了没"以 `competitions/{id}` 的 entry（solve_count / score / rank）与 stage challenges 列表为准，不轻信宣传文案。
- urllib 直连平台不稳（404/超时），引擎用 httpx 同款路径才通；外部探测要复用引擎的 CTF2Client。

### L6 · 已验证的正向事实（照做）
- 4 模型并发（gpt-5.1 / claude-sonnet-5 / glm-5.3 / deepseek-v4-pro）对异构题目效果好。
- 调试阶段（赛前）解题 = 比赛正式开始前的分数积累，价值巨大，务必利用。
- `--max-concurrent 4` 匹配平台 stage `max_targets=4`，容器题串行由引擎自行控制。

**结果**：`scripts/exploit_ycb12067.py` 在自建靶场上读出**我们自己埋的 flag**，判分器判 **SOLVED**。


**闭环含义**：这是羊城杯基准里**第一道被证实的可评测题**——
`kind=arena`、`truth=self-planted`、判据是「输出里出现我们埋的 flag 明文」。
真值不依赖原赛 flag、不依赖已关闭的平台，也不依赖任何 writeup。

**复现命令**（服务器，两条）：
```bash
cd /tmp/arena12067
python3 /tmp/ctf_arena.py --cmd "./ld-linux-x86-64.so.2 --library-path . ./pwn" \
    --cwd /tmp/arena12067 --port 31550 --plant-flag 'DASCTF{x}' --timeout 40 --log /tmp/a.log &

```
⚠️ 必须用题目自带 `ld-linux` + `--library-path .` 锁 libc 2.35——
服务器系统 libc 是 **2.39**，偏移全不同（实测 `write@@` 位置不一样）。

**攻破路径（全部亲测，非照抄 writeup）**：`vuln` 的 `read(0, rbp-0x20, 0x30)` 溢出 0x10 →
跳板 `0x40122b` 做「任意地址写 ≤0x30 字节 + 控制 [rbp]/[rbp+8]」→ 泄漏 `write@GOT` 拿 libc →
BSS 上拼 `open("flag")`+`read`+`write` 的 syscall 链（seccomp 只杀 execve）。

**四个 bug 都是靠证据抓出来的，值得记**：

| # | 症状 | 定位手段 | 真因 |
|---|---|---|---|
| 1 | 第 2 轮 read 段错误 | gdb：`_dl_runtime_resolve_xsavec+19`、`rsp=0x403680`、`SEGV_ACCERR` | 满写 0x30 必然连带覆盖 `read@GOT`；重解析的 xsave 帧 **0x1780 字节**（本机有 avx512f）> 一整页，**抬 rbp 到页尾也装不下** |
| 2 | 第 6 轮 `si_addr=NULL` | strace：`SEGV_MAPERR si_addr=NULL`，且子进程从未 `openat` | 1 操作数 gadget 后我补 `0` 当填充，gadget 一 `ret` 就落到那个 0 上 |
| 3 | 同上 | 内存 dump：`[0x404050]` 变成跳跃器地址 | SKIP 固定吃 2 qword，所以每块必须**正好 3 个链 qword**；块内不足 3 时用 `ret` 补（不是 0） |
| 4 | gdb 复现"看起来"更糟 | 对比真实 socket 跑 | **文件回放时 `read` 会吃满 0x30**，"只发 8 字节"只在 socket 有背压下成立 → 文件回放会写出错误布局，**是假复现** |

**三个关键技巧（比 writeup 更稳）**：
1. **用 8 字节部分读单独打 GOT**：`read` 的上限是 0x30、不是必须读满 → socket 上只发 8 字节即可
   只改 `seccomp_load@GOT`，`read@GOT` 完好，**全程零重解析**（writeup 的"把解析器帧放高地址"
   在 avx512 机器上不可行）。
2. **跳板必须预置**：8 字节那轮不写 `[rbp]/[rbp+8]`，由前一轮先放好。
3. **连续轮 rbp 步长 0x30**：`call read@plt` 把返回地址压到 `rsp-8`，若 rsp 落在本次写缓冲内
   就会被 payload 覆盖（实测第 2 轮崩）；步长 0x30 使 rsp 恰在缓冲区起点，压栈位置在区外，
   代价是块间夹 0x10 跳板槽，用 `pop rdx; pop rbx; ret` 当跳跃器吃掉。

**对基准的意义**：羊城杯 18 道可评测题里，**12067 已从"纸面可自建"变成"实测可判分"**。
其余 8 道 pwn 是多进程服务（broker/listener/nginx+.so），自建成本高得多，暂列 P2。

### 6.17 12080 Jammed 深挖结论：结构已破，密码未得（诚实停手）

**已确定的结构**（PIL 行投影 + 8× 放大逐字复核）：
- 两页各有 24 条记录，格式 `[序号][SEP][5 位流水码][SEP][2 位片段]`，共 11 字符/行；
- **SEP 字形在两页不同**：A 页（`BENCH RECORD A`）打 `/`，B 页（`BENCH RECORD B`）打 `1`
  —— 这是「错字模」的直接证据，也解释了为什么 B 页每行第 0、6 位恒为 `1`；
- A 页序号编码成 **2 个字母**（`xl` `xk` `xh` `hl`…），B 页是 2 位数字（01–24，行序为乱序）；
- 24 个片段已在 8× 下逐一确认（如 `#01=91` `#16=k5` `#13=t3` `#07=ek` `#24=c4`）。

**已试并失败的假设（全部记录，勿重跑）**：
1. 取 B 页 payload 任意连续切片（start 0–7 × width 1–9，共 45 种）→ 密码哈希全不匹配；
2. 按 seq 升序 / 行序 / 行序倒序拼接 → 全不匹配；
3. 大小写、加 `\n`、空格分隔、`/` 分隔、序号前缀 → 全不匹配；
4. 全行拼接（264 字符）、只 5 位流水码（120 字符）、码+片段换序 → 全不匹配。

**结论**：B 页字符**不是**真值（否则「末 2 位按 01–24 拼接」必然命中哈希）。
说明 A、B 两页都用了非标准字模，必须先用**五字符段的重复杂模式**把 A 行与 B 行配对，
再解出 A→真值的字符映射，才能拿到可用的片段。这是一个完整的谜题级工作量，**当前停手**——
理由：我自己解出这题不会提高引擎的解题率，而 §6.16 的测量器才是能持续产出能力数据的设施。
所有中间结论与失败假设已在此记录，接手时可零成本续。

### 6.20 纠正：那个「474 次死循环」是我的布局 bug，不是引擎缺陷（2026-10-25 18:45–19:00）

**怎么发现的**：判分器说 0/1 之后我没有直接写成"引擎不行"，而是去看了 trace

```

{"command": "cd /challenge/workspace && python3 -c \"import os; os.walk('/challenge')…\""}
```

模型不是"笨"，是**看不见工件**——它在 `/challenge` 下反复找，因为我把附件平铺在了题目根目录。

**根因**：引擎约定 `题目目录/distfiles/` 放附件、`题目目录/workspace/` 做工作区，
沙箱把题目目录挂到 `/challenge`（`backend/agents/solver.py:195` 的提示词原文：
「All files are under /challenge/ — distfiles at /challenge/distfiles/, workspace at /challenge/workspace/」）。
我的 `prepare_workdir` 把工件复制到根目录 → `/challenge/distfiles` 是空的 → 死循环。

**修复**（`scripts/ycb2026_run.py`）：
- 工件一律放 `distfiles/`，并建 `workspace/`；
- 准备完**自检**：`distfiles/` 下缺任何登记工件就直接 `SystemExit`——**宁可跑不起来，也不让空目录跑出"能力结论"**；
- `solver_rule_layer.sh` 改为递归遍历（兼容 `distfiles/` 布局），并把 Windows 的 CRLF 转成 LF
  （`set -u\r` 会被 dash 当成 `Illegal option`，实测 rc=2 —— 又一次被 `suspect` 检测抓住）。
