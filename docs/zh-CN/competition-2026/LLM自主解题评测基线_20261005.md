# LLM 自主解题评测基线（2026-10-05）

> 目的：给出**首个真实的自主解题能力数字**。此前的静态真题评测（19/55）测的是
> "题面里有没有 flag"，本评测测的是"**给目标机之后，模型能不能自己打进去**"。
>
> 诚实边界（先说清）：
> 靶机是按真实漏洞形态手写的最小实现，比原题简单（无混淆、无 WAF、无多步组合）。
> 所以本数字是**上界**，不是赛场预期。用途是横向比较与回归追踪，
> **不可对外宣称"能解多少题"**。

## 一、评测设计

- 被测对象：LLM（默认 `deepseek-chat`，走 DeepSeek 官方 API）
- 输入：题面描述 + 平台分配并注入的靶机地址
- 工具：仅 `http_get` / `http_post`（可带 header、body、content-type）
- 终止：模型输出 `{"action":"answer","flag":"..."}`，或用满 8 步
- 判据：平台按 `code=="00000" && data.isCorrect==true` 判分（与真实平台同一判据）
- 题目：13 个真实漏洞靶机（web 类题型 12/12 全覆盖）
- **不给专用探测器** —— 这是与 `TestLiveTargetEndToEnd` 的本质区别

命令：
```bash
LLM_EVAL_LIMIT=3 go test -count=1 -v -run TestLLMAutoSolve ./internal/ctfplatform/   # 子集
go test -count=1 -v -run TestLLMAutoSolve ./internal/ctfplatform/                      # 全量 13 题
```
未配置凭据时 `t.Skip`（CI 常态）。换模型：`LLM_EVAL_BASE_URL` / `LLM_EVAL_API_KEY` / `LLM_EVAL_MODEL`。

## 三、🔴 最重要的发现：模型在盲扫，不读题面

失败题的动作序列（trace）高度一致，8 步全部耗在路径枚举：

```
第1步 GET /          第2步 GET /robots.txt    第3步 GET /flag
第4步 GET /index.php 第5步 GET /admin        第6步 GET /api
第7步 GET /login     第8步 POST /login username=admin&password=admin
```

而题面里明确写着"构造恒真条件绕过 SQL 注入""JWT 签名密钥过弱""未做内网地址限制"。
**模型完全无视题面**，套用固定模板枚举路径，预算耗尽即放弃。

→ 真实短板是**「读题 → 识别攻击向量 → 针对性构造」的行为模式缺失**，
  不是模型智力问题，也不是工具问题（工具已能执行任意 payload）。

## 四、工具缺陷曾污染结论（已修正，但必须留档）

| 轮次 | 观测内容 | 结果 |
|---|---|---|
| 第 1 轮 | `HTTP 状态 + body`（截断 1200） | 4/13（31%） |
| 第 2 轮 | `HTTP 状态 + **响应头** + body`（截断 2000） | **5/13（38%）** |

- 题 2002（Cookie）的 flag **只存在于 `Set-Cookie` 响应头**。
  第 1 轮观测不含响应头 → 该题**在工具层面就不可能解**。
- 🔴 **教训：拿到评测数字先质疑工具，再质疑模型。** 否则会把工具缺陷记成模型短板，
  改进方向跑偏（去换模型，而真正该做的是修工具）。
- 同批加入的还有**失败 trace 输出** —— 没有它就只能得到"未解出"三个字，
  根本无法区分"模型不会"与"题目/工具本身不可能解"。诊断价值高于分数本身。



## 六、🔴🔴 决赛级风险：评测时发现本机已无任何可用 LLM 通道

做第 4 轮（脚手架改进后）复测时，**所有 LLM 通道全部不可用**：

| 通道 | 实测结果 |
|---|---|
| DeepSeek（`api.deepseek.com`） | **HTTP 402 Insufficient Balance**（余额耗尽） |
| DashScope（`qwen-plus`/`qwen-turbo`/`qwen-max`/`deepseek-v3`） | **HTTP 400 Access denied, account is in good standing** |
| SenseNova（`SenseChat-5`） | **HTTP 403 Forbidden** |
| Moonshot（`moonshot-v1-8k`/`-32k`/`kimi-k2-0905-preview`） | **HTTP 404 模型不可用或无权限** |
| 火山方舟 ARK（`doubao-1-5-pro-32k`） | **HTTP 404 模型不可用** |
| OpenAI（`api.openai.com`） | **连接超时（被墙）** |

**后果**：
1. 脚手架改进后的复测**无效** —— 13 题中 8 题在第一步就收到 402，
   该轮的 3/13 **不是能力数字，不能与 5/13 比较**（AGENTS.md 第一条 1.3：环境故障 ≠ 代码缺陷）。
2. **这本身是决赛级风险**：若决赛当天模型通道同样不可用，
   平台侧虽然能拉题、能起靶机、能提交，但**没有模型产出 flag → 整条得分链失能**。
   本项目历史上已因同类问题踩坑（线上曾因 `qwen3-max` 免费额度耗尽导致全通道 403）。

**必须做的两件事（属赛前 P0，不是代码问题）**：
   若赛前一直 401，务必在赛前一周找赛事方确认/申请，而不是当天才发现。
2. 准备**至少一条备用通道**并实测可用（当前所有第三方通道均已实测不可用）。

## 六、脚手架改进与效果（同通道可比）

针对 §三 的"盲扫不读题面"诊断实现了 4 条改进：

| # | 改进 | 实现 |
|---|---|---|
| 1 | 强制先分析攻击向量 | 第 1 步只接受 `{"action":"analyze","vector":"..."}`，直接发请求**被拦截打回** |
| 2 | 步数预算 8 → 15 | `maxSteps` |
| 3 | 连续 404/401 早停换策略 | 连续 2 次即注入"别猜路径了，回攻击向量构造 payload" |
| 4 | 攻击向量方法论对照表 | system prompt 内置 14 类向量的**思路**（不给 payload 字符串） |

### 同通道效果对比（均为 OpenRouter `deepseek/deepseek-chat`）

| | 改进前 | 改进后 |
|---|---|---|
| 自主解题 | 2/13（15%） | **4/13（31%）** |
| 总步数 | 99 | 126 |
| tokens | 116,518 | 178,349 |

→ 改进**确实有效**（同通道同模型，唯一变量是 prompt/步数/早停）。
代价是 token 增 53%（步数 + 更长 prompt），单轮成本约 $0.003。

### 🔴 过程中发现并修掉的两个 prompt 缺陷（比"模型能力"更值得记）

第 1 轮改进后跑全量，**11 道失败题的第 1 步全部选了 `source-leak`** —— 包括 SQL 注入、SSTI、LFI、命令注入题。
这不是模型读不懂题面，是**我的 prompt 有两个具体缺陷**：

1. **对照表首项偏见**：向量表按类型顺序排列，第一项恰好是 `source-leak`，
   叠加 `temperature=0.2` 的贪心解码 → 每道题都选列表第一项。
2. **POST 示例误导内容类型**：示例里 `content_type` 写的是 `application/json`，
   模型就用 JSON 发 SQL 注入，而表单接口读不到该字段 → 请求 401。

修法（均已落地）：
- 把"向量清单"改成**「题面关键词 → vector」映射表**（检索式，而非罗列式），
  显式写"不得凭直觉选列表第一项，SQL 注入题绝不能选 source-leak"；
- POST 示例默认改为 `application/x-www-form-urlencoded`，并单列一行强调；
- 映射表末行才是"无明确关键词 → 先 GET / 观察"（避免过早把模型导向盲扫）。

→ **教训：LLM 行为异常时，先怀疑自己的 prompt 设计，再怀疑模型。**
列表罗列 + 低温度 = 首项锁死；示例即默认 = 误导内容类型。

## 七、🔴 模型通道影响很大（跨通道数字不可比）

| 通道 / 模型 | 题面+工具版本 | 结果 |
|---|---|---|
| DeepSeek 官方 `api.deepseek.com`（实际后端 deepseek-flash） | 旧版（8 步、无方法论） | **5/13（38%）** |
| OpenRouter `deepseek/deepseek-chat` | 旧版（8 步、无方法论） | 2/13（15%） |
| OpenRouter `deepseek/deepseek-chat` | 新版（15 步 + 方法论 + 早停） | **4/13（31%）** |

**跨通道不可比**（同一模型名、不同后端路由，能力差异明显）。但由此得到一条对决赛有用的判断：

> **"我们能解多少题"不仅取决于代码与 prompt，更取决于用哪个模型通道。**
> 同一个项目、同一个评测，DeepSeek 官方 38% vs OpenRouter 路由 15%（旧版 prompt）——
> 差距 2 倍以上。决赛前必须在**官方指定/可用通道**上重测，不能拿别的通道的数字对外承诺。
