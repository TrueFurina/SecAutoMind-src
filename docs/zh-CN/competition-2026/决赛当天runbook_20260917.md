## 0. 赛前一天（T-1）自检

```bash
# ① 环境自检：缺 %AppData% 会让所有 go 命令失效（极易误判成缓存被删）
export APPDATA="$USERPROFILE/AppData/Roaming"
go version && go env GOPATH        # GOPATH 应为 D:\DevCache\gopath

# ② 三道快速演练（各 <1 分钟，任何一个 FAIL 都不许上场）
go test -count=1 -run TestRehearsal ./internal/ctfplatform/          # 整链路演练
python scripts/freeze_gate_test.py                                    # 冻结闸门自检
python scripts/build_championship_evidence.py --check                 # 证据包一致性

# ③ 压力演练 + 并发扫描（摸当天该用的并发档位，约 3 分钟）
REHEARSAL_STRESS=1 REHEARSAL_PROBLEMS=30 REHEARSAL_CONCURRENCY=8 \
REHEARSAL_SOLVE_MS=80 REHEARSAL_LIST_429=3 REHEARSAL_SUBMIT_429=2 \
  go test -count=1 -run TestRehearsalStress ./internal/ctfplatform/
REHEARSAL_SWEEP=1 go test -count=1 -run TestRehearsalConcurrencySweep ./internal/ctfplatform/

# ④ 门禁全绿确认
python scripts/secret_guard.py && python scripts/verify_evidence.py && python scripts/check_material_numbers.py
```

任何一项 FAIL → 当天**不启用对应功能**，降级清单见 §4。

## 1. 开赛启动（按顺序，逐项确认有输出）

```bash
# 平台接入（凭证只走环境变量，不落盘）
export DASCTF_BASE_URL="<官方平台地址>"
export CTF_AGENT_PLATFORM_TOKEN="<官方 Token>"   # 或 DASCTF_TOKEN

# 自动化三开关
export CTF_POLL_ENABLED=true          # 启动轮询器
export CTF_AUTOSOLVE_SUBMIT=true      # 解出即自动提交
export CTF_AUTO_BUILD_ENV=true        # 🔴 需要靶机的题自动「起靶机 → 取地址 → 打靶」
export CTF_POLL_INTERVAL=20           # 拉题间隔秒数（平台限流严则调大）
```

启动后 5 分钟内必须看到的**四个健康信号**：

| # | 信号 | 判据 |
|---|---|---|
| 1 | 拉题成功 | 日志出现"发现新题 N"且 N>0（放题前 N=0 也正常） |
| 2 | 靶机链通 | 需要靶机的题日志出现"靶机已启动"+"靶机地址 http://…" |
| 3 | 提交链通 | 至少一题 `Accepted`（赛题描述含明文 flag 的题应秒中） |
| 4 | 无异常刷屏 | 没有 `连续 429`/`WAF 冷却` 的持续告警 |

## 2. 赛中观察（每 15 分钟扫一遍）

| 指标 | 健康值 | 异常处置 |
|---|---|---|
| 新题处理数 | 持续增长 | 停滞 → 看 §3 排障 |
| Accepted 数 | 持续增长 | 不动 → 检查提交判据/Token 是否过期 |
| 拉题请求 | 每次 ≤2 次 HTTP（含重试） | 暴涨 → 平台在限流，调大 `CTF_POLL_INTERVAL` |
| 连续 429 计数 | 0~1 | ≥3 → **自动进入 30/60/120/300s 阶梯**，属正常保护，不要手动重试 |
| WAF 冷却 | 无 | 出现 → 自动冷却 300s，期间**禁止手动打平台** |
| 靶机实例 | 每题起 1 次 | 反复起 → 检查 build-env 返回码（见 §3） |

## 3. 故障处置（按症状对号入座）

### 3.1 需要靶机的题全 MISS、日志无"靶机已启动"
- 检查 `CTF_AUTO_BUILD_ENV` 是否真的设为 `true`；
- 看日志里"起靶机失败"的具体错误：`HTTP 4xx` → Token/参数问题；`平台返回错误: code=…` → 按平台提示处理。

### 3.2 "靶机已启动"但"靶机地址为空 / 取靶机地址失败"
- 官方把地址放在 `challenge_detail.endpoints[].exposeIps[0]`；若平台把该题放在"无需靶机"分支，
  手动从浏览器确认靶机地址后，**人工在界面解题**（不要现场改代码）。

### 3.3 拉题一直 429
- 自动阶梯会拉长等待；若 10 分钟未恢复：调大 `CTF_POLL_INTERVAL`（如 60s）重启进程。
- **重启是安全的**：题目 ID 去重在内层，但重启后会重新处理已提交题 → 提交判分由平台兜底
  （错误答案不计次），可接受；重启前先记下当前 Accepted 数。

### 3.4 某题反复提交不中
- 每题约 50 次机会，**别手动刷**。日志里看 `ExtraCandidates`，把候选 flag 人工到平台网页提交一次确认。

### 3.5 进程崩溃 / 卡死
- 直接重启（见 3.3）；现场**禁止**改代码——确属代码致命缺陷需要热修，
  走逃生阀：`export FREEZE_OVERRIDE_ACK=1 && python scripts/freeze_gate.py --freeze-override "<≥20 字理由>"`。

## 4. 降级清单（某功能不可用时的最小可用姿态）

| 不可用 | 降级动作 |
|---|---|
| 自动提交（Token 过期） | `CTF_AUTOSOLVE_SUBMIT=false` 重启，日志里抄 flag 人工提交 |
| 起靶机链 | `CTF_AUTO_BUILD_ENV=false` 重启；需要靶机的题人工网页操作 |
| 平台持续限流 | `CTF_POLL_INTERVAL=60` + 降低并发（见 §5） |
| 整个轮询器 | 单题模式：界面人工 + 用日志里的 presolve 候选 |

---

## 5. 并发档位怎么定

- 默认 `MaxConcurrency=2` 偏保守。演练台实测（本地仿真，无真实限流）：并发 8 可到 ~7.9x 加速、无失败。
- **真实平台的限流强度未知**，故建议：开赛先用 **4**；观察 30 分钟无 429 且拉题正常 → 提到 8；
  出现连续 429 → 回落到 2。改并发 = 改环境变量重启进程（安全，见 3.3）。

```bash
REHEARSAL_SWEEP=1 go test -count=1 -run TestRehearsalConcurrencySweep ./internal/ctfplatform/
```
