## 三、五个结构性根因（按代价排序）

### 根因 1 · 代理指标替代目标（代价 ≈2 小时）

门禁、安装包、附件归档都有"做完了"的信号；解题没有，只有"还没解出来"。
于是时间稳定地流向前者。这在本项目已经**第二次**发生（上午复盘已写过"目标漂移"），
说明它不是偶发失误，而是**默认行为**——只要赛时还允许碰工程，它就一定会发生。

**结构性修法**：不是"提醒自己别做"，而是**赛前把这些事全部做完并冻结**，
赛时物理上不打开这些目录。

### 根因 2 · 验证错了对象（代价 = 25 次提交 + 半小时）

12082 我把六段答案做到了字节级核对：`e-cdn81` 的 `1` 是 0x31 不是字母 `l`、
base32 解码恰好 24 字节、文档读者逐个比对 prompt 判断越权。
**验证得越扎实，越不愿意怀疑内容**——于是 25 次全押在"第 4 问取值错了"上，
而唯一从没变过的变量是**提交格式**（README 写 `flag{...}`，平台只认裸内容）。

更讽刺的是：正确值 `20260915T1031` 在我第 3 次尝试里就出现过了，
它失败了（因为带壳），我就把它划掉了。

**结构性修法**：第一次提交失败后，**先做通道对照实验**（已知正确串 × 裸/带壳 × 字段名），
再动内容。判据一句话：**N 次全败且某一维从未改变，那一维就是 bug。**

### 根因 3 · 没有"可解性"筛选，只有"难度"筛选（代价 ≈1 小时）

12080 Jammed 是最典型的：花掉最多时间做 863 次哈希比对、8 方向键盘错位、336 种配对，
但**根本没有可靠的读取手段**——打字机字体里 `1` 和 `l` 完全同形，OCR 无法消歧。
等于在错误的输入上做了正确的搜索。

判据应该是：**先问"我怎么知道这次猜对了"，再设计搜索。** 没有 oracle 的搜索不是实验，是掷骰子。

### 根因 4 · 协作没有单一事实源（代价 = 重复推导 + 14 分钟信息延迟）

同一题至少三条线在跑：

- 13:10 我开始独立分析 12082
- 13:20 我推出六段答案（Q4 错）
- **13:36 另一会话已产出正确 flag（Q4 = `20260915T1031`）**
- 13:50 我才从用户那里知道"提交要裸内容"

也就是说：**正确答案在我手里迟到了 14 分钟，而格式信息迟到了 30 分钟。**
现场有 5 份 board/handoff、多个按题分目录，但没有一份**实时的"已得/已试"台账**。

**结构性修法**：一份作战板，所有会话读写同一份，每题固定四列：
`状态 / 已得结论 / 已试且排除 / 当前阻塞`。任何人拿到结论 1 分钟内落板。

### 根因 5 · 选型验证滞后到赛中（代价 = 前半程 0 flag）

自研 presolve 对"单层编码"可靠（base64/hex 秒出），对"多步推理 + 外部工具链"基本无能；
开源 ctf-agent 在调试赛 4/4 全解。这个对比是**比赛进行中**才被验证的。
选型本该赛前用同一批题做 A/B，而不是拿正赛当试验场。

## 五、可执行的改动（不是决心，是清单）

### 赛前 T-30 分钟（必须全部打勾）

1. **通道三连测**：拿上一场任意一题的已知正确串，分别以「裸 / `flag{}` / `DASCTF{}`」提交，
   把返回码记在纸上。**这是唯一能防住本次最大失误的动作。**
2. **工具链盘点**：PIL / cryptography / 7z / z3 / angr / pwntools，缺的提前装到服务器。
3. **靶机 API 跑通一次**：`CreateInstance → GetAccess → DestroyInstance`，确认端点格式。
4. **建唯一作战板**：题号 / 状态 / 已得 / 已试排除 / 阻塞。

### 赛中（四条硬规则）

5. **只做三件事：读题、解题、提交。** 工程类目录（scripts/、installer/、docs/ 的维护）一律不打开。
6. **选题按「分值 × 可解性」**，静态优先；靶机题先探活（`serviceStatus`）。
7. **单题 20 分钟硬停**，到点写"我卡在哪、缺什么"，换题。
8. **提交失败 5 次 → 强制停手做通道对照**，禁止继续枚举内容。

### 赛后（30 分钟内）

9. 只写「已得结论 + 已试排除」，不写长篇；writeup 放第二天。

## 七、一句话结论

**不是解不出来，是把一半时间花在了不产生分的事情上，并且在唯一能拿分的那道题上验证错了对象。**

- 时间：2 小时给工程、2 小时给解题 → 应改为 0 小时给工程、4 小时给解题。
- 验证：25 次验证内容、0 次验证通道 → 应改为 1 次验证通道、再验证内容。
- 协作：3 条线重复推导同一题 → 应改为 1 份台账、3 条线并行不同题。

这三条都不需要更强的模型、更多的工具、更深的技巧——只需要**换掉默认行为**。

### 新增教训 6 · 事后合理化会覆盖实证（代价：一份错的 writeup + 一条错的"正确值"流传）

writeup 用「npx -y 惰性安装、配置写入 ≠ 安装完成」的严谨推理，得出与平台接受值**相反**的结论。
推理越漂亮，越容易盖过「平台明明接受了另一个值」这个事实。
**判据：flag 类题目的真值只有平台接受记录（isCorrect/eventId）；事后分析再合理也只能是"解释"，
不能是"改判"。** 写 writeup 时若分析与接受记录冲突，先怀疑分析。

### 新增教训 7 · 试了所有带壳变体，唯独没试「不带壳」

13:42 的取证会话其实已怀疑过包装问题（原话：「或确认平台是否要求 DASCTF{} 包装」），
也试过 `DASCTF{}` 包装——但 15 次变体里**没有一次是完全裸提交**。
帮凶：12063 的 flag 本体就以 `DASCTF{` 开头（提交串天然带花括号且被接受），
让「flag 带花括号」看起来天经地义。
**判据：一旦怀疑格式维度，就穷举格式维度本身（裸 / 带壳 / 字段名），而不是继续在内容维度上穷举。**
