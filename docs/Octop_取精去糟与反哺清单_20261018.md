## 1. 一句话结论

**取它的"外壳工程约定"，弃它的"消费级产品形态"，反哺它的"安全规则内容与 Windows 盲区"。**

Octop 是通用个人助手，我们是安全/CTF 垂直平台。重合层只有 Agent 运行时外壳；它的差异化功能（远程桌面、IM 桥、专家市场、主动推送）对我们是负资产——决赛评审看的是解题能力与证据链，不是助手像不像人。

## 3. 糟粕：明确不学的五条

### 3.1 向导口令文件永久保留（不学）

`password_file.py` 的 `boot_self_heal` 注释写明：*"The file is intentionally kept forever as a permanent record and is never deleted, even after setup completes."* `CHANGELOG.md` 里也有一条修复：*"取消首次引导时删除 octop-login.txt 引导密码文件的逻辑，避免引导密码意外丢失"*。

这是**明文凭据长期驻留磁盘**。他们的动机可以理解（忘记密码兜底），但代价是任何能读该文件的人永久持有首启口令。

我们的做法是 `SetupComplete` 校验通过后 `os.Remove`（`internal/handler/auth.go:402`），更正确，**保持不动**。他们值得学的一点只有：把文件**绝对路径写进日志**（`wizard password generated; file=...`）——我们用 `windowsgui` 构建时 stdout 不可见，这一点确实不如它。

### 3.2 配置分两处（不学）

`~/.octop/config.json` 只有 1,144 字节（bind_host/port/plugins/database），真正的业务状态在 `octop.db`（425,984 字节 + 119,512 字节 WAL）。配置不可 diff、不可 code review、备份粒度粗。

我们 `config.yaml` 单一真值源 + `scripts/count_stats.py` 口径门禁，比它干净。**不要为了"像它"而把配置迁进数据库。**

### 3.3 口令文件落在数据根之外（不学，且我们自己有同源病）

它的数据根是 `~/.octop`，口令却在 `~/octop-login.txt`（`Path.home()` 硬编码，`setup.py` 与 `password_file.py` 三处都用 `Path.home()`）。后果：备份/迁移数据根时会漏掉凭据文件。

**我们这边是同一个病的镜像**：

- 7 处硬编码 `"data/..."`：`internal/app/app.go:89`、`internal/config/config.go:1996-1997`、`internal/handler/auth.go:329`、`internal/handler/chat_uploads.go:31`、`internal/workflow/engine.go:30`、`cmd/server/main.go:170`。
- `installer/SecAutoMind-Setup.nsi:25` → `InstallDir "$PROGRAMFILES64\SecAutoMind"`，`:27` 要求 admin。
- `install-shortcut.ps1` → 快捷方式工作目录 = `$PSScriptRoot`（安装目录）。

于是"装到 Program Files + 普通用户双击"= 往 Program Files 写 `data/`。**未实测**，但 64 位程序无 UAC 虚拟化重定向，机制上会被拒。这必须修，且它和 Octop 的"不能选安装位置"是同一类问题的两端。

### 3.4 `0o600` 在 Windows 上是空操作（不学其表述）

`ensure_password` 里 `os.open(..., 0o600)` + `os.chmod(target, 0o600)` 在 POSIX 上有效，Windows 上不改变 NTFS ACL。我们自己 `app.go:117` 也用 `0600`——**不要把它写进安全承诺或 PPT**，否则是给自己埋雷。

### 3.5 内容注水（不学）

首启日志：`expert catalog loaded: 18 templates`、`subagent catalog loaded: 272 agents across 19 divisions`。272 个子代理对通用助手是卖点，对我们是噪音。我们 `roles/` 13 个、`agents/` 18 个，精而准，**不追数量**。

## 4. 反哺：可以提交上游的四项

前置事实（决定 PR 打向哪个仓库）：

- 规则内容**不在** `TencentCloud/Octop` 仓库里。`tool_guard_rules.py` 的 `ensure_seeded()` 调 `octop_harness.security.tool_guard.rule_guardian.read_bundled_rules_yaml()`，真正的 YAML 在 `TencentCloud/octop-harness` 的 `src/octop_harness/security/tool_guard/rules/dangerous_shell_commands.yaml`。
- `load_rules_from_directory()` 只遍历 `_DEFAULT_RULE_FILES = ("dangerous_shell_commands.yaml",)`，**新增独立 YAML 文件不会被加载**，必须往同一个文件追加。
- Octop 仓库的 PR 规则：base 打 **`develop`**（不是 main），必须带测试、带截图、更新 `CHANGELOG.md`，一个 PR 只解决一个问题。

### 4.1 PR-A（docs，最可能合并） — ✅ 已提交，见 §7 / [PR #2170](https://github.com/TencentCloud/Octop/pull/2170)

- **仓库 / 分支**：`TencentCloud/Octop` → `develop`
- **标题**：`docs: complete the ~/.octop layout tree and note where the wizard password lives`
- **改什么**：`docs/configuration.md` 的 "Filesystem layout" 代码块。本机磁盘实际存在但文档未列：`workspaces/`、`security/tool_guard/`、`portable/`；另加一句说明——首启口令在 `<home>/octop-login.txt`，**不受 `OCTOP_HOME` 影响**。
- **为什么是我们提**：我们是真实用户，按这份文档在本机找不到配置文件，最后靠读源码才定位。这是最硬的用户证据。
- **验证方式**：`tree` / `ls` 一张截图贴进 PR（他们的规范强制要求截图）。
- **风险**：低。纯文档，不动代码。

### 4.2 PR-B（规则内容，我们的专业优势） — ✅ 已提交，见 §7 / [PR #83](https://github.com/TencentCloud/octop-harness/pull/83)

- **仓库 / 分支**：`TencentCloud/octop-harness` → `develop`（§4 原计划写 `main`，按该仓 `CONTRIBUTING.md` 更正为 `develop`）
- **标题**：`feat(tool_guard): add Windows/PowerShell dangerous-command rules`
- **改什么**：向 `rules/dangerous_shell_commands.yaml` 追加 8 条规则；在 `tests/test_tool_guard.py` 补对应用例。
- **现状缺口**（已在 `octop-harness` 全仓检索确认，命中数均为 0）：`EncodedCommand`、`mshta`、`schtasks` 一条都没有。现有 20 条规则里，Windows 相关只有 `Shutdown-Computer` / `Restart-Computer` 两个词。
- **我们的规则包**：`docs/octop-pr/windows_powershell_rules.yaml`（8 条，覆盖编码命令、下载执行、隐藏窗口、LOLBins、持久化、凭据转储、防御规避、PowerShell 反弹 shell）。
- **本地验证结果**（等价校验脚本，复刻 `GuardRule` 语义：YAML 列表 + 枚举校验 + `re.IGNORECASE` 编译）：

  ```
  schema: 8 rules, 0 error(s)
  summary: 21/21 positives, 16/16 negatives, 0 schema errors
  ```

  正样本含 `powershell -enc <b64>`、`IEX ... DownloadString`、`certutil -urlcache`、`schtasks /create`、`procdump -ma lsass.exe`、`wevtutil cl System` 等；负样本含 `ls -la`、`npm run build`、`grep -rn "service"`、`curl ... -o out.html` 等常见良性命令。
- **注意事项**：
  1. 不要加 `(?i)` 前缀——`GuardRule` 统一用 `re.IGNORECASE` 编译，加前缀是噪音。
  2. 类别只能用 `GuardThreatCategory` 已有枚举（10 个），否则 `ValueError` 直接拒载。
  3. `TOOL_CMD_WIN_DEFENSE_TAMPER` 现在只能归到 `code_execution`，语义不准——这正是 Issue-B 的由来。
- **风险**：中。规则会进入用户默认规则文件，误报会打扰所有人。所以负样本必须一起进测试。

### 4.3 Issue-A（Octop 仓库） — ✅ 已提交，见 §7 / [Issue #2171](https://github.com/TencentCloud/Octop/issues/2171)

**标题**：`OCTOP_HOME is ignored by the setup wizard password file`
**内容**：`PathLayout.from_env()` 支持 `OCTOP_HOME` 重定向数据根，但 `infra/setup/password_file.py` 与 `api/routers/setup.py` 三处都用 `Path.home()`。自定义 `OCTOP_HOME` 时，DB 在新位置、口令留在用户主目录；Docker 版只是因为 `HOME=/data` 才恰好对齐。建议统一到 `PathLayout.root`，或至少在文档明示"该文件不随 `OCTOP_HOME` 移动"。
**为什么不直接提 PR**：这是行为变更，涉及既有集成测试（`tests/integration/test_setup_wizard.py` 断言文件在 `Path.home()`），维护者可能有意为之。先问，别硬改。

### 4.4 Issue-B（octop-harness 仓库） — ✅ 已提交，见 §7 / [Issue #84](https://github.com/TencentCloud/octop-harness/issues/84)

**标题**：`GuardThreatCategory has no defense_evasion category`
**内容**：现有枚举 10 类，缺 `defense_evasion` 与 `persistence`。导致"关闭 Defender / 清空事件日志 / 建计划任务"这类规则只能塞进 `code_execution` 或 `privilege_escalation`，分类失真，审计报表也会失真。建议扩展枚举，并说明是否属于破坏性变更。

### 5.2 落地记录：初始密码文件路径进日志（2026-10-18）

`internal/app/app.go` 原先只 `fmt.Printf("初始密码已保存至: %s\n", pwFile)`。`windowsgui` 构建没有控制台，stdout 整段不可见，用户即使打开了提示文件也无从知道它的路径。

改法：落盘成功后同时 `log.Logger.Info("初始密码已保存至提示文件", zap.String("file", pwFile), zap.String("home", paths.Home()))`。logger 的兜底目标是 `<数据根>/logs/secautomind.log`（`internal/logger/logger.go` 的 windowsgui 分支），所以 GUI 模式下日志文件是唯一可见渠道。

**只记路径，不记口令本身**——日志会落盘，口令不进日志（沿 §3.4 对"明文凭据驻留"的批评口径）。

### 5.3 落地记录：危险命令规则外置（2026-10-18）

把 §2-3「危险命令规则外置为数据」用在自己身上。`isDangerousShellCommand` 的 17 条规则从 Go 切片搬到 `internal/security/command_rules.yaml`，经 `go:embed` 编译期嵌入，`internal/security/command_rules.go` 负责解析编译。

**没有做成"数据根可覆盖"**：这是安全边界，运行时读外部文件等于允许外部文件静默削弱防护，且要新增一个配置项（违背本仓 AGENTS.md 的 Simplicity first）。改规则必须走发版。若将来确需用户自定义，再做数据根覆盖 + 校验 + 告警。

**顺带修掉两个真实误报**（子串匹配的固有缺陷，实锤样本）：

| 命令 | 旧行为 | 新行为 |
|---|---|---|
| `sync /data` | 拦为 netcat（`"nc "` 命中 `sync` 内部） | 放行 |
| `spy -c x` | 拦为 Python 代码执行（`"py -c"` 命中 `spy`） | 放行 |

修法是程序名规则一律改成正则 `\b<名>\s`（词边界 + 空白），而不是继续 `strings.Contains`。17 条规则的 reason 文案与列表顺序**逐条保持不变**（`shell_interception_test.go` 的 reason 断言依赖顺序：元字符先于程序名）。

**新增测试** `internal/security/command_rules_test.go`：

- `TestCommandRulesLoaded`：规则文件不变量（≥16 条、全部编译通过、reason 非空）——把 `loadCommandRules` 的 fail-closed panic 契约变成构建期可断言的东西。
- `TestCommandRulesWordBoundaryFixes`：13 个曾被误拦的良性命令（`sync`/`rsync`/`lnc`/`spy -c`/`mycurl`/`wget-like-tool`/`telnetd` 等）必须放行。**若退回子串匹配，本测试必须变红。**
- `TestCommandRulesUnlessContains`：`unless_contains` 字段的语义与旧实现全局判定一致（`$((` 算术展开放行、`$(whoami)` 拦截）。
- `TestCommandRulesFirstMatchWins`：顺序敏感性回归（`curl x | sh` 报"管道"而非 curl）。

**验证**：`go build ./...` rc=0；`go test -count=1 ./internal/security/...` ok（原 17 拦/10 放用例 + 新 4 组全绿）；全量 `go test ./...` 除 `ctfplatform` 耗时 530s 外全部 ok；gofmt 三个新文件经 LF 归一判定为干净（仓库 CRLF 假阳性口径见 AGENTS.md）。
