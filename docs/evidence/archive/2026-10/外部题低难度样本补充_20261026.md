## 🔴 关键：修掉第三个「假成绩」出口

本轮先跑了一版，`cycling` 同样解出，但日志是：

```
放弃前确定性兜底命中: CTF{Recycling_Is_Great}   ← 仍是 presolve
```

根因：`core/main_agent.py:644 _deterministic_last_chance()` 在**放弃前强制跑一次 presolve**，
**完全不受 `CTF_AGENT_INTERNAL_PRESOLVE` 管辖**，且把 `solved_by_presolve` 置 True。
**没有任何环境变量能关掉它** —— 这是纯 LLM 口径的一个真实漏口。

**已修**：新增 `CTF_AGENT_LAST_CHANCE_PRESOLVE`（默认 `1` 保持既有基线行为，设 `off` 才关）。
改动 8 行，`ast.parse` 通过，备份 `.workbuddy/tmp/main_agent_before.py`。

修后复跑，日志验证：**预扫命中 = 0、兜底命中 = 0**，`cycling` 仍解出但 `solved_by=main_agent_llm`。

## `cycling` 这个解出算谁的？—— 需要限定说明

链路归因（已逐行核对 `core/main_agent.py`）：

1. 第 1 轮 attempt：LLM 失败 → `_infer_skill_require()` **从 LLM 自己的反思里推断出「应该用 cycling 攻击」**；
2. 第 2 轮 attempt 第 0 步：`_last_skill_require` 被消费 → 自动调用 `crypto_cycling` skill → 命中。

**判定：路由决策来自 LLM，执行来自确定性 solver。**
按项目口径（presolve 不计、LLM 自主解题计入）应记为 **LLM 贡献**，
但**必须标注「LLM 选路 + 确定性 solver 执行」**，不可表述为「模型独立完成密码学攻击」。
