**样本**：同一道 `ext_gctf2021_filestore`，同配置（纯 LLM、25 步上限、`max_retries=1`、600s 档）。
模型身份已确证：`glm-4-flash` vs `xfyun/generalv3`。

## 结论

✅ **28% → 1.2%，差 23 倍。`glm-4-flash` 的输出协议失守是模型特性，不是框架问题。**

✅ **失败性质不同**：

- `glm-4-flash`：`tool_failure`（4/4）——**动作格式层**，走不到决策层；
- `xfyun/generalv3`：`wrong_direction` / `unresolved`——**走到了决策层**，失败在方向判断。

❌ **仍然不能写「换模型能提升解出率」**：两边都是 **0/1**，都没解出这道题。
换模型改善的是**协议可靠性**，不是解题能力——这两件事必须分开说。

## 两个附带更正

### 1. 「模型名不进日志」是我上一轮说错了

实测失败行**本来就有** `payload.model=`：

```
LLM HTTP 500 失败：payload.model=generalv3 messages=2条 ...
```

只有**成功调用**不记录模型名。所以模型名可观测性缺口比我说的窄 —— 只需在成功路径补一行，
而非全链路缺失。上一轮那条判据**过度诊断**，已更正。

### 2. xfyun `generalv3` 额度已耗尽

xf4 轮 18 次全部 `AppIdNoAuthError` 且 0 次成功，`xf3` 也已出现 6 次 500。
**xfyun 只剩 `lite` 可用**（`generalv3` 需要单独开通/有独立额度）。
所以 84 次调用中，后两轮部分数据是「额度不足」下的残缺样本，比例 1.2% 仍成立但样本被压缩。
