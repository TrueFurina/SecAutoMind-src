# 服务器副本对齐：把「唯一待决」的前提量一遍 · 2026-11-09

> 结论先行：长期记忆里挂了很久的「唯一待决：服务器副本对齐」，**两条理由实测都不成立**——
> `reset --hard` 不会删未跟踪产出（且本次范围 0 个删除），`agentic_binding.py`
> 在服务器上存在且已被 git 跟踪。但**结论仍然是「不对齐」**，理由换成有证据的两条：
> 待同步的 25 个提交里含 `SecAutoMind_PPT/*` 改动（触发「PPT 永久冻结」硬约束），
> 且全量覆盖 60+ 个文件会牵动并行会话；只动 ref 则让 `dirty_files` 从 19 暴涨。
> 更关键的是：**实质危害已经被 `code_fingerprint()` 显式自曝**——服务器实测
> `dirty_files=19 / clean_checkout=false / note="本次跑批不能等价于 commit 0f02bec7…"`。
> 所以这不是隐性假绿，而是「已被正确标注的已知限制」，不该继续挂在「待决」里。

## 3. 两条旧理由逐条推翻

1. **「全量 reset 删 15 个未入库产出」** —— `git reset --hard` 只重写**已跟踪**
   文件，未跟踪产出要 `git clean` 才会动。本次范围**0 个 D**，连已跟踪文件都不会删。
   那 13 个 `??`（`purellm_full188.json`、`ssrf_runtime_*.json`、
   `purellm_full176.result.json*` 等）在只做 reset 的方案下会原样保留。
2. **「只同步本轮文件会因缺 `agentic_binding.py` ImportError」** —— 实测服务器
   `scripts/agentic_binding.py` **存在**，且 `git ls-files --error-unmatch` 显示
   **已被跟踪**。那是更早副本的旧状态，如今不成立。

## 4. 新的、有证据的阻断（结论仍是「不对齐」）

推翻旧理由不等于该动手。重新评估出两条硬阻断：

- 🔴 **`90e9c5c`「口径数字按提交态真值收敛 31 处」改了 `SecAutoMind_PPT/*` 下的
  2 个文件**。`git log 0f02bec7..HEAD -- SecAutoMind_PPT` 只有这一个提交。
  硬约束「PPT 永久冻结：未说『解冻 PPT』前 `SecAutoMind_PPT/*` 不碰」⇒
  全量对齐会改写服务器工作区的冻结区，不能由本会话擅自决定。
- 🔴 **25 个提交里有 69 个 M 文件**，除已手工同步的 7 个外还有 60+ 个（docs、
  Go 代码、CI、题库证据等）会被一次性覆盖。虽无活跃进程占用 `~/sam`，
  但服务器上另有并行会话使用的其它副本，一次性改写 60+ 文件的收益不明确。
- **只动 ref、不动工作区**（`git update-ref`）也不是好方案：HEAD 前移后，
  那 60+ 个未同步文件会全部变成 `M`，`dirty_files` 从 19 暴涨到 60+，
  代码指纹反而更难读，且 `git status` 会误导下一个会话以为有人批量改了代码。

## 5. 实质危害已被字段自曝（这才是关键）

`code_fingerprint()` 第 20 轮就是为「服务器 = 旧 commit + 手工粘贴新文件」
这种形态设计的：`clean_checkout` 要求「有 commit **且** 未提交改动数 == 0」。
在服务器 `~/sam` 实跑：

```json
{
  "commit": "0f02bec7ff91812a8412f8bc25b4aecbb13057d0",
  "branch": "feat/private-pool-v1-20261107",
  "dirty_files": 19,
  "dirty": true,
  "clean_checkout": false,
  "available": true,
  "python": "3.12.3",
  "note": "工作区有 19 个未提交改动 ⇒ 本次跑批**不能**等价于 commit 0f02bec7ff91"
}
```

`code_fingerprint_selftest()` 在服务器 **4/4 PASS**（干净仓库判 True、
加未跟踪文件即变脏、非 git 目录 available=False 带原因、依赖键完整）。

⇒ 任何在服务器产出的 evidence 都自动携带「不可归因到 commit」的标记。
**危害是「不能引用版本」，不是「指纹撒谎」**，而前者已被显式标注。
把它继续叫「唯一待决」会让人以为有个隐性假绿没修，反而误导。

## 6. 处置

- **维持服务器 `~/sam` 现状**，不做全量 reset、不动 ref、不碰冻结区。
- 把 `MEMORY.md` 的「唯一待决」改写为**已知限制 + 有证据的阻断理由**，
  避免下个会话再从头纠结「要不要拍板对齐」。
- 若将来确需对齐，前置条件：① 用户明确解冻 PPT 或确认可覆盖冻结区；
  ② 先备份 13 个未跟踪产出（虽 reset 不碰它们，但整个流程要可回滚）；
  ③ 之后重跑两端门禁并刷新 `code_fingerprint` 基线。
