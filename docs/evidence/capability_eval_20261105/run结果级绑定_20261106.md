# 第 12 轮：`--run` 结果级绑定（第十一个偏差）——2026-11-06

> 上一轮把 `agentic` 前置守卫打到首次全绿后，本轮不再加门禁，而是查
> **「前置通过 → 真跑批 → 判分」这条链本身**。结论：链路里有一个比
> 「证据被篡改」更基础的洞 —— 判分根本不检查结果是不是这次跑出来的。

## 1. 起点

`run_capability_eval.py` 的 `--run` 段（修改前）：

```python
ev["result_pool_sha256"] = _sha256(bp)      # bp 来自命令里的 --benchmark 参数
rc = subprocess.call(cmd, cwd=ROOT)
if not args.result:
    return rc
return report(adjudicate(args.result, ev, args.out, args.mode, cmd, ...))
```

两个结构性问题：
- `result_pool_sha256` 是**命令参数的指纹**，不是结果文件的指纹。判据里
  `used_sha == claimed_sha` 只比较同一份自动生成证据里的两个键 ⇒
  **参数自证，与结果内容毫无关系**；
- 有 `--result` 时 `rc` 被完全忽略，`adjudicate()` 无论跑批成败都会读那个路径。

## 2. 实证（修改前，两个攻击都产出 verdict）

前置条件用 v2 池 + 三项 env 让守卫全绿，`--result` 指向入库的
`smoke3.result.json`（3 题，旧结果），跑批命令故意不写它：

| 场景 | 命令 | 旧行为 |
|---|---|---|
| A | `python -c "print('FAKE RUN')"`（rc=0，不写结果） | 判分照跑，产出 `total=3` 的 verdict |
| B | `python -c "sys.exit(7)"`（rc=7） | **rc 被忽略**，一样判分 |

两份 verdict 里 `result_pool_sha256 == pool_sha256 == 3bfb3a3922c9886c…`
看起来「结果池绑定成立」，实际只是把 `--benchmark` 参数抄了两遍。
也就是说：**任何一次跑批失败、或命令把结果写到别处，都会拿上一次的旧结果
冒充本批次**，而且判据会给它盖一个「池指纹一致」的章。

## 3. 修法（只改 `run_capability_eval.py`，不碰他人 WIP、不改 `ci.yml`）

新增两个纯函数：

- `snapshot_result(path)`：跑批前记录结果文件的 `exists / sha256 / st_mtime_ns`。
- `verify_run_result(result_path, snapshot, pool_path, rc, started_ns)`：跑批后
  三条同时成立才放行判分，任一不成立即 **fail-closed 返回 2，不生成 verdict**：
  1. `rc == 0`，且结果文件存在、可解析、`details` 非空；
  2. 结果文件确实被本次跑批重写 —— 「字节未变且 mtime 未变」判旧结果洗白，
     「mtime 早于本次跑批开始」判未被写入；
  3. 结果里的题 `id` **全部属于本批次题池**（旧池结果不能套新池指纹）。

`--run` 段据此在判分前校验，并在证据里留下结果级字段
`result_file_sha256` / `result_written_by_this_run` / `result_ids_in_pool_proven`；
同时把「绑定结果题池」的打印改成「**命令参数题池（仅参数，非结果级证明）**」，
避免日志再把参数自证读成结论。

顺带修两处小问题：
- **路径规范化**：跑批子进程 `cwd=ROOT`，主进程 cwd 未必是 ROOT；相对
  `--result` 在两侧会指向不同文件。现在统一成绝对路径再交给 snapshot /
  verify / adjudicate。
- `report()` 的 `os.path.relpath(args.out, ROOT)` 在 Windows 跨盘绝对路径下抛
  `ValueError`（本轮实测撞到 `C:\tmp` vs `E:\repo`），改为失败时显示绝对路径。

自测 `runbind_selftest()` 接进 `pipeline_selftest()` 的 **E 段**；CI 第二段
本来就跑 `run_capability_eval.py --selftest`，故 `ci.yml` / `GATES.md` 未改。

## 5. 两个**排除**的假洞（记下来，免得下轮重挖）

1. **CRLF 行尾导致 CI 恒红？** 上一轮的 IP 直连证据把本机 Go 源码 sha256 写进
   证据，提交时 Git 警告过 `LF will be replaced by CRLF`。实测 4 份文件工作树
   `CRLF bytes=0`，且工作树 sha256 == `git show HEAD:<path>` 的 blob sha256 ==
   证据里的值 ⇒ `.gitattributes` 已管住行尾，CI Linux checkout 不会漂移。
2. **换池跑批时判分读旧池？** `grep load_questions` 看到 L589 写死
   `load_questions(POOL)`（v1 常量），一度判为「第十二个偏差」。复核作用域：
   `adjudicate()` 用的是 `load_questions(pool)`（参数来自 `--pool`），
   `POOL` 常量只出现在 **`pipeline_selftest()` B 段的合成自测**里。
   ⇒ 生产路径无此问题。这正是「结论作用域 = 断言作用域」的又一次实例：
   看到常量不等于看到生产消费者。

## 6. 边界（别把本轮读成能力进步）

- 修的是**入口正确性**，不是能力证据。真实 `--run` 一次都没跑（正向场景用的是
  合成命令写 2 题假结果，只为验证放行路径）。
- 该校验只防「旧结果复用 / 跑批失败被判分 / 旧池结果套新池指纹」，**不防**
  模型先验、题源公开、题面明文答案、通道归属伪造 —— 那些仍由既有判据负责。
- 题源仍全公开、`anchored=False (0/154)`、4 份 verdict 作用域未变、
  `capability_rate` 一个没动。**能力证据仍为空**。
- 仍缺：私有题池+外部锚点注册表、服务器部署副本对齐 HEAD 后的真实 `--run`、
  判据接进 `solve_one()`、修判分口径。
