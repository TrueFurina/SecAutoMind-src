# 首次真实端到端评测 + 第十三个偏差：分母混有结构不可解题

日期：2026-11-06　范围：能力评测链路验证　**不产出可引用能力率**

## 0. 这一轮做了什么

前 13 轮都在补工程件，且多次声明「不该靠加门禁造进展」。本轮**不再新增门禁**，
而是做一件从未做过的事：在所有锁（前置守卫、结果级绑定、判据、verdict 一致性、
证据面 12 条入口）都装好之后，**真跑一次 `--run` 端到端评测**，看链路在真实
LLM 调用下能不能走通、真实数据会不会暴露合成自测看不见的问题。

产物：`real_eval3.runlog.redacted.txt`（脱敏运行日志，同目录）。

## 1. 真实跑批事实（非合成自测）

驱动：一次性脚本从 HKCU 注册表读取凭据，经**内存 env** 传给子进程，
不落盘、不打印、不进命令行；产物全部在 `.workbuddy/tmp/`（gitignore），
不污染 `docs/evidence` 的入库证据。

命令要点：

```
--provider stepfun --benchmark purellm_clean_benchmark_v2.json
--limit 3 --concurrency 1 --timeout 90
```

必须显式 `--provider stepfun`：orchestrator 默认 `tokenrhythm`，其
`supports_tools=True` 会**自动**开启 agentic 路径。stepfun 的 `supports_tools=False`。

| 阶段 | 实测 |
|---|---|
| 前置守卫 | 11 项全 OK（含 4 项 pure_llm 路径 N/A），池指纹 `3bfb3a3922c9886c` |
| 跑批 | `rc=0`，3/3 完成，`solved=0` |
| 结果级绑定 | `OK（本次写入 sha=d47d53d3fd1defbe，题 id 全在本批次池内）` |
| 判分 | 有效开跑 3 / 原始命中 0 / LLM_SOLVED 0 / CLEAN_FAIL 3 / NOT_ATTRIBUTABLE 0 |
| verdict | `claimable=True`、`rate=0.0`、`claim_scope=engineering_regression_only` |

真实执行细节（非空跑）：latency `3.09 / 38.58 / 23.65` 秒、`error` 全空、
`raw_head` 非空；`summary.agentic=False`、单模型 `step-3.5-flash`、

`result_ids_in_pool_proven`、`temperature_fixed` 全 True；
`scoring_variant_gap.false_negative_count=0`。

**结论 1**：整条链在真实 LLM 调用下首次跑通，结果级绑定没有误伤真实结果写出行為。
此前所有「正向场景」都是合成命令写假结果，这次不是。

## 2. 第十三个偏差：`0.0` 的分母里混着结构不可解题

真实结果里 3 题 `got` 全空、`flag 花括号模式` 0 次。查模型输出后发现**不是模型不会**，
而是模型 3/3 明确回复：

> 「题目中明确提到存在 source.py 和 output.txt 两个核心文件，但你未提供这两个文件的
> 具体内容，缺少必要的题目信息无法完成推导。」

静态核查 v2 池（154 题）：

| 事实 | 数值 |
|---|---|
| 题面引用外部文件名（source.py / output.txt / capture.pcap …） | **17 / 154** |
| 这 17 题在 `data/questions_external_bench/_attachments/` 下有对应目录 | **0 / 17** |
| 这 17 题带 `requires_airgap` 标记 | **0 / 17**（与 23 道 airgap 题零交集） |
| pure_llm 前置守卫对 `--artifact-dir` 的态度 | **明确禁止** ⇒ 设计上不给附件 |

判据的「有效开跑」只认 `latency > 0 且无致命 error` ⇒ 这 3 题（及全池那 17 题）
全部计入分母并判 `CLEAN_FAIL`。

**表述要精确**：`provenance.known_limitations` 里**已经写了**「大量题面过短或缺附件，
结构上不可解」，`report()` 也会把它打印成 `[!]` 警告 —— 所以不是「完全没人消费」。
真正的问题是：这条局限**不进 verdict、不区分具体是哪几题、不影响有效分母与 rate**，
下游证据链无法程序化消费，只有人读日志才看得见。于是 `rate=0.0` 的上限由
「题目有没有给必要条件」决定，而不是模型能力 —— 但读数本身长得和「模型不会」一模一样。

## 3. 修法（最小、只标注）

- 新增 `attachment_dependency_fragment(result_path, pool_path, command)`：
  判据只认**代码级事实** —— 跑批命令是否提供 `--artifact-dir`，加上题面是否引用
  外部文件名。**不查附件目录**：`_attachments/` 被 gitignore，CI checkout 里可能
  不存在，查了会造成假阴性。
- 结果写进 verdict 顶层 `attachment_dependency`（题数、题 id、批次大小、
  `artifact_dir_supplied`），`report()` 打印
  `[!] 结构不可解 N/M 题 ⇒ 0 命中不等于模型不会`。
- **只量化标注**：不改判分、不重算 rate、不从分母剔除、不改题池。
  剔题会改变池指纹，而 v2 父池指纹已钉死，会让 4 份历史 verdict 的绑定失效。
- G 段 `attachment_dependency_selftest()` 接进 `pipeline_selftest()`
  （CI 第二段本来就跑该入口），`ci.yml` / `GATES.md` 未改。

## 4. 验证（全实跑）

| 项 | 结果 |
|---|---|
| G 段变异自测 | **3/3**：未给附件标 1 题 / 带 `--artifact-dir` 归零 / 池损坏 fail-closed None |
| 真实数据对照 A/B/C | 真实结果无附件 **3**；同一结果声明提供附件 **0**；换成 3 道不引用附件的题 **0** ⇒ 不是恒定值 |
| 真实结果重判（`--adjudicate`，不重跑 LLM） | 标注仍 **3/3**；判分变 `NOT_ATTRIBUTABLE 3 / rate=None / claimable=False` |
| `run_capability_eval.py --selftest` | RC=0，`链路自测 PASS`（A–G 七段） |
| 11 项门禁 | 全 RC=0；`verify_verdict_chain PASS（4 份 / 0 异常）`；证据面 `--check PASS` |
| CI 缺件模拟（移走 `rev_leak.out`） | RC=0 |
| 明文/凭据扫描 | 原始日志 0 次、脱敏日志 0 次、本轮 diff 0 命中 |

**关于 `--adjudicate` 对照**：同一份刚由 `--run` 产出的真实结果，换入口重判得到
`CLEAN_FAIL 0 / NOT_ATTRIBUTABLE 3 / rate=None`，与 `--run` 的
`CLEAN_FAIL 3 / rate=0.0` 不同。原因是 `--adjudicate` 用的是 preflight 自动证据，
缺结果级内生证据（这是「历史批次不受前置阻挡、判为不可归因」的既有设计），
**不是 bug**。但它说明 verdict 结论依赖入口，不能把两种读数混着引用。

- **能力证据仍为空**。本轮是 3 题小样本真跑，`rate=0.0` 且作用域
  `engineering_regression_only`；更关键的是 **3/3 结构不可解**，所以这个 `0.0`
  连「模型表现」都不能解读，只能说明链路可执行。
- 真实 `--run` 只跑 3 题，**不是全量 154**；未刷 `count_stats` 数字。
- 未改题池、未改判分口径、未碰他人 WIP `ctf_stepfun_orchestrator.py`（仍 7+/5-）、
  未碰 PPT、未 push；会话按纪律 claim → release。
- 要真让分母有意义，三条路各自都有代价：①给 pure_llm 路径提供附件
  （要改前置守卫与 WIP orchestrator）；②把不可解题单列成新池
  （要新指纹 + 重绑 4 份历史证据）；③转 agentic + 真实附件 + 子进程隔离证据
  （第 13 轮刚把 agentic 置为 fail-closed）。本轮未做，不假装已解决。
