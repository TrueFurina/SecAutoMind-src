# IP 直连证据实跑 + 第十个偏差（结果出口）——2026-11-06 第 11 轮

> 本轮不再新增门禁脚本来制造「进展」。目标是把能力证据链里**至今唯一缺失、
> 且可以在当前条件下真跑出来**的一块补上：断网闸的 IP 直连证明。
> 结论先行：**证据已取得且被消费侧判据真正放行；能力证据仍然为空。**

## 1. 起点：为什么是这块

主记忆与 `cmd/airgaptest/main.go` 的注释都写着同一条历史判据：

> 历史所有「断网跑批」日志里模型只试过域名，拿到 `Temporary failure in name resolution`；
> 这个错误与「机器没配 DNS」完全同形 ⇒ **无一提供 IP 直连证据**，旧「断网成绩」一律按未隔离处理。

而 `run_capability_eval.py --preflight --mode agentic` 明确要求
`--airgap-proof` 里 `ip_direct_blocked=true && af_unix_ok=true`。
此前该参数**从未被满足过**：`--preflight` 默认 `pure_llm` 模式把它标 N/A 绕过，
`agentic` 模式则必然 FAIL。本轮服务器可达、会话登记空闲（活跃 0/5 → claim 后 1/5），
具备实跑条件。

## 3. A/B 原始输出（IP 直连，绕开 DNS）

基线（不开闸）：

```
[airgaptest] CTF_AIRGAP="" Enabled=false IsChild=false
AF_INET CONNECTED-NOT-BLOCKED
AF_INET6 OSError 101 [Errno 101] Network is unreachable
AF_UNIX OK
AF_INET-UDP OK
```

开闸（`CTF_AIRGAP=1`）：

```
[airgaptest] CTF_AIRGAP="1" Enabled=true IsChild=false
AF_INET PermissionError 1 [Errno 1] Operation not permitted
AF_INET6 PermissionError 1 [Errno 1] Operation not permitted
AF_UNIX OK
AF_INET-UDP PermissionError 1 [Errno 1] Operation not permitted
```

判读要点：
- 基线 `AF_INET CONNECTED-NOT-BLOCKED` ⇒ **服务器本来就有外网**，断网不是环境属性；
- 开闸 TCP/UDP 全 `EPERM errno=1` ⇒ 是 seccomp 在 syscall 层拦的，
  不是 `ENETUNREACH(101)`、不是 DNS 失败；
- `AF_UNIX` 两组都 OK ⇒ 没误伤本地 IPC；
- 基线 `AF_INET6` 是 `101`（该机无 IPv6 路由），开闸变成 `EPERM 1` ⇒ 该族同样被拦。

二进制 `sha256=6dc5591d841c05f5…`，Go `go1.25.4 linux/amd64`。
两组 stdout 原文逐字存进证据 JSON，不摘录、不改写。

## 4. 证据件：`scripts/prove_airgap_ip_direct.py`

按项目既有纪律设计，四条硬约束：

1. **自动生成**：`--run` 真跑 ssh A/B，从原始 stdout 解析出
   `baseline_egress_proven / ip_direct_blocked / af_unix_ok / udp_blocked`；
   不许人填 `true`。证据含 `generated_at`、`host`、源码/二进制 sha256、两份原始输出。
2. **重算复核**：`--check` 纯本地、不联网，从 `baseline_output_raw` /
   `gated_output_raw` **重新解析**并逐字段比对存盘值；
   同时校验 4 份 Go 源码 sha256 与本机当前文件一致（源码一漂移，旧证据立刻红）。
3. **fail-closed**：以下任一即 `NOT_PROVEN`，不给放行：
   基线本来就断网、开闸报 `ENETUNREACH`/DNS 失败、`AF_UNIX` 被误伤、
   UDP 出口没拦、A/B 缺一侧、传输后源码指纹不一致、字段缺失。
4. **可变异验证**：`--selftest` 12/12（7 个输出形态 + 5 个篡改变异），全部实跑通过。

产物：`airgap_ip_direct_proof_20261106.json`（`verdict=PROVEN`，`reasons=[]`）。
脚本本身不含任何密钥或题目答案值。

## 6. 第十个偏差：`summary.coverage` 是绕过判据的伪能力率出口

排查 `solve_one()` 接线时发现（只读，未碰他人 WIP）：

```python
# scripts/ctf_stepfun_orchestrator.py (他人 WIP，本轮未改)
solved = sum(1 for r in results if r["solved"])
summary = { ..., "solved": solved,
            "coverage": round(solved / len(results), 4) if results else 0, ... }
```

`coverage` **完全由 sha256 命中算**，判据链（`judge_run` / verdict）是**可选的旁路**：
`run_capability_eval.py --adjudicate` 是事后另写一份 verdict 文件，
原始 result.json 里的 `coverage` 不受任何约束。
历史 `scripts/purellm_full176.result.json` 实测：

```
summary.solved = 1   summary.coverage = 0.0057   total = 176
```

而那唯一 1 命中早已被证伪为**题面明文抄写**。也就是说，任何人直接打开结果文件，
就能读到一个看起来像「能力率 0.57%」的数，而整条判据链对此无能为力。

**本轮最小封堵**（不新建脚本、不改 WIP、不改 `ci.yml`）：在
`verify_capability_evidence.py` 的交叉校验里加一条——
**入库的 `*.result.json` 中任何 `solved=True` 的题，必须被某份 verdict 的 `rows` 归因**；
未覆盖即报红「summary.coverage 会成为伪能力率」。

边界必须说清：
- 只锁**入库**结果。当前唯一入库的 `smoke3.result.json` 是 `solved=0`；
  `purellm_full176.result.json` 在 `scripts/` 下且被 gitignore，**不在扫描范围**，
  它那个 `0.0057` 依旧躺在本机磁盘上 —— 本轮没有、也不该去改历史证据文件，
  只在本文档明确点名「禁止引用」。
- 这条断言只防「未来把带命中的结果入库却不判归因」，不追溯修复历史文件，
  也不把 `solved` 字段从生产脚本里改名（那是他人 WIP，需持有跑批权的会话处理）。
- 更彻底的修法（判据接进 `solve_one()` 返回体 / 结果落盘前自动降级）
  仍是待办，见 §8。
