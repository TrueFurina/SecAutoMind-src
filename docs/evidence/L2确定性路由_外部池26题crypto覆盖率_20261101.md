| 项 | 取值 |
|---|---|
| 题源 | `data/questions_external_bench/external_bench.json` 的 **crypto 子集 26 题**（外池共 40 题 = crypto 26 + misc 14） |
| 被测层 | **只跑 L2**（Python skill 确定性路由），不开 L3、不调 LLM ⇒ 全程 **零 token** |

## 结果

**2 / 26 = 7.7%**，26 题合计 347.4s（平均 13.4s/题），零 token。

| 题 | 结果 | 耗时 | 命中 skill / 备注 |
|---|---|---|---|
| `ext_gctf2023_least-common-genominator` | **HIT** | 6.4s | `crypto_lcg_recover`（喂 `dump.txt`，0.49s） |
| `ext_gctf2023_mhk2` | **HIT** | 106.4s | `crypto_knapsack_mhk` `kind=mhk2_decrypt`（101.9s） |
| `ext_gctf2023_zip` | MISS | 63.1s | 唯一"跑满"的 miss（bkcrack 类路径，未出 flag） |
| 其余 23 题 | MISS | 4.3–13.0s | 全部在 13s 内走完 28 个 skill ⇒ 都是快速失败（参数/格式不匹配），不是算不完 |

两次命中的 sha256 均与题集登记的 `flag_sha256` 逐位相等。审计：`crypto_lcg_recover.py` /
`crypto_knapsack_mhk.py` 源码中 `requests|urllib|socket|http.client|curl|wget|subprocess`
**零匹配**，输入只有附件本地文件 ⇒ 满足"sha256 命中 + 零外网访问"双条件，不是抄公开 writeup。

## 本轮由这次普查逼出来的两个真 bug（都已修，各自独立提交）

### 1. `ceb7804` L2 单点超时 30s → 120s

修前 mhk2 是 **L2-MISS**，日志只有一行 `L2-MISS`，看不出任何原因。真机日志：

```
skill 超时  {"skill": "crypto_knapsack_mhk", "timeout": "30s"}
```

而同一个变体把上限放开后跑 **101.9s** 才出结果。也就是说：**LLL/格基/因式分解这类
crypto 主力 skill 在默认配置下 100% 被超时掐死，失败形态与"skill 解不了"完全一致。**
这是最难归因的一类静默失败——能力已经具备，被配置关掉了。

修法：`Runner.l2Timeout`（`CTF_L2_SKILL_TIMEOUT`，默认 120s）只作用于 L2 批量扫；
单点上限 = `min(剩余整类预算, l2Timeout)`，预算仍是硬闸。`RunSkill`（模型单点）不受影响。

验证：同题同参数 106.1s → `L2-HIT cand=1`，sha256 一致。

### 2. `e37a675` 生产路径 L2 没有整类预算

`cmd/runner` 原来调的是无限预算的 `TryCategory`：crypto 类 28 个 skill × 最多 6 个
(文件×分派) 变体 × 30s ⇒ **最坏 56 分钟/题**。跑批里看不出来（题多了均摊），赛时直接把
单题时间预算吃光。

修法：删掉无限预算入口（`grep` 确认零调用点，让"忘了传预算"编译期就不成立），只留
`TryCategoryBudget` / `TryCategoryLocal`；预算真值源统一为 `CTF_L2_BUDGET`，
生产兜底 180s，`llmbench --l2-budget` 默认也读同一个环境变量。

## 24 道 miss 的归因（为什么 7.7% 是天花板，不是阵容不够）

按题提取日志里所有子进程失败的错误串，**24 道题的失败谱几乎完全一致**：

```
integer modulo by zero ×2~4      # skill 把缺省参数 0 直接拿去取模
Expecting value: line 1 col 1    # skill 对非 JSON 文件 json.load
KeyError 'n' / 'pt' / 'curve'    # 必需的数学参数没送到
```

同一批错误在 26 道题里反复出现，说明 L2 的实际行为是：**拿同一份文件广撒 28 个 skill**，
而不是"按工件语义选 skill"。根因在 skill 的入参契约上：

- 19 个 `crypto_*` skill 里，**只有 7 个**接受 `path`（能吃附件文件）；
  剩下 12 个要的是 `n/e/c/curve/factors/p_high` 这类**算好的数值**，L2 没有来源可填。
- 那些数值**不在附件里**：全 26 题扫描，只有 **2 题**的附件存在 ≥2 个大整数参数赋值
  （`2021_h1` 的 `chall.py: mod,a,b,n`；`2024_zkpok` 的 `param.py: n,c`）。
  其余题目的附件是 `server.py` / `server.dart` / `*.sobj` —— **题目本体在服务端，离线无输入**。

补充证据：

- `ext_gctf2023_primes` 的 `chal.sage` 只有函数定义（`gen_primes/prod_exp/encode`），
  求解需要的 `X` 不在文件里 ⇒ 上一轮列的待办「给 primes 补 `path` 入口」**是死路**，本轮用证据关闭。
- `ext_gctf2022_cycling` 的 `chall.py` 是服务端脚本，`n,e,ct` 同样不在附件 ⇒ 同上，关闭。

结论：**7.7% 反映的是这套外部池"可离线求解"的比例，不是 skill 阵容的上限。**
用"86 个 skill"讲故事会把预期抬到与事实不符的高度；L2 在离线批里的真实定位是
"有工件、且工件格式与该 skill 的入参契约匹配"的那一小块。

## 顺带做的一次诚信审计：附件里的 flag 文件

4 道题的附件目录里直接带 `flag` / `flag.txt`（`least-common-genominator`、`filtermaze`、
`numerology`、`bpfbox`）。逐一按 raw 与 strip 两种形态算 sha256 与题集登记的 `flag_sha256`
比对：**4/4 全部不相等**（其中 3 个是同一个 9~11 字节占位符）⇒ 不存在"读附件 file 抄答案"
的污染，命中的 2 题不是靠这条路径。

## 复现

```bash
# 服务器上，隔离副本 /tmp/l2cov
export CTF_SKILLS_DIR="$PWD/CTF-Agent_融合/ctf_agent/skills"
./bin/llmbench --real data/questions_external_bench/external_bench.json \
  --att-root data/questions_external_bench/_attachments \
  --work-base /tmp/l2cov_work --with-l2 --l2-budget 180s \
  --ids <26 个 crypto id 逗号分隔> --out /tmp/l2cov/l2_crypto26.json
```

无 LLM key 时自动进 `l2Only`（不跑 L3），报告里每行带 `layer=l2 / l2-miss`，
`seconds` 是该题 L2 实际耗时。
