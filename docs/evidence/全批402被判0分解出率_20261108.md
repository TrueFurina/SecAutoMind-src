# 全批 402 被判成「0% 解出率」：调用失败被塞进能力分母

日期：2026-11-08
作用域：`scripts/check_pure_llm_caliber.py`（判据）、`scripts/ctf_stepfun_orchestrator.py`（生产侧）
结论一句话：**一次都没问出口的调用，过去会以 `capability_rate=0.0 / claimable=True / blocking=[]`
的形式落盘。** 这是「换池洗白」的镜像：那边是把不该算的算成解出，这边是把不该算的算成没解出。

---

## 一、怎么发现的

上一轮用 `--netns-isolate require` 起了两次真实隔离跑批，两次都在**第一次 LLM 调用**就 402：
stepfun「`exceeded your current quota`」、tokenrhythm（jiyuan key）「`账户余额不足，请充值`」。
当时只记了一句「按既有口径整批剔除」，没验证**口径是否真的会剔除**。这一轮去验证，发现不会。

## 二、实测：判分器把 5 道死题全部算成有效分母

拿服务器上那两份真实结果文件，过当时的判分器（证据键全部置真）：

```
verdicts        = {'LLM_SOLVED': 0, 'CLEAN_FAIL': 2, 'NOT_ATTRIBUTABLE': 0}
effective_runs  = 2 / 2
claimable       = True
capability_rate = 0.0
blocking_reasons= []
```

`CLEAN_FAIL` 的语义是「题被问过了，模型没解出来」。而这 2 题的每一次调用都是 402，模型从未被问到。

根因有两条，互相独立，各自都能单独造成这个结果：

### 根因 ①（生产侧）失败没写进 `error`

`ctf_stepfun_orchestrator.py` 的 agentic 分支返回体里 `"error": ""` 是**无条件**的。
全部轮次失败时，失败只留在 `llm_rounds[].error` 与 `api_error_first` 里：

```
error            = ''                      ← 所有消费方先看这一格，它说"没问题"
api_error_rounds = 1
api_error_first  = 'HTTP 402 Payment Required: 账户余额不足，请充值后重试。'
llm_rounds       = [{finish_reason: 'error', content_chars: 0, tool_calls: 0}]
latency          = 3.99                    ← >0，所以"0 秒空跑"那条判据也拦不住
```

### 根因 ②（判据侧）`_effective()` 只看 `error` 与秒数，不看轮次

```python
def _effective(detail):
    secs = detail.get("latency", detail.get("seconds"))
    if not isinstance(secs, (int, float)) or secs <= 0:   # 3.99 通过
        return False
    err = str(detail.get("error") or "")
    if err and any(k in err.lower() for k in (...quota, 403, 429...)):
        return False                                       # err 是空串，不命中
    return True                                            # ⇒ 有效
```

记忆里记的口径是「有效分母 = seconds>0 **且 max_round>=1**」，但代码里从来没有第二句。

## 三、修法

### 判据侧：只认**正面证据**，缺字段一律不判废

新增 `_rounds_all_failed()`：`llm_rounds` 非空且**每一轮** `finish_reason` 都是
`error`/`timeout` ⇒ 这题没有任何模型输出。生产侧也可直接声明 `all_rounds_api_failed=True`。

🔴 关键约束：**缺字段 ≠ 否定**。`docs/evidence/private_pool_v1_20261107` 与
`private_pool_v2_20261107` 的结果文件**整份没有 `llm_rounds`**（40/40 全都缺）。若把
「缺字段」读成「没有成功轮次」，88.3% 那批会被自己的判据判废。已实测：改前改后

| 批次 | 旧 verdict | 新复算 | 一致 |
|---|---|---|---|
| agentic_s1 | rate=0.925 claimable=True | rate=0.925 claimable=True | ✅ |
| agentic_s2 | rate=0.825 claimable=True | rate=0.825 claimable=True | ✅ |
| agentic_s3 | rate=0.900 claimable=True | rate=0.900 claimable=True | ✅ |

### 批级：全批调用失败 ⇒ 不给读数

`claimable` 多一条与：`len(api_failed) < len(details)`。全批失败时
`rate=None`、`claimable=False`，并写进阻断理由
「全批 LLM 调用均在 API 层失败（N/N 题），本次不产生能力读数」。

部分失败**仍然出率**（那些题确实没被问到，剔除是正确方向），但必须自己说明分母为什么变小：
`notes` 里写「分母提示：k/N 题因调用层失败被剔出，本文 rate 的分母是 M」。
否则读的人得自己做减法才知道 40 题为什么算出 「3/21」。

### 生产侧：失败要写在所有消费方都会看的那一格

- agentic 分支：`all_failed = bool(stats) and api_err_rounds == len(stats)`，
  此时 `error = api_error_first`；新增显式键 `all_rounds_api_failed`。
  `api_error_rounds` / `api_error_first` 复用同一组变量，不再重算两遍。
- 纯 LLM 分支另有一个同族缺陷：`body` 里没有 `choices` 时（**200 + 错误信封**，网关/代理常见），
  旧代码把整段错误 JSON 当模型正文、`finish` 记成 `"stop"`、`api_error_rounds` **硬编码 0**
  ⇒ 一次失败被记成「模型答了一段 JSON 但没答对」。
  现在：`no_choice=True` ⇒ `finish_reason="error"`、`error` 落原文、
  `search_text` 置空（不在错误信封里找 flag）。
- 两条异常分支也补 `all_rounds_api_failed`。

## 四、验证

判据自测 32/32（原 20 条 + 新 12 条），`--selftest` EXIT=0。新增覆盖：

| 用例 | 断言 |
|---|---|
| 全轮 API 失败 ⇒ 不算有效开跑 | `_effective=False` |
| 全轮 API 失败 ⇒ `NOT_ATTRIBUTABLE` 而非 `CLEAN_FAIL` | 判分语义 |
| 全批 API 失败 ⇒ rate 为 `null` 而非 `0.0` | 读数方向 |
| 全批 API 失败 ⇒ 明确写进阻断理由 | 可审计 |
| 1/3 题失败 ⇒ 仍出率且分母=2、rate 仍 0.5 | 防「剔除变做小分母」 |
| 缺 `llm_rounds` 的历史文件 ⇒ 仍有效、仍可 LLM_SOLVED | 历史兼容 |
| 有一轮成功 ⇒ 有效（哪怕其余轮 402） | 不过度剔除 |
| 402 措辞换成「账单未结清」⇒ 结构判据仍抓到 | 不依赖文本 |

**变异验证**：删掉 `_effective` 里的 `if _rounds_all_failed(detail): return False` 两行
⇒ 5 条转 FAIL、32→27 通过、EXIT=1。其中最有说服力的一条：

```
FAIL 1/3 题调用失败 => rate 仍是 0.5      got=0.333333 want=0.5
```

——一张死题把 50% 拖成 33.3%，这就是「假红进分母」的实际幅度。

**真实数据**：服务器上那两份 402 结果文件，5/5 道题从「有效」变「无效」：

| 批次 | n | 旧判据有效 | 新判据有效 | 全轮失败 |
|---|---|---|---|---|
| tokenrhythm/jiyuan | 2 | 2 | **0** | 2 |
| stepfun | 3 | 3 | **0** | 3 |

**闭环**（不调真实 LLM，注入假 `call_llm`）：200+错误信封 ⇒
`error` 非空、`api_error_rounds=1`、`all_rounds_api_failed=True`、`got=''`；
同一份记录进判分器 ⇒ `api_call_failed_no_successful_round`。三组对照：

| 场景 | claimable | rate | api_call_failed_runs |
|---|---|---|---|
| 1 死 1 活 | True | 0.0 | 1（分母 1） |
| 只有死题 | **False** | **None** | 1 |
| 只有活题 | True | 0.0 | 0 |

## 五、这条不改什么（避免过度声明）

- 不改池、不改题、不剔分母之外的东西。部分失败仍按原口径出率。
- 不宣称「隔离下的解题率」。额度墙还在，`0/5` 是 `NOT_ATTRIBUTABLE`，
  不是 0% 能力，也不是「隔离拖慢了模型」的证据。
- `attachment_dependency` / `scoring_variant_gap` / 私有性锚点全不受影响。

# 附：修这条时被同一族缺陷绊到的三处（都是「环境变了，判据没跟着走」）

## 六、`capability_caliber_test.py` 自 11-07 起一直是红的，没人知道

跑五段入口才看到：`私有性外部锚点证据 FAIL 差异字段=['registry_sha256']`。

- 证据文件 `private_proof_audit.json` 是 **11-05** 写的，那时注册表还不存在 ⇒
  `registry_sha256=null`、`reasons=["no_registry: ..."]`。
- 注册表 **11-07** 由 `dadb513` 入库（v1 十题）⇒ 重算变成
  `registry_sha256=9776a80e…`、`reasons=["registry_pool_sha256_mismatch"]`。
- 结论**没变**：`anchored=False`、`0/154`、`pool_sha256` 一致。

这就是「证据快照 vs 活环境」的经典冲突。处置：重生成证据（`--check`），
差异只有 3 行；结论一字未改。

同一处还牵出**另一个**真问题：重生成后 git diff 显示**整文件 34 行全变**，
而实质只差 3 行 —— 因为 `audit_private_proof.py` 写证据时没指定 `newline`，
Windows 的文本模式把 `\n` 翻成 `\r\n`。后果不只是 diff 噪音：**同一条命令在
Linux 上永远复现不出那份字节**，评审核对不上时会归因成"数据被改过"。

## 七、verdict 链与证据门禁互相矛盾（两边都"正确"，合起来必红）

重生成私有性证据之后，`verify_verdict_chain.check()` 全红，理由
`claim_scope.private_proof_reason 与代码重算不一致`。

- 证据门禁要求：快照必须等于**现算**结果 ⇒ 逼你重生成。
- verdict 链要求：verdict 里记的理由必须等于**现算**理由 ⇒ 重生成后现算理由变了，历史 verdict 对不上。

两条都是对的，但合起来让「注册表日后入库」这件事必然制造红，而且**无法靠修真实问题消除**。
判据变成枷锁之后，人们只会去关它。

处置：把 `private_proof_reason` 定性为**说明性文本**而非**声明**，比对时豁免文本值，
但必须同时满足两条：
1. 绑定的布尔 `private_proof_anchored` 一旦分歧，照旧报红（"伪造锚点"用例仍红）；
2. 未锚定却不写理由 ⇒ 红（豁免不等于放行空理由）。

自测同时钉住两个方向：`未锚定却删掉理由 → 红`、`只改理由文本、结论不变 → 放行`。
现在是 9/9。

## 八、顺手堵住 CRLF：`--out` 写入必须显式 `newline="\n"`

用 AST 判据（不用正则 —— 正则会被注释/字符串里的 `open(args.out, "w")` 骗）
扫 `scripts/*.py`：凡是 `open(<x>.out, "w"…)` 都必须带 `newline`。修了 8 处：
`audit_private_proof` / `audit_writeup_answer` / `audit_pool_prior` /
`audit_scoring_variant_gap` / `audit_external_pool_readiness` /
`check_pure_llm_caliber` / `ctf_arena_batch` / `ctf_stepfun_orchestrator` /
`audit_run_logs` / `overnight_status`。

其中两处是 AST 找到而 `grep 'open(args.out'` 漏掉的（`a.out` 形态）——
判据抓的是**结构**，所以抓得到。

变异：把 `audit_pool_prior.py:245` 的 `newline` 删掉 ⇒
`1b/2 证据写入可复现性 FAIL`、`audit_pool_prior.py:245` 被点名、rc=1；还原后 PASS。

## 九、本轮的三个"自踩坑"（都是自己写判据时踩的）

1. **同一规则两处实现，30 分钟内就分叉**：`is_api_failed()` 第一版无条件读
   `api_error_first` 文本，于是一次 402 后转成功的正常题被判"调用失败"——
   那是**缩小分母**（抬高比率）的危险方向。收敛成单一实现 `api_call_failed()`，
   `analyze_retry_recoverability` 只转发不重写。
2. **自测自己报假红**：`failed = [x for x in results if not x[1]]`，而 `rc=0` 是假值
   ⇒ 8 条全 PASS 却打印 7/8。改比 `!=`。同族：「缺失≠否定」「0 不是失败」。
3. **CRLF 又咬一次**：`git check-ignore --stdin` 那轮是输入侧，这轮是输出侧。
