### 🔴 更正上一轮的两条结论

1. **「本机 pip 拿不到索引、gmpy2 装不上」是错的。**
   真因是**清华镜像按 User-Agent 拦 pip 26**：同一个 URL，
   `curl` 200、`urllib` 200、`pip/24.3.1` 200，而 pip 26 的真实 UA 稳定 **403**（实测 3/3）。
   `pip -vvv` 才看得到：`"GET /pypi/web/simple/scapy/ HTTP/1.1" 403`，
   然后把 403 降级成 `from versions: none` —— 报错文本里连「403」都没有。
   换腾讯云镜像后两个包都秒装。
2. **「cp314 没有 gmpy2 wheel」是错的。**
   `gmpy2 2.3.2` 就有 `cp314-cp314-win_amd64` wheel。上一轮我只看了镜像页面上
   `grep cp314` 的片段（页面很长，被我截断了），没有真的让 pip 去解析。

教训与「文件名里的 airgap 不是机制」同源：**报错文本不是原因**。
`from versions: none` 既可能是「真没有」，也可能是「HTTP 403 被吞」，
必须看到 HTTP 状态码才能区分。判据要落在可观测的那一层。

### 4. `temperature_fixed` 判据：同一段代码，两种写法，结论相反

`scripts/run_capability_eval.py::_fixed_temperature_proven()` 原本是：

```python
vals = re.findall(r'["\']temperature["\']\s*:\s*([0-9.]+)', src)
if len(vals) >= 2 and len(set(vals)) == 1:
    return True, "请求体显式固定 temperature=%s（%d 处）"
```

而 orchestrator 在 2026-11-07 为 kimi 系列（400 不认该参数）改成了条件下发：

```python
if _accepts_temperature(model):
    payload["temperature"] = 0.2      # 下标赋值，不是 dict 字面量
```

**行为一模一样，正则命中数从 2 变成 0。**

实测：

| 位置 | 判据实现 | 结果 |
|---|---|---|
| 服务器 `~/sam` | 正则版 | **`(False, '请求体未显式固定 temperature（vals=[]）')`** |
| 落盘 `preflight_evidence_auto_20261107.json` | —— | **`temperature_fixed = True`** |

⇒ **那份 evidence 是用旧代码生成的，此后从未重跑。** 现在拿它去引用，引的是一条
重跑就红的历史状态。

而且这个判据**两个方向都会错**：

- 假红：代码正确但换了写法（上面这例）；
- 假绿：把 `{"temperature": 0.2}` 写进**注释或字符串**，正则会判 True，而真实请求体里没有它。

一个判据同时能出假红和假绿，说明它测的是**文字**不是**行为** —— 与
`_registry_threaded_proven()` 被注释里的 `adjudicate(` 骗成假阳性是同一族
（那次已改 AST，这次忘了同样处理）。

## 四、修法

### 1. `_fixed_temperature_proven()` 改正则 → AST + 交叉比对

AST 层面数两件事，再比对：

- **请求体字面量**：同时含 `"model"` 与 `"messages"` 两个 key 的 dict（实测 2 处）；
- **temperature 覆盖**：`<x>["temperature"] = <num>` 下标赋值 + dict 字面量里的
  `"temperature": <num>`（实测 2 处，行 399 / 647）。

判据 = 覆盖数 ≥ 请求体数 且 取值唯一。当前返回：

```
AST:请求体 2 处全部显式固定 temperature=0.2（2 处赋值，行 399,647；
条件发送见 `_accepts_temperature`：不支持该参数的模型不带此字段）
```

刻意保留的取舍：
- **不要求无条件发送**。`kimi-` 前缀不带该字段是**修 bug 不是缺陷**，
  判据只要求「凡是发请求的地方都写了 temperature 这个意图」，条件性写进 basis。
- **新增一条请求路径却忘加 temperature 会红**（覆盖数 < 请求体数）。

### 2. 自测 `temperature_selftest()`：7/7，含「旧正则会假绿」的对照

6 个合成源码变体 + 1 条对照：

```
PASS baseline_two_paths   got=True   want=True
PASS missing_one_path     got=False  want=False   请求体 2 处，只固定了 1 处
PASS mixed_values         got=False  want=False   取值不唯一:[0.2, 0.9]
PASS comment_only         got=False  want=False   请求体 2 处，只固定了 0 处（注释不算）
PASS syntax_broken        got=False  want=False   不可解析 ⇒ fail-closed
PASS no_request_dict      got=False  want=False   无请求体 ⇒ 形状变化 fail-closed
PASS old_regex_fooled     旧正则看到注释里的 ['0.2'] ⇒ 会判 True（假绿实证）
```

最后一条是最有价值的：同一段合成源码上同时跑新旧两种判据，把「测文字 vs 测行为」
的差别钉在自测里，而不是靠文档提醒。

接进 `pipeline_selftest()` 的 I 段。完整链路自测 `--selftest` → **A–I 全段 PASS，RC=0**。

> 补充一个自己踩的坑：`mixed_values` 变体最初用 `str.replace` 构造，
> 因换行数不匹配**静默没生效**，变体没变却"通过" —— 自测空转。已改为显式写全字符串。
> 这与「变异必须看得见」是同一条纪律。

## 七、补做的两件：代码指纹 + 环境脚本

### 1. `code_fingerprint()`：把「跑的是哪份代码」变成字段

`scripts/run_capability_eval.py` 的 evidence 新增 `code_fingerprint`，四类信息：

```
commit / branch / dirty_files / clean_checkout
python / implementation
deps{gmpy2, scapy, brotli, zstandard, sympy, fastapi, pycryptodome}
root / available / error / note
```

**接线不是只写不读**：`judge_run()` 把整个 `evidence` 原样带进 verdict
（`verdict["evidence"]["code_fingerprint"]`），所以从此「结果 → 代码版本」这条链
才是通的。历史 verdict 里没有这个键，本身就是「不可归因」的可见证据。

三条刻意的设计：

1. **脏工作区必须记出来且不许当干净**。`clean_checkout` 同时要求「有 commit」与
   「未提交改动数 == 0」。服务器工作区正是「落后 37 commit + 手工粘贴的新文件」，
   只记 commit 的指纹会撒谎。
2. **未安装的依赖记 `null` 而不是省略键**。省掉键等于把「缺依赖」从指纹里删了，
   而缺依赖会改变结论（缺 scapy+brotli 时 pcap 通道根本不存在）。
3. **任何一步失败返回 `available=False` + 原因，不抛**。`git` 不在 PATH 时评测入口
   不能崩，但也绝不能因此假装有指纹。

自测 `code_fingerprint_selftest()` **4/4**（合成仓库）：干净仓库判真、
**加一个未跟踪文件即变脏**、非 git 目录 `available=False` 且带原因、依赖键完整。
接进 `pipeline_selftest()` J 段，`--selftest` A–J 全段 PASS / RC=0。

preflight 实跑输出（当前工作区）：

```
WARN 代码指纹（commit + 工作区脏度 + 依赖）  commit=2326cb69… branch=feat/…
     dirty=36 python=3.14.6 deps[gmpy2=2.3.2,scapy=2.8.0,brotli=1.2.1,…]
     ；工作区有 36 个未提交改动 ⇒ 本次跑批**不能**等价于 commit 2326cb69
```

标 WARN 而不是 FAIL 的理由：开发中脏树很常见，一票否决会让评测入口不可用；
但它必须可见，并写进 evidence 与 caveat（
`clean_checkout=false 时，本次数值不能等价于该 commit`）。

### 2. `scripts/setup_runtime_env.sh`：让「跑批环境」可复现

手工敲 `pip install` 补回来的环境，换机器就会再缺一遍。脚本做了四件事：

1. **从 `pyproject.toml` 生成依赖清单**（核心 + `dev` + `pcap`），不写死 ——
   写死的清单必然与 pyproject 漂移，而漂移的后果就是「按文档装完还是缺包」。
2. **真比 `requires-python`**。第一版在服务器上直接 FAIL 了：
   `FATAL: 解释器 3.12.3 低于 pyproject requires-python=>=3.13` ——
   因为服务器副本还带着旧的 pyproject。这正好证明 fail-closed 有效
   （同步 pyproject 后通过）。
3. **PEP 668 自动降级**：`externally-managed-environment` → `--user
   --break-system-packages`（只写 `~/.local`，不碰 `/usr/lib/python3/dist-packages`）。
   服务器实测走到了这条分支。
4. **import 级自检**，不信 pip 的 `Successfully installed`：
   逐个 `importlib.import_module` 并打印版本，缺则逐项列出并 exit 1。
   （第一版漏了 `pillow → PIL` 的别名，把「装好了」报成「缺 pillow」——
   假红也是缺陷，已修。）
