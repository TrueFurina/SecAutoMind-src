## 1. 上一轮留下的缺口

上一轮（2026-11-08）结尾写的是：

「注入假 `call_llm`」不算数，原因和 402 假红是同一个：**fixture 里的结果文件形状，

## 2. 做法

新增 `scripts/e2e_llm_contract_test.py`：

- 起一个只绑 `127.0.0.1` 的桩 HTTP 服务，实现 `/v1/chat/completions`；
  `STEP_BASE_URL` 指向它，`STEP_API_KEY` 是进程内临时造的哑值（不是凭证，从不打印）。
- 跑**真实** `ctf_stepfun_orchestrator.py`（`--provider stepfun`，纯 LLM 路径），
  产出真实的 `result.json`；再直接把这份 dict 喂 `check_pure_llm_caliber.judge_run`。
- 五种返回形态，各自对应一个真实故障类别：

| 桩模式 | 模拟 | 正确归属 |
|---|---|---|
| `solved` | 正常答对 | `LLM_SOLVED` |
| `wrong` | 正常答错 | `CLEAN_FAIL` |
| `envelope` | HTTP 200 + 无 `choices` 的错误信封 | `NOT_ATTRIBUTABLE` |
| `http402` | HTTP 402 余额不足（上一轮真跑批撞到的） | `NOT_ATTRIBUTABLE` |
| `http401` | HTTP 401 鉴权失败，**文本不含旧关键字表的任何词** | `NOT_ATTRIBUTABLE` |

- 9 条断言分三面：字段面（生产者必须落 `llm_rounds` / `finish_reason=error` /
  `all_rounds_api_failed` / 非空 `error`）、判分面（三种归属各落对桶）、批次面
  （3/5 失败 ⇒ 分母缩到 2、rate=0.5、`notes` 自报；全失败 ⇒ `claimable=False`、无读数）。
- 3 组变异，各自问一个不同的问题（见 §3）。

接线：作为**第 13 条**入口接进 `verify_capability_evidence.EXTERNAL_GATES`，
而该门禁由 `capability_caliber_test.py` 第 4 段调用、后者已进 `ci.yml`（第 1140 行）。
所以「写了没锁进 CI」这条纪律是满足的，不是本机跑过就算数。

## 3. 三个自踩坑（都比「测试没过」更有信息量）

### 3.1 间歇性 7/9：`latency` 两位小数 × `_effective()` 的 `secs > 0`

第一次跑 9/9，第二次 7/9，连跑 6 次有 5 次红。红的不是调用失败那几题，而是
**正常答错**的 `e2e_wrong` 变成 `NOT_ATTRIBUTABLE("ineffective_run")`。

根因：生产者写 `"latency": round(time.time() - t0, 2)`；本地桩往返 <5ms ⇒ 落成 `0.0`。
消费者 `_effective()` 第一句就是 `if secs <= 0: return False`。于是**一道真答过的题**
被当成空跑，`attributable` 从 2 掉到 1、`rate` 从 0.5 变成 1.0。

这是生产者精度与消费者口径的边界，不是判据写错：真实厂商端点不会 <5ms，
但本地/内嵌模型会。处置：

- 桩侧 `time.sleep(0.02)` 模拟真实网关量级，代码注释里写明**这不是掩盖问题**；
- 新增 `latency_precision_probe()` 在自测输出里把边界原样打出来：
  `api_call_failed(fast)=False / _effective(latency=0.00)=False / _effective(latency=0.01)=True`；
- **不改 `_effective()`**。改判分口径会让历史 verdict 失效，且 `candidate_variants` /
  判分口径在他人 WIP 里，不能单方面动。记为已知限制，留给出于统一口径的那次修改。

修完连跑 6/6 稳定通过。

### 3.2 只抹两处落账信号，分类**没有**变红 —— 这不是失败，是冗余生效

初版 M2 把 `all_rounds_api_failed`、非空 `error`、`llm_rounds` 抹掉，预期分类会崩。
实测分类仍全绿：消费者 `api_call_failed()` 有三条互不依赖的判据
（显式标记 → 轮次明细 → `api_error_first` 文本 + `api_error_rounds`），
而外层 `except` 仍留着 `api_error_first`/`api_error_rounds`，第三条照常命中。

把它从「失败的变异」改记为**负对照**：断言 `producer_ledger_present` /
`producer_marks_api_fail` 必红（字段面会咬），同时断言三条分类断言**必须仍绿**。
这样「冗余真实生效」变成可测量的，而不是一句自评。

### 3.3 只退消费者也不变红：402 文本恰好含旧关键字表的 `quota`

M3 想证明「`api_call_failed()` 那半边修复是承重墙」。第一版只把
`return not api_call_failed(detail)` 换回 `return True`，结果 0 条变红。
`git show 6215f80^` 取到修复前原文才看清：旧 `_effective()` 本来就有关键字表
`("no available channel", "cooldown", "quota", "403", "429")`，而桩返回的 402 是
`exceeded your current quota` —— 旧表照样挡住。

两处修正：

1. M3 逐字还原修复前的**整段** `_effective()`（旧关键字表 + 无条件 `return True`），
   不再只改最后一行；
2. 补 `http401` 形态，错误文本 `authentication required` —— 旧表里没有 `401` /
   `authentication`，新 `api_call_failed()` 靠 `all_rounds_api_failed` 命中。
   加上它以后 M3 才如预期变红（`judge_api_failed_not_clean_fail`、
   `batch_partial_keeps_reduced_denominator`），**消费者那半边是否承重**才被测到。

顺带得到一个更准的结论：402 假红是**生产者与消费者两半边联合造成的**
（生产者 `error=""` 让旧关键字表看不见失败；旧消费者又没有轮次判据）。
单退任一半边，对 402 这个形态都不足以复现。

## 4. 派生路径的 CRLF 盲区（上一轮判据只修了一半）

写 e2e 时发现：主结果 `result.json` 写了 `newline="\n"`，但同一批产出的
`result.json.audit.json` 没写 —— Windows 上一个 LF、一个 CRLF。

```
ctf_stepfun_orchestrator.py:1130  audit_path = args.out + ".audit.json"
ctf_stepfun_orchestrator.py:1131  open(audit_path, "w", encoding="utf-8")        ← 漏
summarize_external_runs.py:231   p = os.path.join(ROOT, args.out)
summarize_external_runs.py:233   open(p, "w", encoding="utf-8").write(text)      ← 漏
```

上一轮加的 `writers_missing_newline()` 用 AST 只看
`open(<某对象>.out, "w")`，**派生变量名一律看不见**。这和第 12 轮「grep 漏掉
`a.out` 形态」是同一族：判据认的是写法，不是「这是不是证据产物」。

- 扩展：先收集「赋值右侧含 `X.out` 的变量名」到 `derived`，再让
  `open(<derived名>, "w")` 与直接 `open(args.out, ...)` 同等受判。
  **没有**扩大成「所有 `open(..., "w")`」—— 临时文件 / config 不是证据，
  全扫会制造噪声，门禁反而会被关掉。
- 自测加 3 条：`derived_bad.py` 必被抓、`derived_good.py` 与非派生路径不误判、
  把派生赋值的 `.out` 去掉即不再命中（反向可证伪）。`12/12`（原 11/11）。
- 两处真实写入点补 `newline="\n"`，门禁 `PASS（0 处）`。
