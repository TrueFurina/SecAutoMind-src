## 3. 三个结论（都可被本文数据直接支撑）

1. **`json_object` 不是病根**。四组里 B 臂从未把失败清零：step-5 v2 的 B 臂仍有 3/16 空回复。
   失败模式统一为 `empty_reply`（`finish_reason=length`、content=0、内容全进 CoT），与开关无关。
2. **修复有效，但只在生产路径上体现**。裸 API 单次：step-5 81.2%；经加倍重发：93.8%；
   step-3.5 单次 93.8% → 100%。因此「按裸 API 成功率评估生产行为」本身就是错的度量。
3. **v1 的两组数字是被污染的**。v1 未传 provider → step-5 那 2 次 `protocol_fail` 实为
   「content 空 → 回退读 CoT → 解析失败」，属测错路径；旧路径还把 CoT 里的 JSON 记成 ok，
   所以 v1 的 100%/100% 与 v2 的 75%/81% 不可混比。**v2 才是生产口径。**

## 5. 不能从本文得出的结论（边界）

- **不产生解出率**：只测 plan 阶段协议层，不是完整 agent 轨迹；解题能力不受此结论约束。
- **n=16 太小**：1 次 = 6.25 pp；8 个提示彼此不独立，Δ 实际由 1–2 个提示驱动。
- **C 臂只 16 次**，不足以定阈值，只能当观测值。
- 旧的 `protocol_fail=248 / empty_reply=131` 仍无原始日志，本文**既不证实也不证伪**。
