# 结果：StepFun `json_object` 协议 A/B + CoT 预算归因（2026-11-04）

> 预注册（口径/判据/阈值/混杂，测前已入库）：`docs/evidence/stepfun_jsonmode_AB_预注册_20261104.md`

**判定（按预注册阈值 ≥20pp）**：`json_object` **未证有效**。

## 2. 探针：`content` 为空的真因是 CoT 吃满输出预算（非“不守 JSON 协议”）

`max_tokens` × `json_object` 四格实测（每次 1 次调用）：

| max_tokens | json_object | finish_reason | content 长度 | reasoning 长度 |
|---|---|---|---|---|
| 64 | 关 | `length` | 0 | 101 |
| 256 | 关 | `length` | 0 | 377 |
| 64 | 开 | `length` | 0 | 102 |
| 256 | 开 | `length` | 0 | 368 |

→ `json_object` 开着也照样截断；**开/关都不是变量，预算才是**。

## 3. 比 A/B 更值得修的发现：引擎把 CoT 当答案（“ok”桶被污染）

A/B 的 32 条里，**B 臂 2/16** 出现了 `content=0`、`completion_tokens=2000`（预算耗尽）：

| 记录 | content | reasoning_content | 引擎判定 |
|---|---|---|---|
| B/crypto_b64 r1 | 0 | 3656 | **ok**（从思维链里搜出 JSON） |
| B/flag_check r1 | 0 | 4217 | **ok**（同上） |

即：`_extract_content` 在 content 空时回退 `reasoning_content`，而 `_extract_json_object` 又能从
散文里搜出 `{...}` —— **截断被伪装成成功，Agent 会拿“思考过程里的半句话”当动作继续跑**。
A 臂同题 0/16 出现该情况（描述性差异，n 小，不作结论）。

## 4. 两个代码级缺陷（已修，见 §5）

1. **字段名不认识**：`_extract_content` 只回退 `reasoning_content`；StepFun 另有 `reasoning` 字段。
   单看这一个字段会漏 → 记成 `empty_reply`；而 API 多数时候两个字段同值 → 又被当成 `ok`。两边都错。
2. **计量不可用**：`reasoning_len=3656` 字符、`completion_tokens=2000`，但
   `completion_tokens_details.reasoning_tokens=0`。**无法从 usage 区分 CoT 与答案**，
   预算/成本审计只能靠字符数猜。与 776a383 修的“双桶重复计数”属同一类口径失真。

## 5. 已做的修复（最小、可回退）

- `_stepfun_cot_truncated()`：仅 stepfun 且 `finish_reason=length` 且 content 空 → 判截断。
- 截断时**最多两次加倍预算重发**（上探 8192），仍失败则保留首响应，不静默。
- stepfun **不再**把 `reasoning/reasoning_content` 当答案（非 stepfun 的 DeepSeek 回退保持不变）。
- 回归：`tests/test_llm_client_contract.py` **11 passed**；新增 4 条用例（CoT 不当答案 / 截断重发 /
  有内容不重发 / 非 stepfun 回退保留）。
- 实机验证：`max_tokens=256` → 日志 `StepFun CoT 耗尽输出预算(256)，加倍到 512 重发` →
  返回非空内容（`OUT_NONE=False`）。
