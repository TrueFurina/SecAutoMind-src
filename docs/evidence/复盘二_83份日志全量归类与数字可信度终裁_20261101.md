## 0. 一句话结论

83 份日志里，**只有 3 个数字可以拿去说话**（L2 的 2/26、mhk2 的 106.4s
零 token、lb12 的 3/12=25%）；**4 个数字是假的**，其中两个假得最狠 ——
`eval_m4.log` 的 14/14=100% 是**联网抄官方 `flag.txt`**，
`eval_m4_airgap.log` 的 12/14=85.7% **根本没断网**（`evalharness` 未接 airgap），

再加一条更要紧的：14:59 有一批**分母完全干净**的 23 题（2/23=8.7%），
它把"解出率"这件事拆开了 —— **L2 零 token 拿 2 题，L3 真烧 21 题拿 0 题**。
纯 LLM 的增量是 0。

### 2.0 第 9 条是目前最好的一条，也是最能回答"解出率多少"的一条

它同时满足三件事，是全部 83 份日志里唯一做到的：**分母无 0 秒污染**、
**每道题的附件都真实存在**、**跳过数为 0**。所以 8.7% 这个数本身是干净的。

但它同时给出一个不留情面的结论：

```
L2（确定性 skill，零 token）： 2/23 = 8.7%
L3（deepseek-reasoner，真烧）：  0/21 = 0%
```

**纯 LLM 在这 21 道 crypto 上的增量是 0。** 早年"17% 解出率"里能站住的部分，
全部来自确定性路由，不是模型能力。这条与 #1（L2 2/26=7.7%）互相印证，
且两次是不同题池、不同时间、不同模型 —— **7.7% / 8.7% 是同一件事的两次测量**。

### 2.1 第 8 条值得单独看：唯一一次「有候选但答错」

```
[ext_gctf2021_abc-arm-and-amd] misc  cand=1 hit=false 130.4s
  candidates: ["CTF{0n3_5h3ll_2_ru13_7h3m_4ll}"]
```

这是全量日志里**唯一一次模型给出了形态完整的候选而判假**的记录，属
`answer_wrong`（能力层），不是 `no_candidate`。它说明模型有"编一个像模像样的
flag"的倾向 —— 与第 3 批 `primes` 自造 `CTF{YkDOLI…}` 同源。判分必须比
sha256，不能看形态。

## 3. 三条硬发现

### 3.1 airgap 机制本身是对的 —— 但历史日志从没证明过它生效

服务器**有网**（实测 `ctf2.dasctf.com` 200、`api.github.com` 200、
`raw.githubusercontent.com` socket 可建连）。这直接推翻了长期假设"服务器对外网本来就不通"。

因此必须用 **IP 直连**绕开 DNS 来区分"被 seccomp 拦"与"没路由"。
`cmd/airgaptest` 做 A/B 对照，同一台机、同一时刻：

```
A. 不带 CTF_AIRGAP：
   AF_INET  CONNECTED-NOT-BLOCKED      ← 1.1.1.1:80 真连通
   AF_INET6 OSError 101 Network is unreachable
   AF_UNIX  OK / AF_INET-UDP OK

B. CTF_AIRGAP=1：
   AF_INET      PermissionError 1 Operation not permitted   ← 拦住了
   AF_INET6     PermissionError 1 Operation not permitted
   AF_INET-UDP  PermissionError 1 Operation not permitted   ← DNS 一并堵死
   AF_UNIX      OK                                          ← 不误伤本地 IPC
```

**结论**：机制可信、fail-closed、不误伤。但**历史日志无一提供 IP 直连证据** ——
`l3_airgap_6.log` 里模型只试了域名，拿到的是 DNS 失败，和"这台机器没配 DNS"
完全同形。这条正是 MEMORY 里记的教训"金丝雀别拿域名当靶子"的第二次复发。

⇒ 今后任何"断网跑批"，**必须在日志里留下 IP 直连被 EPERM 的证据**，
否则该批成绩按"未隔离"处理。建议把 `cmd/airgaptest` 收为跑批前置自检
（类比 `--selftest`）。

### 3.2 `eval_m4_airgap.log` 名字骗人，「断网基线」需要重测

- `cmd/evalharness/main.go` 里 `grep airgap` → **0 处**。只有 `cmd/llmbench/main.go`
  接了（`airgap.RegisterMain` / `MaybeRunChild` / 启动打印 `airgap=`）。
- 该日志 r7 用 `urllib` 从 `raw.githubusercontent.com` **成功下载了 14848 字节的
  `chall`**（返回里出现 `b'\x7fELF\x02\x01\x01\x00…'`），r8 `file chall`、
  r9 `objdump -d`、r11 `objdump -s -j .rodata` 拿到 `33313331 00733474 336c6c31`
  （即 `3131` / `s4t3ll1…`），r12 拼出完整 flag 喂给 `./chall` 得 `Access Granted`。

**这里的定性要分清两件事**（不能因为"联网"就把能力一起否定）：

| 维度 | 判定 |
|---|---|
| 隔离性 | ❌ 没断网，`airgap` 名不副实 |
| 输入来源 | ❌ 附件本身坏了（见 §4），模型只能上网找官方 binary |
| 解题过程 | ✅ **真逆向**：反汇编 → 读 `.rodata` → 拼碎片 → 本地执行验证 |
| 该数字能否报 | ❌ 不能。它测的是"给网 + 会逆向"，不是"断网能力" |

### 3.3 `range_all13` 的 13/13 是教学靶场

题源目录 `/tmp/lbw/2001..2013`，题面自述：

```
# 2001
平台已分配靶机。访问靶机首页并查看页面源码，flag 藏在源码注释里。
靶机地址: http://127.0.0.1:19001  [非本服务端口]
```

flag 是 `flag{live_source_leak_ok}` / `flag{live_sqli_auth_ok}` / `flag{live_lfi_ok}`
—— 自造值。13 题平均 17s。这类跑批的价值是**验证链路通**（L3 工具环、
python_session、requests 全链路可用），**零能力意义**。与 `real_benchmark`
里"11 题题面直给 flag"同性质，不得进分母。

## 4. 附件链路：24.1% 成功率，是"模型被迫上网"的直接原因

`scripts/audit_read_attachment.py` 扫 7 份主日志：

```
总调用 54 次 | 成功 13 | 失败 41 | 成功率 24.1%
   19  HTTP 403                        ← GitHub API 限流
   14  scheme 不被支持（本地路径/file://）  ← 纯工具缺陷
    4  HTTP 404（dasctf token 失效）
    2  raw.githubusercontent 失败
    2  TLS handshake timeout
```

两条都可修，且收益明确：

1. **14 次是"不吃本地路径"** —— `range_all13`/`jy_kpi40` 里每题都先失败一次
   （`unsupported protocol scheme ""`，再 `"file"`），然后模型改用
   `python_session open()` 兜底。**每道题白烧 1~2 轮**。改法：入口处判断
   `os.Stat` 成功即直接读盘，不进 HTTP 分支。
2. **19 次 HTTP 403** 说明模型默认去 GitHub 找输入。这不是"模型爱联网"，
   是**输入没送到手上**。修好 1 之后这条自然下降。

⇒ 附件的正确修复优先级 **高于**任何模型侧调优：它同时影响"能力测量干净度"
和"每题轮次成本"。

## 8. 边界声明

- 本文**不判定**除 §2 表格外的任何数字。`armA~armJ` 十个实验臂的语义已无法从
  日志复原（多数只有 1 题、`model=` 为空），按"不可用"处理，不做猜测。

  也靠联网拿输入，未逐题验证 —— 因此不能反过来断言"14 题全是抄的"。
- 断网能力的真实值**目前未知**：§2 第 2 条被打折后，手上没有任何一条可自证的
  断网成绩。§2 第 9 条虽然有干净分母，但它的 json 里没有 `airgap` 字段、
  也没有 IP 直连被 EPERM 的记录，按 §3.1 的规则只能记"未隔离"。重测
  （§6 第 4 条）之前，对外只能说"尚无自证的断网能力数据"。
- §2 第 9 条引自并行会话 14:59 的产出 `ext_crypto25_airgap.json`，本文只读取
  不改动该文件；其 `airgap` 证据缺失一事已在上表标注，是否补测由该批次负责人决定。
