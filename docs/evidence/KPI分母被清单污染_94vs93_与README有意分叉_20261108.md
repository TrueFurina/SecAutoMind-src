## 二、`real_corpus` 为什么是 94 而不是 93

旧实现只有一行：

```python
return sum(1 for p in QUESTIONS_REAL.rglob("*.json") if p.is_file())
```

`rglob("*.json")` 把附件目录里的**清单**也算成一道题：

```
data/questions_real/_attachments/_hygiene_manifest.json   ← JSON 数组，非题目
data/questions_real/**/*.json                              ← 93 道真题
```

实测：`rglob` 命中 94 个 json，其中**只有 1 个不是题目对象**（`not-object:list`）。

### 为什么这不是「差一个数」

1. **方向反了**：`README.zh.md` 写的是 93（正确），闸门按 94 判它「漂移」。
   一条正确的文档被判红，接下来最自然的动作就是**把正确的 93 改成错误的 94**。
2. **分母进了比率**：`coverage_of_corpus = offline_verified / real_corpus = 14/94 = 14.9%`，
   而真实是 `14/93 = 15.05%`（README 自己写的「约 15.1%」）。分母被污染的比率，
   和「伪造分数」只差一个自觉。
3. **同一份清单，两个门禁各错一个方向**：
   - `_kpi_canonical.count_real_corpus()` → 多数了它（94）
   - `_audit_corpus_integrity.audit()` → 对它调 `.get()` 崩掉 → 上游吞成「池不在快照里」
     → 报 **「questions_real: 池消失（曾有 93 题）」**（2026-11-08 上一轮已修）
   一处清单文件，一边伪造「数据丢失」，一边伪造「分母更大」。

### 旁证

`ctf_agent/deliverables/能力缺口诊断/ITEM4_CAPABILITY_GAP_DIAGNOSIS.md:134`（2026-09 的历史快照）写的是
`offline_verified=14 · real_corpus=93 · skills=78`。**93 在 9 月是对的**；93→94 是清单被放进
`_attachments/` 之后发生的，期间没有新增真题。

### 修法

只认「能不能当题目对象」：

```python
def _counts_toward_corpus(p): 
    try: payload = json.load(...)
    except (OSError, ValueError): return True   # 读不出 → **保留计数**
    return isinstance(payload, dict)
```

两处刻意的取舍：

- **不按目录名白名单**（不排 `_` 前缀目录）：否则将来真放进 `_` 目录的题会被悄悄漏掉。
- **解析失败仍计数**：分母变小会**直接抬高**覆盖率，是危险方向；损坏由题库健康门禁去报。

变异实测：把 `return isinstance(...)` 改回 `return True` ⇒ 2 条红
（新用例 `assert 4 == 3`，以及 `test_readme_counts_green_on_live_repo` 重新报 README 漂移）。

## 三、`README.md` 是有意分叉，不是项目 README

`MIGRATION_DELTA_20261024.md` 第 14 行早就写清了：

> 有意分叉 | 1 | `README.md`：本融合副本已改写为《CTF-Agent 融合留存说明》（副本自己的门面文档），
> 非过期拷贝。**两边各自保留**，不回灌、不覆盖

但**没有一条门禁知道这件事**。于是 6 条门禁拿这份 2KB 的留存说明当项目 README 判：

| 门禁 | 误报措辞 | 真实原因 |
|---|---|---|
| `test_no_dead_path_references[README.md]` | 「只解析到 6 个 token（应 >=10）——**解析器可能失效**」 | 解析器没问题，文件本来就只有 6 个 token |
| `test_readme_counts_green_on_live_repo` | 「README.md: 计数声明**缺失**」×5 | 留存说明不承载 KPI 声明 |
| `test_readme_heldout_green_on_live_repo` | 「held-out 声明**缺失**」×2 | 同上 |
| `test_live_repo_kpi_declarations_consistent` | 「公开声明文件必须保留 `offline_verified` 声明行」 | 同上 |
| `test_mutation_adding_exclude_dir_flips_readme_to_red` | 「基线应先是绿的」 | 变异基线选错了文件（应选文档正本） |
| `test_live_repo_breakice_*` ×2 | `StopIteration` | 段落不在本副本（见第四节） |

### 修法：把豁免绑在「自证」上，不绑文件名

```python
_FORK_NOTE_MARK = "融合留存说明"

def front_doc_is_fork_note(path) -> bool:
    """首个一级标题含「融合留存说明」即认定为本副本的留存说明。"""
```

于是豁免**自带失效条件**：有人把真 README 放回来 → 标题一改 → 豁免消失 →
所有校验立刻恢复 `mandatory` 并重新报「声明缺失」。

变异实测（把 `# CTF-Agent 融合留存说明` 改成 `# CTF-Agent (project README)`）：
**7 条红**，横跨 3 个测试文件 —— 证明这是有条件豁免，不是永久免检：

```
test_kpi_canonical::test_readme_counts_green_on_live_repo
test_kpi_canonical::test_readme_heldout_green_on_live_repo
test_kpi_canonical::test_forked_front_readme_is_declared
test_readme_path_integrity::test_no_dead_path_references[README.md]
test_readme_path_integrity::test_mutation_adding_exclude_dir_flips_readme_to_red
test_doc_consistency::test_live_repo_kpi_declarations_consistent

```

配套：`test_fork_exemption_disappears_without_self_declaration` 用合成目录做正反两向
（两份普通 README ⇒ 10 条缺失；只把一份改成留存说明 ⇒ 恰好剩 5 条，且全部落在另一份上）。

### 顺带补上的两处文档真话

- `README.md` 加了一行指路：**门面文档是 `README.zh.md`**（此前它一个指向都没有——
  读者打开它就是「融合留存说明」，找不到项目说明）。

  改成：「属**本地副本**内容，不在版本库内（克隆后不会有）」。这样它与
  ALLOWLIST 里「在陈述我们不收录」的定义才一致。

## 四、break-ice 段落：不在这个副本里，是边界不是故障

英文 break-ice 实验段落（`11/15` / `8/15` + 「Denominator caveat (do not conflate)」）
只在源仓库 `README.md` 里；融合副本的 `README.md` 被改成留存说明，`README.zh.md` 从未收录。
所以副本内**没有对象可守**。

原实现 `next(...)` 找不到标题直接抛 `StopIteration`——一条看不出所以然的红，
把「副本边界」报成了「代码坏了」。

修法：`_breakice_doc_text()` 找不到就 `pytest.skip`，**skip 原因写明正本在哪**；
另加 `test_breakice_absence_is_deliberate` 把边界钉成可执行事实，堵半截恢复：

- 副本 `README.md` 必须自证是留存说明（否则前提没了，必须重判）；
- 两份 README 都**不得**出现 `11/15` / `8/15` —— **半截恢复最危险**：
  数字贴回来了、限定语没跟回来，读者立刻又把两个 `15` 当同一分母。

## 五、剩余 15 条红：全部是「本机缺包」，没有一条在代码里

| 族 | 条数 | 原因 |
|---|---|---|
| 缺 `gmpy2`（**硬依赖**） | 12 | `test_deterministic_chains` 4 / `test_rsa_high_even_p_known` 4 / `test_rsa_fallback` 2 / `test_ezrsa_route_fix` 1 / `test_pem_small_e_wrap_fallback` 1 |
| 缺 `scapy`（可选 extra `pcap`） | 3 | `test_pcap_probe` 3——用它**现场生成 pcap 夹具**，属测试夹具依赖 |

**本机装不上**（已实测，不是没试）：`pip install gmpy2` → `from versions: none`；
`pip install scapy` → 同样 `none`。即 pip 在本机**拿不到索引**（镜像页面 curl 可访问、
pip 无响应），不是版本不匹配。另：本机 Python **3.14.6**，而 `pyproject.toml` 声明
`requires-python = ">=3.13"`——硬依赖 `gmpy2` 的稳定版 wheel 覆盖到 cp313，
cp314 只有 2.3.x/2.4.0a1 起才有，这条**依赖集在 3.14 上的可满足性**值得赛前单独验一次。

> 🔴 **上面这段（"装不上" + "cp314 无 wheel"）两个结论都已被推翻，保留原文作对照。**
> 真因是**清华镜像按 User-Agent 拦 pip 26**：同一 URL `curl` 200、`urllib` 200、
> `pip/24.3.1` 200，而 pip 26 真实 UA 稳定 **403**（3/3）。`pip -vvv` 才看得到
> `403`，而 pip 把 403 降级成 `from versions: none` —— **报错文本里连状态码都没有**。
> 换腾讯云镜像后 `gmpy2-2.3.2-cp314-cp314-win_amd64.whl` 与 `scapy-2.8.0` 秒装，
> 本机门禁随 22 → 0。详见
> `docs/evidence/跑批副本落后37commit_与依赖从未装齐_20261108.md` §二。
> 另注：`requires-python` 已从 `>=3.13` 放宽到 `>=3.12`（依据见同文 §四.3），
> 因为唯一实际跑题的环境是服务器 3.12.13。

服务器实测 `gmpy2=True`，故既有跑批数字不受影响。

## 六、缺依赖静默降级：把「能力不存在」说成「解不出」

`skills/rsa_fermat_factor.py` 缺 gmpy2 时：

```python
if not HAS_DEPS:
    return None          # ← 与「试过了，没解出」完全同形
```

调用方是谁：`core/presolve.py` 的 L2 RSA 确定性通道、`agents/crypto_toolkit.py` 十余处
fallback。它们全都拿 `None` 当「没解出」，于是**赛时表现为模型 RSA 不行，账记在模型能力上**，
真因是能力根本没装上。

实测对照：**同一份代码**，本机 12 条 RSA 用例红、服务器全绿，差的只有环境。

修法：缺依赖时 `logging.warning` 一次（每进程一次，不刷屏），措辞点名
「**不是「解不出」，是能力不存在**」。新增 `tests/test_rsa_dep_guard.py` 守两条：
告警必须出现且只出现一次；`HAS_DEPS` 必须与 gmpy2 真实可导入性一致
（防有人为变绿把标志写死 `True`）。
