## 🔴 第 3 项：唯一真回归（已在本会话后续收口）

**链路**：`ci.yml:957-960` 的 `flag-extract-contract-gate` 第一步就是
`python scripts/check_flag_extract_contract.py --check`（不是只有 `--selftest`）。

**现象**：`scripts/secret_guard_flag_test.py:537` 被判
「内长 `{4,200}` ≠ `{1,200}`；字符类不是 `[^{}\n]`」，
门禁措辞为「清除侧比判分侧窄 = 0 命中只证明没有长 flag」。

**根因（逐提交核对）**：
- `fa2fb6c`（绿 CI 的提交）里该文件**没有**这行宽口径正则；
- 本地待推提交 **`8a36311`「外形判据的盲区先量后写：不放开也不收紧，两端钉成测试」**
  新增了 `wide = _re.compile(r"([A-Za-z0-9_]{2,})\{[^}\n\"]{4,200}\}")`；
- `3c7d745` 随后只改了同文件的解码方式（latin-1 逐字节），未动该正则；
- 门禁 `scan_regex_copies()` 用 `rglob("*.py")` 扫 `scripts/` 与 `data/`，
  **不区分测试文件**，于是把测试内部的「宽口径捞候选」正则当成了清除侧拷贝。
- 门禁判据本身在 `fa2fb6c` 与 HEAD **逐字未变** ⇒ 是新代码触发，不是门禁退化。

**性质判断（不要误修）**：该正则所在行上一行注释写明
「宽口径候选（只为把可能是答案的东西捞全，判『是不是真答案』仍走题库哈希）」。
它是**测试专用检测口径**，不是脱敏/清除侧实现；`ACCEPTED_VARIANTS` 目前只给
`scripts/secret_guard.py` 备案豁免（理由：检测型窄口径是有意的噪声防线）。
所以门禁报红的语义（清除侧窄 → 再泄一次）在此**不适用**，属扫描集过宽导致的误报。

**当时的边界判断**：这行是并行会话有意写的代码，且落在在途判据线上；
按文件边界红线不代改。当时列出两个候选方向（**均未采用**，理由见下节收口记录）：
1. **门禁侧**：把「测试文件的候选正则」与「清除侧拷贝」分开（例如按
   `_test.py` 或按上下文语义分流），并补变异用例证明「清除侧真窄仍必红」；
2. **测试侧**：把该行改成与判分口径一致的 `{1,200}` + `[^{}\n]`，
   但会改变 `8a36311` 有意设计的宽口径，须由该线作者确认。

⚠️ 本轮实验曾尝试方案 2，因 heredoc 里 `\n` 被解释成真实换行而写出坏文件，
出现过一次「门禁绿但 `py_compile` 语法错」的**假绿**；已全部恢复并复核主工作树干净
（`git status --short scripts/secret_guard_flag_test.py` 为空）。
教训再次印证：只信「语法编译 + 门禁 + 测试自身」三者同时绿，不接受单项绿。
