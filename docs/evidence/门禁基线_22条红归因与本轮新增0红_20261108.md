## 三、本轮修掉的那条假红：一条清单文件伪造了一场数据丢失

链条四步（每步都可复现）：

1. `data/questions_real/_attachments/_hygiene_manifest.json` 是一个 **JSON 数组**
   （清单，不是题目），自 `c7289ec`（11-02）起入库。
2. `_audit_corpus_integrity.audit()` 对池内所有 `*.json` 取 `json.loads` 后直接
   `audit_question(q, ...)`，对 list 调 `.get()` → `AttributeError`，**整池审计崩溃**。
3. `check_corpus_health.snapshot()` 的 `except Exception: continue` 把崩溃吞成
   「该池不在快照里」。
4. `compare()` 看到「基线有、当前没有」，报
   **`questions_real: 池消失（曾有 93 题）`** → 阻断回归 → 聚合门禁红。

一处脚本 bug 长成了「93 道真题没了」的告警。**反过来更危险**：真丢题时，
它和「脚本又崩了吧」同形，会被放过。

修法（两层，缺一不可）：
- `_audit_corpus_integrity`：`_` 前缀**支持目录**里的非对象 JSON 不计数
  （清单不是题目）；池根部出现非对象 JSON 则记 `not_question_object` 为 broken（可见）。
  ⚠️ 只跳过「非对象 + 在支持目录」两个条件同时成立的文件 —— 实测把整个 `_` 目录
  排掉会让 `questions_external` 42→39、`questions_ext` 37→34，凭空多出两条「池缩水」。
- `check_corpus_health`：`snapshot(errors)` 出参记录崩溃，`apply_audit_errors()`
  把「池消失」改写成「审计崩溃」，**仍然阻断**（fail-closed）。

验证：
- `scripts/check_corpus_health_test.py` 扩到 **8/8**（新增 4 条：崩溃≠池消失、崩溃仍阻断、
  无崩溃不多报、审计器容忍 list 清单）。
- 变异实测两条都会变红：去掉「池消失」过滤 → `audit_error_not_loss` FAIL；
  让非对象文件重新崩 → `audit_tolerates_list_manifest` FAIL。
- 修后各池计数与基线**逐项相等**：`questions_real 93/9/2/82`、`questions_external 42/39/0/3`、
  `questions_ext 37/33/1/3`、`questions_ext_cybench 11/11/0/0`（原 10、改善 1）、
  `questions_ext_A 11/11/0/0`、`trial5 0/0/0/0`。→ `check_corpus_health.py` rc=0「无回归」。
