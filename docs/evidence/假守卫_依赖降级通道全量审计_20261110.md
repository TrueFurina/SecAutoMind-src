# 假守卫：依赖降级通道全量审计与收口（2026-11-10）

**一句话结论**：`skills/misc_grid_resample.py` 的依赖守卫**从来没生效过**——守卫、
标志、错误分支都写在代码里，但缺依赖时模块在导入阶段就崩，有依赖时标志恒为
`True`，`if not HAS_DEPS` 是永不可达的死分支。同一份 AST 审计还查出
`core/presolve.py` 有 9 处「导入失败即 `return None`」只留 debug 日志（1 处连日志
都没有）。两处都把「能力根本没装上」记成了「模型没解出」。本轮全部收口，并加了一道
能在干净检出上自动判红的门禁。

## 2. F1：守卫不可达的完整机制

`CTF-Agent_融合/ctf_agent/skills/misc_grid_resample.py`（修复前）：

```python
21  import numpy as np          # ← 模块级硬导入，不在 try 内
22  from PIL import Image       # ← 同上
24  try:
25      import numpy as _np     # ← 重复 import 一次，只为设标志
26      import PIL as _pil
27      HAS_DEPS = True
28  except Exception:
29      HAS_DEPS = False
...
201 if not HAS_DEPS:
202     return {"ok": False, "error": "缺少 numpy/PIL 依赖"}
```

两种环境下守卫都不工作：

- **缺 numpy / Pillow**：第 21 行就抛 `ImportError`，模块根本加载不了，第 29 行的
  `HAS_DEPS = False` 永远执行不到；
- **依赖齐全**：第 25-26 行必成功，`HAS_DEPS` 恒 `True`，第 201 行是死分支。

调用链实证：`core/presolve.py:296` 把 `skills.misc_grid_resample` 列入 L2 预扫模块表，
`core/presolve.py:1634-1638`（修复前）包着 `from ... import run`，失败时只写一条
`logger.debug("[presolve:grid_resample] 导入失败: %s", exc)` 然后 `return None`。
`None` 在本项目的语义是「试过了，没解出」。于是环境缺依赖时，赛时表现是「网格重采样
这题解不出」，账记在模型能力上，真因是 Pillow 没装。

> 危险点在于**看起来有守卫**。用 `monkeypatch.setattr(skill, "HAS_DEPS", False)` 写的
> 测试会全绿（和 `test_rsa_dep_guard.py` 一样），但它验证的是「标志被人为置 False 后
> 的行为」，不是「真实缺依赖时模块还能不能被导入」。这是本项目反复出现的
> **判据测文字不测行为**的又一种形态。

**修复**：numpy / Pillow 全部移进 `try`（成功设 `HAS_DEPS=True` 并记 `_DEP_ERR`，失败设
`False`）；`run()` 缺依赖时发一次 `logging.warning`，措辞明确点出「不是「解不出」，是
能力不存在」；返回值保持 `ok=False` / 原 `error` 文案不变，另加
`reason="dependency_missing"` 供调用方在机器层面区分。现有调用方只读 `ok` / `flag`
（`presolve.py:1653`），**判分口径零改动**。

## 3. F2：presolve 的 9 处静默导入失败

## 4. 审计口径与覆盖

判据全部走 `ast.parse`，不看正则、不数关键词：扫描集 = 活跃副本
`CTF-Agent_融合/ctf_agent/skills/*.py`（**86 个文件**），其中 2 个声明了 `HAS_DEPS`
守卫（`misc_grid_resample`、`rsa_fermat_factor`）。`presolve.py` 里含 `skills.*` 导入的
`try` 共 38 个，按「纯导入探测 + 失败即 `return None`」精确定义后 **22 条**纳入 C2。

**判据作用域 = 模块级静态 import 语句**。活跃 skills 里另有 3 个文件使用动态导入
（`pwn_exploit_flow.py` / `web_multi_step_chain.py` / `web_xxe_file_read.py`），它们
没有声明 `HAS_DEPS`，本门禁**不对它们声称覆盖**；若将来有人给这类模块加守卫，
C1 的第二条（「try 内必须至少有一个第三方 import」）会 fail-closed 判红，不会假绿。

## 6. 门禁判据与变异自测

| 判据 | 守什么 | 防绕过形态 |
|---|---|---|
| C0 | 声明 `HAS_DEPS` 的模块，`run()` 内必须真有 `if not HAS_DEPS` 分支 | 注释里写守卫不算（M3） |
| C1 | 这类模块的模块级**第三方裸导入集合必须为空**；且 try 内至少有一个第三方 import | 把 import 挪出 try（M1）、守卫架空（M2） |
| C2 | 纯导入探测且失败即 `return None` 的分支，必须调 `_warn_import_once` 且第一参数点名模块 | 换回 debug（M4）、点名不带前缀（M5）、调用塞进注释（M6） |
| C1/C2-COVERAGE | 守卫模块 ≥ 2、C2 分支 ≥ 18（实测 22） | 扫描集或导入结构整体塌陷（M7） |

`--selftest` 共 **11 项全 PASS**：B0/B1 基线绿、B2 覆盖数达标，M1~M7 七种变异全部
判红，M8 确认塌陷后覆盖数归零。基线本身也先证明「判据能变红」，再允许用它判仓库绿。

**红测（不是合成变体，是真实历史版本）**：对 `git show HEAD^` 的修复前源码跑同一套
判据函数，结果为 C1 判红（`模块级裸导入第三方 ['PIL', 'numpy']`）**+ 9 条 C2 判红**
（行号与上表逐一对应）。修复后同一判据全绿：**86 skills / 2 守卫模块 / 22 纯导入
分支 / 下限 18**。

**行为级红测**：把 skill 源码还原成修复前形态喂给子进程探针（同样屏蔽 numpy/PIL），
探针 `rc=1`、末行 `ImportError: blocked by dep-guard probe: numpy`，证明新增单测
不是一道永远绿的摆设。

## 9. 复用纪律（本轮再次验证）

1. **每加一条判据，必须测至少一种「形态等价但排布不同」的绕过**：本轮 M3（注释伪造
   守卫）、M6（注释里的告警调用）专门针对此前多次踩到的「正则被注释骗」。
2. **度量工具先校准再下结论**：初版单测按 `stderr.count("能力不存在")` 判「告警一次」，
   而文案里这个词出现两次 ⇒ 假红。改成数「非空告警行数」才对。
3. **改 CI 必须同步门禁地图**：`docs/GATES.md` 的 C6 立刻变红，跑
   `gen_gates_map.py --write` 后全绿。
4. **Windows 建 worktree 用极短路径**：长附件名会触发 `Filename too long` 并让
   index reset 失败，报错看起来像 git 损坏，其实是路径长度。
5. **CRLF 工作树与 LF blob 必须分开谈**：按字节做批量替换时先确认行尾，写回保持
   原有 CRLF；终验一律在纯 LF 提交态做。
