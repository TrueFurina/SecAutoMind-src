## 一、契约四件套（T0 抽样实测）

**测法**：`python -X utf8 scripts/audit_tool_contracts.py --t0`
——静态扫 Go 注册块（含 `Name: builtin.ToolX` 常量形式），按四维判定。
**口径**：静态粗检，report-only；命中 ≠ 运行时缺陷，未命中 ≠ 合格（见文末"已知误判面"）。

实测（2026-10-20，扫到 47 个注册块，T0 清单 22 个全部命中）：

| 维度 | 现状 | 判定 |
|---|---|---|
| ① 入参 schema | T0 22/22 均有 `InputSchema`；4 个未声明 `required` | **已复核**：4 个均属"故意不声明"，登记在 `NO_REQUIRED_EXEMPT`（见表下） |
| ② 错误投影 | **12 个 T0 工具**在结果文本里拼 `err.Error()`（如 `complete_asset_scan`、`update_asset`、`upsert_project_fact`） | ⚠️ 真实缺口 |
| ③ 响应预算 | 3 个 T0 列表类工具（`list_knowledge_risk_types`、`search_knowledge_base`、`webshell_file_list`）未见显式 `limit` 参数 | ⚠️ 需复核 |
| ④ 溯源 | 写操作返回 id/主键；读操作多数只回文本 | 部分（无统一 evidence 字段） |

**`required` 豁免登记**（大门禁分档，2026-10-20 修正）：

| 工具 | 为什么不声明 | 复核 |
|---|---|---|
| `create_asset` | host/ip/domain 三选一**无法**用 JSON Schema 表达（Bedrock 拒绝顶层 oneOf/allOf/anyOf，源码注释自陈），由 `assetFromCreateArgs` 代码强制 | 2026-10-20 |
| `list_project_facts` | 全可选筛选 + 分页，无参即列出当前项目全部 | 2026-10-20 |
| `list_vulnerabilities` | 全可选筛选（scope/severity…），无参按对话绑定项目默认范围返回 | 2026-10-20 |
| `query_assets` | 分页查询，条件全可选，默认每页 20 条 | 2026-10-20 |

门禁初版把「T0 缺 required」当无条件硬缺陷，一跑就把这 4 个判红（exit 1）。
**修法不是删掉判据**：删了它就再也发现不了"有必填却没声明"。现分两档——
缺 `InputSchema` 无条件阻断；缺 `required` 只有**未登记理由**的才阻断，且自测
`test_gate_blocks_unregistered_no_required` 钉住这档不能失效。

### ② 为什么"错误投影"排第一

模型看到的不是 HTTP 状态码，是**工具返回的文本**。`textResult("错误: "+err.Error(), true)`
把驱动层的 `database is locked` / 表名 / 路径原样喂给模型，模型会把它当成"事实"
继续推理（甚至写进报告），而用户看到的是一段"内部细节"。

已有同类先例：`api/auth.py` 的注册错误文案分类（芒得很职 M01 / REA #12）。
工具层应当同构：**对外文案白名单 + 内部原文只进日志**。

### 修法（不要求一次改 12 个）

1. 新增 `toolError(scene string, err error) *mcp.ToolResult`：对外只出 `scene`
   （"资产不存在或无权回写"这类可行动文案），原文进 `log.Printf`；
2. 逐个替换 `textResult("错误: "+err.Error(), true)`；
3. 加静态守卫（正则扫 `textResult\([^)]*err\.Error\(\)`）进 CI，存量登记基线，只拦新增。

> 本次未动手改 Go：① 本机无 Go 工具链，改完无法编译验证（纪律：不写跑不了的代码）；
> ② 12 个工具的错误文案需要业务判断（哪些错误该暴露给模型才能自我纠正）。

## 二、输出层：选定事实视图（REA #204）

REA 原话是"compose the required calls in one execution and **return only selected
facts**... Do not return raw_result, whole Evidence or unrelated inventories"。
翻成本项目的一条规则：

> **工具返回的第一段必须是"这次要的结论"，原始数据附在后面并受预算约束；
> 不返回与本次任务无关的清单。**

落地形态（写进工具实现约定的三条）：

| 规则 | 反例 |
|---|---|
| 列表类一律带 `limit`（默认 20，上限 100），并回 `total` 让模型知道"还有多少没看到" | 返回全库 3000 条资产，模型只用了前 3 条 |
| 大文本（文件内容/扫描日志）先回摘要 + 前 N 行 + `truncated: true` | 整份日志塞进上下文 |
| 只回与请求相关的字段，不回整条 DB 行 | 查一个 id 却返回 20 个字段 |

已具备的正面例子：`get_tool_execution` / `wait_tool_execution` 只回状态与结果摘要，
不回全部中间事件——这是 T0 里输出面最干净的两个。

## 三、T0 工具的任务边界（两行式，REA #202）

每个 T0 工具在 prompt 侧声明两行：**能做什么（只读/只写范围）+ 什么时候停**。

格式（直接抄进工具 description 或 agent prompt）：

```
边界：只读 {范围}；不写库、不发网络请求、不调用其它工具。
停止：拿到 {这 3 个事实} 即停止，不再补充调查。
```

以三个 T0 工具为例：

| 工具 | 边界（第一行） | 停止（第二行） |
|---|---|---|
| `list_vulnerabilities` | 只读当前对话/资产的漏洞记录；不跨项目检索 | 拿到 id+标题+等级即停；需要详情再单独 `get_vulnerability` |
| `search_knowledge_base` | 只读知识库；不写库、不触发 ingest | 命中 3 条以上相关条目即停；无命中即停（不要换 5 组关键词硬凑） |
| `webshell_exec` | 只在已建连的授权靶机上执行单条命令；不批量、不持久化 | 命令回显到手即停；失败重试 ≤1 次 |

**为什么必须写"停止"**：不写停止条件的工具，模型会"过度调查"——同一份事实换 5 个
关键词查 5 遍，token 成本翻倍而结论不变。这也是 T0 分级要解决的问题之一。

## 四、信息不足：`NOT_ENOUGH_INFO` 标记（REA #37）

**规则**：当工具无法给出结论（无数据 / 权限不足 / 上游故障）时，**必须**显式返回
`NOT_ENOUGH_INFO` 及原因分类，不许返回空字符串、"暂无"或编一个看起来合理的结果。

返回约定（JSON 文本，兼容现有 `textResult`）：

```json
{"status": "NOT_ENOUGH_INFO", "reason": "no_data | no_permission | upstream_error | ambiguous_input",
 "what_is_missing": "近 7 天无该资产的扫描记录", "next_action": "先调用 complete_asset_scan"}
```

- `reason` 四类固定：无数据 / 无权限 / 上游错误 / 输入歧义——**不要**新增自由文本分类，
  否则 agent 侧无法分流处置。
- `what_is_missing` 写"缺什么"，不写"失败了"（后者无法行动）。
- agent 侧收到该状态时：**不得**把它当"没问题"继续（这正是 #64「未验的计数器不当零」
  在工具层的同构要求）。

目前状态：`analyze_image`、`get_tool_execution` 等已有明确失败文案，但**没有统一标记**；
统一标记属 P1（需改工具实现 + agent 解析，二者必须同批改，否则标记没人消费）。

## 五、已知误判面（本脚本不保证的部分）

| 情况 | 结果 | 处置 |
|---|---|---|
| `mcp.ToolResult{IsError: true}` 直接构造 | 可能判成"无 isError 路径" | 人工复核；脚本只认 `textResult(..., true)` |
| 动态拼接的 InputSchema | 可能判成"缺 schema" | 人工复核 |
| 描述文本里出现 "limit" 字样 | 可能误判"有限流参数" | 只作粗筛，最终看 schema 字段 |
| 描述里提到 id 但函数体没返回 | 可能误判"有溯源" | 人工复核 |

## 六、工具**配方**侧（`tools/*.yaml`，2026-10-20 补，REA #176）

内置 MCP 工具与 `tools/*.yaml` 里的外部命令行配方是**两条链路**：前者走注册表
（`Name:` 注册块），后者由 exec 层按 `command + parameters` 拼命令行。四件套
**不能照抄**——照抄会造出一个"看起来很严、实际判不到东西"的假门禁。

实测（commit f739406 后，`python -X utf8 scripts/audit_yaml_tool_contracts.py`）：

| 维度 | 口径 | 实测 |
|---|---|---|
| ① 入参轮廓 | parameters 非空 + 每项 type/description | 89 份真声明 / 493 个参数，缺 type 0、缺 description 0 |
| ② 原样透传面 | `additional_args` 直拼命令行末尾 | **80/89（89%）** —— 既定设计，**只计量不阻断** |
| ③ 响应预算 | 配方文件内是否声明上限 | 无字段 → 显式标 out_of_scope（上限在 exec 层） |
| ④ 溯源 | source/trust/license/upstream | `hashpump` 缺 upstream URL（1 项，baseline 登记） |

| 观察项 | 计数 | 说明 |
|---|---|---|
| 全无 `required: true` 的工具 | 13 | arp-scan / bloodhound / checkov / cloudmapper / falco / kube-bench / kube-hunter / linpeas / pacu / prowler / responder / scout-suite / terrascan——多为"零参即可跑"的扫描器，需人工确认是否真无必填 |
| 口径对账 | `count_stats.tools_yaml`=90，本脚本=89，差 1 | 差的那 1 份是 `tools/_shared_args.yaml`（以 YAML anchor 被各工具引用，登记在 `TOOLS_YAML_NOT_A_TOOL_BUT_COUNTED`）；差值无法解释时门禁红 |

**为什么 ② 不进门禁**：89% 命中率的设计缺陷不是缺陷，把它设为硬缺陷只会让首日
全红，结局必然是 `--no-verify`。它的价值在于**落档**：将来讨论"配方参数表到底
约束了什么"时，有一个实测数字而不是印象。

**为什么改判 ②**：MCP 侧"失败是否走 isError"在配方文件里**根本判不到**（错误
投影发生在 exec 层，配方没有错误处理代码）。照抄只会得到"全部未知"。改判可静态
判定的等价风险——参数表被 `additional_args` 一次性作废——才有意义。

## 七、依赖清单盘点（`env_fingerprint.deps_manifest`，REA #239）

一份结果文件的环境指纹原来只记 `_WATCHED_DEPS` 六个固定包。问题：清单里新增一个
会决定结果的依赖，指纹**不会变**——"环境看着齐全、其实漏了关键项"。

改为从仓库清单生长后（`python -X utf8 scripts/env_fingerprint.py --root <仓库>`）：

| 仓库 | 参与依赖集的清单 | 声明/已装 | 有声明无锁定 |
|---|---|---|---|
| SecAutoMind | `requirements.txt` | 9 / 6 | **python**（无 requirements.lock / uv.lock） |
| study-help-pro | `py-server/pyproject.toml` | 32 / 25 | 无（node 有 package-lock，python 有 uv.lock） |
| marl-ecdsa | `requirements.txt` + `requirements.lock.txt` | 11 / 14 | 无（双清单齐全） |

口径选择（写在代码注释里，便于复核改判）：
- 只认 depth ≤ 1 的清单进依赖集；更深的（`Security-Agent_融合/submission/…`、
  `deploy/career-pilot/backend/requirements.txt`）属归档/子项目，**盘点里可见但不并入**；
- 解析不了 pyproject 时**给理由**（`unparsed_manifests`），不返回空集冒充"没依赖"。

**结论引用纪律**：本文件的数字可用于内部整改排序；**不得**用于对外宣称
"52 工具契约完备度 X%"——抽样口径是静态粗检，不是 conformance 通过率。
