**为什么这是最致命的一条**（不是"技术债"，是定位问题）：
HITL（Human-in-the-Loop 人工审查）是本项目对外宣称的核心安全卖点之一 —— "人机可控"。现在的行为是：**数据库写入失败时，UI 仍会返回「已批准 / 已驳回」成功**。于是产生一个无法回答的评委提问：

> 「你怎么证明每一次人工拦截都真的落库了、可审计？」

答不上来。**安全产品的价值不在"能不能拦"，在"能不能证明拦过"。** 这条修起来是 5 行的事（把 `_, _ =` 换成 `if _, err := ...; err != nil { return err }`），但它决定一个 5 分钟的答辩环节是加分还是翻车。

其余同类吞错（次要）：`internal/database/rbac.go:211-212`（建索引）、`database.go:1076`、`workflow_package.go:63,127`、`hitl_logs.go:41`。

## 三、观感问题（DeSIDERATA — 白送的分不要）

### 🟡 P1｜gofmt 卫生（数字有虚高，需修正口径）

`gofmt -l internal cmd` 报 **283 个文件**未格式化，cover `agent/`、`c2/`、`config/`、`handler/`、`security/`、`workflow/` 等核心包。

**2026-09-09 修正：这个数字虚高。** 实际执行 `gofmt -w` 后 git 只记录 **52 个文件**有实质变化，其余 229 个是 **CRLF/LF 行尾符误报** —— 本环境（Git Bash + `core.autocrlf`）下 `gofmt` 期望 LF 而工作树文件是 CRLF，`gofmt -l` 会把纯行尾差异也算作"未格式化"，但 git 提交时行尾被规范化吸收、不产生 diff。

> **可复用经验**：在 Windows + autocrlf 环境里，`gofmt -l` 的文件数不能直接当"待整改文件数"写进材料，必须用 `gofmt -w` 后 `git diff --stat` 才知道真实规模。本报告初版写的"41% 文件未格式化"夸大了约 5 倍。

不改不影响运行，评委也不会编译失败 —— 但评委**会打开 IDE**，看得到实打实的格式问题。修复成本是一条命令：`gofmt -w internal cmd`。

### 🟡 P1｜`openapi_paths.go` 5208 行单函数（已核实为真）

`internal/handler/openapi_paths.go:5` `func buildOpenAPIPaths(...)` 一路到底 5208 行，内含 288 个 `summary/operationId`。

性质要说公道话：**它是 OpenAPI spec 的 map 字面量，属机械生成内容，与业务逻辑 God file 不同，可以酌情豁免**。但它放在 `internal/handler/` 里当一个函数仍是组织错误 —— 应当外置为 `api/openapi.json` 资源文件，`go:embed` 加载。顺带它大概率也是 gofmt 巨量的贡献者之一。

### 🟡 P2｜技术报告的「第三种数字」

`docs/zh-CN/competition-2026/技术报告_SecAutoMind_202609.md:159` 与 合订本 html:310 写 **"Go 613 文件"** —— 既非旧口径(662)亦非新真值(683)，属于自由漂移。这是最典型的手写数字症状。

## 五、锐评（不客气的那部分）

**1. 你们的铁律是对的，问题是它只活在了 MEMORY.md 里。**
"数字必须来自 count_stats.py" 这条规则写得漂亮，也在 MEMORY.md 里反复强调。但现实是：官网 5 处 140、证据包 8 处旧值、技术报告 613 —— 三份活跃材料，三种数字。**规则写下来不等于规则被执行。** 缺的不是规则，是**一个 `--check` 模式的 CI 钩子**：在 push 时 grep 材料里的数字，与脚本真值比对，不一致直接 fail。这条钩子 20 行代码，能永久解决这一类问题。现在靠人肉记得改，就一定会有下一次。**这也是"架构先行"落到实处的最小单元 —— 用机器保证口径，不靠自觉。**

**2. 「已收官」这个说法，只对了一半。**
MEMORY.md 写着"深度质检收官态：God file 拆完、吞错清零"。实测：God file 没拆完（5208 行，另 11 个文件超 1200 行），吞错没清零（HITL 5 处）。反倒是**没写进总结的**技术债标记、经典吞错模式是真的 0。说明**质检是一次性的自查，不是闭环** —— 查过的就干净，没查到的角落就一直脏。建议把 MEMORY.md 里那句"收官态"改成"已知残留清单"，把 God file 与 HITL 两条明明白白写在上面。**假装收官比没收官危险，因为它会让你停止找。**

**3. 最能区分冠亚军的地方，恰恰是你们现在最松的地方。**
能力侧你们已经拉满了：十三基准、双语言机验、静态 34.5% 天花板且能自证每道 MISS 的成因 —— 这些是硬功夫，评委很难挑。但决赛评审看材料的时间远多于看代码。**一个写着 140 的官网、一个打不开自洽 evidence 表、一个 IDE 里 41% 波浪线的仓库，会在评委心里悄悄把"严谨"这个标签摘掉。而一旦"严谨"被摘掉，前面所有的 34.5% 都会被重新怀疑。**

**4. 密钥那件事的性质，值得说清楚。**
严格按 GitHub 口径，你们是合规的 —— `config.yaml` 确实被 ignore 了，这点做得对。但项目自己的定位是"安全作品"，一个声称做安全的产品，**自己的打码门禁因为一个正则缺口失效**，这件事如果被懂行的评委发现，杀伤力远大于泄露本身 —— 因为它是"安全团队对自己不严谨"的直接物证。所以这不只是一个 key 的问题，是**门面信誉问题**：把正则改成 `(sk|sk-ws|AKIA|ghp_|xox[baprs])[-_.]?[A-Za-z0-9._-]{12,}`，然后立即做一次全仓 + 交付包扫描。
