## 三、发现的问题（分级）

### 🔴 P1-1｜密钥门禁的**最强防线可静默缺席**，仍给 PASS

- 实测输出：`真 key 指纹库 0 条（⚠️ 未加载到真 key：config.yaml 缺失且无相关 env，指纹反查未生效）` → 随后 `[PASS]`。
- 成因：`secret_guard.py` 的 `load_real_fingerprints()` 取不到真值时**不 fail-closed**（`main()` 以 `return 1 if real else 0` 收尾），仅降级为形态匹配。本轮实测即命中该场景（工作树 `config.yaml` 已零明文；本地 shell 读不到 User 级 env；CI 同理）。
- 为何是 P1：**与 2026-09-13 泄露事故的失效结构同构**——上次是"省略号被无条件豁免"，这次是"最强防线缺席却被视为通过"。门禁纪律（`honest-agent` §5）要求：取不到真值必须硬失败。
- 缓解事实：本轮**独立反查**（不依赖该门禁）证明工作树与交付包均无真 key 落盘，故**本次结论仍然安全**。但这不是门禁自身的功劳。
- 建议：① 指纹库为 0 时默认 **BLOCK**，提供显式 `--no-fingerprint-ok` 逃生阀；② `make_delivery_package.py` 打包前从 Windows HKCU/环境变量注入指纹源；③ 加一条变异验证（抽掉指纹源 → 必须红）。

### 🔴 P1-2｜内置默认配置 HITL=off，与其余三份配置（approval）不一致

- 实测：`internal/config/default_config.yaml:139 → default_mode: off`；而 `config.example.yaml:139` / `config.yaml:239` / `config.share.yaml:236` 均为 `approval`。
- 该文件由 `internal/config/config.go:21 //go:embed default_config.yaml` **编译进 exe**，即"无 config.yaml 时"的默认行为。启动路径未发现强制覆盖（`hitlEffectiveDefaultMode()` 只读配置值）。
- 风险：直接运行 exe 且未配置 → **HITL 关闭**，与"赛题终审 human-in-the-loop 硬需求"的答辩口径存在落差；同时属典型"四份配置三份口径"漂移。
- 建议：内置默认改 `approval`（或至少在文档/首启向导中显式提示），并加测试锚定"内置默认必须与 config.example 的 HITL 口径一致"。

### 🟠 P1-3｜官网（对外分发页）数字严重过期，且无门禁覆盖

- 实测（`WebFetch https://truefurina.github.io/SecAutoMind/`，HTTP 200 可达）：页面自述
  **17,927 行 Go 代码 / 90+ YAML / 16 场景 Agent / 223 测试文件 / "24/26 测试包通过"**。
- 与活值对比：**126,000 非测试行 / 91 YAML / 18 Agent / 267 测试文件 / 29 包全 ok**。行数差 7 倍；"24/26 通过"更是**自降档**（实际全绿）。
- 成因：`官网/` 被 `.gitignore:81` 排除，不在版本库，口径门禁扫不到 → 无人维护。
- 建议：官网改为由脚本从 `count_stats.py --json` 注入数字；至少在材料冻结前人工同步一次。
- 附带澄清：官网"三端下载"**不是假宣称**——Pages 站点实测 200，页面含 Win/Linux/macOS 下载入口。惟 Release 资产本身未能验证（见 §四）。

### 🟠 P2-1｜跨语言 golden 的"真源一致性"门禁未接入 CI

- `.github/workflows/ci.yml` 已接入：`run_all_benchmarks.py` / `verify_evidence.py` / 密钥门禁三件套。
- **未接入**：`scripts/gen_protocol_golden.py --check`。CI 的 `go test` 只校验"Go vs golden"，不校验"golden vs 真源"。
- 后果：真源（`dasctf.py`）若变更，golden 静默过期，测试仍全绿 → 与本次 P2-2 的分叉属同一类风险。
- 客观限制：CI 环境无"西湖论剑"真源仓库。建议至少在本地 pre-commit / 打包流程中加入 `--check`，并在 CI 用 golden 文件哈希锁死。

### 🟠 P2-2｜Go 侧 flag 剥壳正则比真源更宽容，且 golden 未覆盖该分支

- 真源：`^(?:flag|FLAG|ctf|CTF|DASCTF|dasctf)\{(.+)\}$`（枚举大小写）
- Go：`(?is)^(?:flag|ctf|dasctf)\{(.+)\}$`（`(?i)` 忽略大小写）
- 差分实测（25 条用例）：**7 条分叉**，全部为混合大小写外壳 —— 真源**不剥壳**（原样提交）、Go **剥壳**：

| 输入 | 真源 | Go |
|---|---|---|
| `Flag{abc}` / `fLaG{abc}` | `Flag{abc}` | `abc` |
| `Ctf{x}` / `cTf{x}` | `Ctf{x}` | `x` |
| `Dasctf{x}` / `DASctf{x}` / `dAsCtF{x}` | 原样 | 剥壳 |

- 而 `protocol_fixtures.json` 的 13 条 flag 用例中**分叉 0 条**（无混合大小写样本）→ **测试全绿掩盖了分叉**。
- 定性：与 `0100fac` 修掉的"自加 `re-` 前缀分支"事件**完全同构**——目标侧单边"更宽容"。按本仓铁律"目标侧偏离真源一律按缺陷处理"。
- 建议：二选一 —— ① 正则改为与真源逐字一致；② 在 fixtures 增补 7 条混合大小写用例并重跑生成器（届时测试会变红，暴露差异后再定夺）。

### 🟡 P2-3｜`codeIsSuccess` 接受 int 0，真源只认字符串 `"00000"`

- 真源 `dasctf.py:562`：`ok_code = str(data.get("code", "")) == "00000"`（严格）。
- Go `dasctf.go:311-323`：`"00000"` → true；**`int 0` 也 → true**。
- 风险有限（`Accepted = okCode && isCorrect` 双条件），但同属 P2-2 的"单边放宽"类。

## 六、评价

### 6.1 能力证据强度：A

- **双语言独立实现 + SHA-256 + 反注水**三重约束下，四基准与十六利用层全绿，Go/Python 两侧逐条对齐，**0 SKIP**。
- 静态 34.5% 有**诚实拆解**（15 真求解器 + 4 flag_scan），不注水、不掩饰 36 道 MISS；执行/Web/附件/题目感知层构成与"关键词求解器天花板"的**代际差异**。
- 最难得的是**协议层**：以西湖论剑真源为唯一真值源做 golden 机验，并已修掉 6 类静默错解 + UA/Content-Type 漂移——这类问题"功能测试永远测不出来，只在赛时静默触发"。

### 6.2 工程质量：A-

- 构建 9.4s GREEN、29 包 0 FAIL、门禁三件套 + 变异验证入 CI、交付包自验三红线、包内二进制与磁盘逐字节一致。
- 扣分项集中在**"防线的可用性"而非"防线的存在"**：P1-1（最强防线可静默缺席）、P2-1（golden 真源一致性未入 CI）都属于"锁装了但没锁死"。这两条恰是本项目历史上**两次门禁失效**的同族问题，值得一次性根治。

### 6.3 材料与对外一致性：B

- 技术报告/声明函/清单口径与 `count_stats` 一致，`verify_evidence` 门禁在线。
- 但**官网**（评委可能访问的分发页）数字滞后一个数量级且无门禁覆盖；内置配置 HITL 口径不统一。对外材料是"评委第一触点"，这两条的实际扣分风险高于代码内的问题。

### 6.4 与赛题对齐度：A

- 赛题 XH-202609 五题眼（自主决策 / 通用 / 网络安全 / 智能体 / 技术研究）在能力层与材料层均有对应物；HITL + 全链路审计直接回应"决策逻辑与可解释性"评分维。
- 待补的仍是**终审门槛项**：安恒网关实测、量化效果实测。

### 6.5 一句话总评

> **这是一个"能力可测、证据可复现、口径有闸门"的决赛级工程**；短板不在能力而在两处"最后一公里"——门禁在异常输入下的失败姿态，以及对外材料（官网/内置配置）的同步纪律。
