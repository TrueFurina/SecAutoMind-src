- 控制器用 **LSILogic SCSI**（匹配原 vmx 的 `lsilogic`），网卡 **82540EM**。
- 访问：`http://127.0.0.1:8080/`（→ guest:80）、`127.0.0.1:2222`（→ 22）、`127.0.0.1:3307`（→ 3306）。
- **原始 VMDK 未改动**：先复制到 `E:/Code/Cyber range/ctf4_work/CTF4.vmdk`，逐字节大小校验一致。

## 训练第 4 轮：纯 Go DES-crypt + .htpasswd 破解（提交 `d397e4e`）

### 为什么要自己实现
靶场链条下一环是「LFI 读 `.htpasswd`（DES-crypt，13 字符）→ 破解 → SSH 登录」。
本机与服务器**都没有 john/hashcat**，服务器 python3.12 的 `crypt` 模块可用但属外部依赖。
故按 **musl `src/crypt/crypt_des.c`**（FreeSec / Solar Designer 血统）实现纯 Go 版本。

### 🔴 四处关键差异（每一处都让 10 条向量全错，必须逐条校准）
| 差异 | 错误写法 | 正确写法 |
|---|---|---|
| 口令→密钥 | 直接用口令字节 | **每字节左移 1 位**（7-bit 密钥，奇偶位清零） |
| 盐值顺序 | `(bin(s[0])<<6)\|bin(s[1])` | **`(bin(s[1])<<6)\|bin(s[0])`** |
| 盐作用点 | 交换 E 表每组 6 位前两位 | **E 输出第 i 位 ↔ 第 i+24 位**（i=0..11） |
| 输出编码 | 6 位一组 LSB 优先 | **6 位一组 MSB 优先**（11 字符，公式照 musl） |

**校准方法（重要，可复用）**：服务器 `python3.12 -c "import crypt"` 生成参考向量
（`crypt("password","ab")="abJnggxhB/yWI"` 等 10 条），写成 `TestDESCryptVectors` 逐条比对。
先单独验证**标准 DES 核心**（`key=0123456789ABCDEF`, `pt="Now is t"` → `3fa40e8a984d4815` PASS），
确认核心无误后再攻包装层——这一步把问题域从"整个 DES"缩小到"包装层 4 个参数"。
另：`WebFetch` 抓 `raw.githubusercontent.com` 全线 404，`git.musl-libc.org/cgit/plain` 可用。

### 性能与实测
- 单条 `desCrypt`：**66 µs/次**（≈1.5 万次/秒·核）；8 并发 ≈5.5 万次/秒。
- 活靶机 4 条记录（ghighland/pmoore/jdurbin/sorzek）：**4ms 扫完内置字典（约 130 词），0/4**。
  **这是正常结果**（口令不在常见弱口令内），不是缺陷；破解正确性由合成哈希测试证明
  （`TestCrackHtpasswd_Hits` / `_SaltIsRespected`）。
- 要真破开需 rockyou 级字典（~140MB，外部依赖，未引入）。

### 纪律
- `ParseHtpasswd` 只收 13 字符 DES 条目，`$apr1$`/`$2y$` 一律跳过（宁少报不误报）。
- 活靶机用例日志**只打用户名与尝试次数，不落口令明文**。
- 临时探针 `zz_des_probe_test.go` 用完即删。

## 训练第 5 轮：完整杀伤链闭环（提交 `630805e`）

**从"只给一个 URL"打到"拿到远程 shell"，全程自动。**

```
LFI 自动发现 page 参数 → /etc/passwd + .htpasswd
→ DES 破解（10 万词系统词表 + 变形）→ ghighland 命中（2m21s / 140 万次）
→ SSH 登录 → uid=505(ghighland) gid=505 groups=100(users)
→ hostname=ctf4.sas.upenn.edu
```

### 关键实现
- `CrackHtpasswdBatched`：**2 万词/批流式**展开（每词 84 变形 → 全量 877 万候选），
  避免一次性物化把内存打爆（这是第一次跑被 SIGTERM 的直接原因）。
- 变形规则：小写 / 首字母大写 / 全大写 / leet（a→@ e→3 i→1 o→0 s→$ t→7）× 21 种后缀。
- `ssh_login.go`：用 `golang.org/x/crypto/ssh`（**已是本仓直接依赖，未新增模块**）；
  显式放开 2009 年的 `diffie-hellman-group14-sha1` / `ssh-rsa`（现代默认已移除）；
  **主机密钥默认拒绝 insecure**，必须显式 `allowInsecureHostKey=true`，有守卫测试锁死。
- 口令明文只在内存传递，**不写日志、不入库**；测试只打印用户名与 `id` 输出。

### 性能实测（重要基准）
- 单条 DES crypt：66 µs（≈1.5 万次/秒·核）。
- 4 条记录 × 877 万候选：**9m59s**；单条 ≈2m21s。
- 破解率：**1/4**（字典覆盖有限，属正常结果，不是缺陷）。

### 经验
- 10 分钟级用例必须放后台跑（前台会被工具时长上限 SIGTERM 掉，且**输出文件为空**容易被误判为"没跑"）。
- `gofmt -l` + `py_compile` 每次必跑：本轮又一次因 Edit 把注释与 `func` 并到一行导致语法错。

## 训练第 6 轮：提权到 root，链条终点（提交 `66611d1`）

**一个 URL → root，全自动。**

```
ghighland 口令登录
→ cat /home/achen/.ssh/achen_priv.ppk   （私钥 -rw-rw-r-- 世界可读，Encryption: none）
→ PPK(843B) → PKCS#1 PEM(883B)
→ 以 achen 私钥登录：uid=501(achen) groups=100(users),501(achen),507(admins)
→ sudo -l: (ALL) NOPASSWD: ALL
→ sudo id → uid=0(root) gid=0(root) groups=0(root),...,10(wheel)
```

### 关键实现
- `ppk.go`：自实现 PuTTY v2 解析。SSH wire 格式 = 4 字节长度 + 内容（`string`/`mpint`）；
  🔴 **头部是 `Public-Lines: 4`（冒号后带空格），必须前缀匹配，不能整行相等**——我第一版就栽在这。
- 只支持 `Encryption: none`；加密的 PPK **明确报错**，不返回半成品 key（否则会误判成"登录失败"）。
- `ssh_login.go` 重构出 `buildSSHConfig`/`dialSSH`/`runOnClient`，新增 `TrySSHLoginWithKey`/`RunSSHCommandWithKey`。

### 🔴 两个环境坑（都很隐蔽）
1. **Go 1.24+ 默认拒绝 <1024 位 RSA**：`crypto/rsa: 1023-bit keys are insecure`。
   2009 年的靶机密钥正好 1023 位 → 握手失败，但报错在握手层，极易误判成"私钥解析错了"。
   解法：`GODEBUG=rsa1024min=0`（进程内 `os.Setenv` 即可生效）。
2. **老 sudo 1.6.x 不支持 `-n`**：`sudo -n -l` 直接报 `illegal option`；
   验证 NOPASSWD 要用 `sudo id`（无 NOPASSWD 时它会读口令失败并返回，不会挂死）。

### 🔴 门禁顺序纪律（本轮踩到）
`check_final_artifacts_freeze.py --update` 必须**最后执行**：先 `fix_material_numbers --apply` 再 update。
我先 update 后修材料 → freeze 报"生成器已改动但产物未重新上锁"，重锁一次才转绿。

### 测试
- `ppk_test.go` 6 例：往返解析、**用 `x/crypto/ssh` 这个独立消费方**校验 PEM（不是自己跟自己比）、
  拒绝加密 / v3 / 垃圾输入 / 非 ssh-rsa。
- `TestLivePrivescToRoot`：活靶机全链，默认 SKIP；支持 `CTF4_SSH_USER/PASS` 跳过破解 → **0.84s 到 root**。

### 🔴 本轮环境假红（重要，别误判成代码坏）
完整套件第一次跑 **RC=1**，唯一失败是 `TestSSRFAttackAgainstRange`：`靶场未就绪: http://127.0.0.1:18220`（等满 10s），
伴随大量 `ConnectionResetError [WinError 10054]`（客户端超时断连的噪音，不是根因）。
**真因**：上一轮整包测试在会话重置时被 SIGTERM 杀掉，**残留 python 靶场进程占着辅助端口**，导致新靶场绑不上。
判定证据：① 该用例**单独重跑 PASS（122s）**；② 随后**完整套件重跑 RC=0（567s）**。
纪律：**不许拿"单测单独跑过"当结论**，必须整包复验一次才算数。

## ✅ 已解决：靶场用例全量偶发失败的真因（提交 `4bf3488`）

**之前记的"未解决"已作废，下面是确证结论。**

### 根因（实测确证，非猜测）
跑完测试后 `netstat` 发现端口被占：
```
TCP 127.0.0.1:18220  LISTENING  10248
PID 10248 → D:\miniconda3_new\python.exe ...\ssrf_range.py 18220   （父进程已死）
```
**`cmd.Process.Kill()` 在 Windows 上没杀干净** → 靶场进程残留占着固定端口
→ 下一轮新实例绑不上（`靶场未就绪` 10s 超时），或打到**陈旧实例**（数据不同 → 取到别的场景 flag、
甚至字节损坏的 `b1n4ry`→`b1n+ry`）。

这完美解释"单独跑永远过、全量跑偶发挂"——单独跑前端口是空的。

### 修复
新增 `internal/ctfplatform/rangeproc_test.go`：
- `killProcessTree(pid)`：Windows `taskkill /PID <pid> /T /F`，其他平台退回 `Kill()`
- `killPortListeners(port)`：启动前扫 `netstat -ano` 杀掉占用端口的残留监听

两个靶场用例（`ssrf_attack_test.go` / `sqli_attack_test.go`）启动/清理各改 3 行，**不动求解器**。

### 验证
| 项 | 结果 |
|---|---|
| 两用例单独跑 | PASS，跑完 18220~18223 **无 LISTENING 残留** |
| 修复后全量 | **RC=0，565.441s**，跑完端口仍干净 |
| 修复前 3 次全量 | 2 次 SQLi + 2 次 SSRF 交替失败（单独跑均 PASS） |

### 🔴 通用教训
1. **"单独跑能过"不能证明用例没问题**——固定端口 + 不彻底清理 = 跨轮次污染，
   表现成"随机某个场景失败"，极易误判成求解器不稳定。
2. Windows 上 `Process.Kill()` 不保证杀掉子进程树，**要 `taskkill /T /F`**。
3. 排查顺序（本次有效）：先单跑排除代码 → 查端口冲突 → **查端口是否有残留 LISTENING** → 查进程命令行。
   不要一上来改求解器。

## 训练第 9 轮：盲注把「请求失败」当「布尔假」（提交 `589669a`）

修完进程残留后**又失败一次**，但现象不同：`sqli` → **`sgli`**（q→g），之前是 `4`→`+`。
**单字符错位**直接指向布尔盲注的逐字符二分。

### 根因
```go
ask := func(cond string) bool {
    _, body := sqliFire(...)   // sqliFire 把 error 吞成 (0,nil)
    return strings.Contains(body, "exists")
}
```
一次网络抖动 → 空 body → `ask` 返回 **false** → 二分往错方向收敛一个字符。
**签名里根本没有 error，调用方无从区分「假」与「请求没成功」。**

### 修法（只改错误处理，不改算法）
- `sqliFireE`：保留 error（含 `io.ReadAll` 读错误）；`sqliFire` 变薄包装，其他调用方零改动。
- `sqliAsk`：三态 `(值, 是否可信)`；**只把传输层失败算不可信**；重试 3 次（50/100/150ms）；
  仍不可信 → 中止返回 nil，**宁可不报也不产出脏 flag**。
- 🔴 踩坑：第一版把 `len(body)>0` 也算失败 → 空响应体触发大量重试，用例 0.9s→3.8s。
  **HTTP 200 + 空体是合法的「假」答案**，不能算失败。

### 同时做的系统性清理
`Process.Kill()` 的问题不止两个用例：全仓 `*_test.go` 共 **16 处**裸调用
（deser/gql/jwt/ssti/upload/web_exploit/web_hints/xxe/presolve），全部换成 `killProcessTree`。
`TestMain` 启动前再清一遍已知测试端口（18089/18090/18095/18098/18099/18220-18224），
防「上一轮被强杀」的残留。

### 验证
- `sqli_ask_test.go` 5 子用例全 PASS（true/false/前两次断连后成功/始终失败/ctx 取消）
- SQLi 两用例连跑 3 轮 **6/6 PASS**
- 全量回归 **RC=0，592.319s**，跑完端口零残留

### 🔴 教训（写进脑子）
**"单字符错位"是布尔盲注的典型症状**——不要往编码/负载上想，先看"失败是否被当成 false"。
同类风险：任何"把 error 吞成零值"的探测函数，都会在负载下静默产出错误结果。
