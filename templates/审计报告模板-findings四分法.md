# 审计 / 调研报告模板（findings 四分法）

> 对应 REA #51：**每条发现必须归类**，且带"基线命令 + 实测输出 + 预期 + 影响面 + 竞争性解释"。
> 用法：复制本文件 → 改标题 → 按节填写。**不合格的填法写在每节的"反例"里。**
> 纪律：四分法是**分类**，不是严重度分级；一条 finding 只能落一类，禁止"既是缺陷又是假设"。

---

## 0. 报告抬头（四行，缺一不可）

```yaml
报告主题: <一句话，含对象与结论方向>
审计时间: 2026-10-20
审计口径: <静态代码审 / 动态实测 / 文档对照 / 外部数据核对>
代码基线: <git HEAD 短 SHA + 是否 dirty>      # 没有基线 = 结论无法复现
环境指纹: python scripts/env_fingerprint.py | jq -c '{python,platform,git_head,deps}'
```

---

## 1. 结论先行（≤10 行）

- 一句话结论：
- 影响面（谁受影响 / 多少条记录 / 哪个环境）：
- **不成立的部分**（本次没查到的、查不了的）：
- 建议动作（按优先级 1/2/3）：

> 反例：只写"整体安全状况良好"。没有影响面与不成立部分的结论＝没有结论。

---

## 2. 发现清单（四分法）

### 2.1 已复现缺陷（reproduced defect）

> 判据：能给出**复现命令**，且在干净环境下稳定出现。

| 编号 | 现象 | 基线命令 | 实测输出/退出码 | 预期 | 影响面 | 竞争性解释（已排除） |
|---|---|---|---|---|---|---|
| D-1 | | `...` | `...` / rc=1 | | | |

- 竞争性解释怎么写：列出"还能怎么解释这个现象"，并写清**为什么排除**。
  没排除的，请把它降级到 2.3（假设）。反例：只写"疑似缓存问题"却不给排除依据。

### 2.2 有据成本（supported cost）

> 判据：这个"问题"是**该花的代价**，有文档/设计依据支持它存在。

| 编号 | 什么看起来像问题 | 为什么是合理代价 | 依据（文件:行） |
|---|---|---|---|
| C-1 | | | |

> 反例：把"没有 Redis 就无法跨进程限流"写成缺陷——单写者部署下这是设计取舍。

### 2.3 假设（hypothesis）

> 判据：有线索但**未验证**；必须写"怎么验"和"验出来会怎样"。

| 编号 | 假设 | 支持线索 | 验证方法 | 若成立的影响 |
|---|---|---|---|---|
| H-1 | | | | |

> 反例：把假设写成结论（"应该是并发导致的"），然后据此推动改造。

### 2.4 不可得证据（unavailable evidence）

> 判据：环境/权限/数据不具备，**本次无法判断**。这条不是免责声明，是待办入口。

| 编号 | 想看什么 | 为什么看不到 | 需要什么才能看到 |
|---|---|---|---|
| U-1 | | | |

> 反例：直接省略不写——"没写"会被读成"没问题"。

## 4. 自查（提交前逐条打勾）

- [ ] 每条 finding 只落一个分类，分类与"判据"一致
- [ ] 2.1 的每条都有可粘贴复现命令与真实退出码
- [ ] 2.3 的每条都有验证方法与"若成立"的影响
- [ ] 2.4 没有留空（哪怕只写"无"）
- [ ] 结论里没有"应该/大概/基本"这类无证据措辞
- [ ] 数字均能指向 registry / 测量脚本 / 本次输出，没有手抄数字
- [ ] 未把合成环境 / 演练结论写成真实效果
